Lisa: Agent-Driven Ticket Workflow

Welcome to Lisa! This guide will help you understand and work with the ticket-based agent orchestration system. Lisa automates coding work through a structured Research–Design–Structure–Plan–Implement–Review workflow.

What is Lisa?

Lisa is a ticket-driven system that runs coding agents (like Claude Code or Codex) through a structured workflow. Instead of manually approving every step, you create a ticket, and Lisa automatically guides the agent through six phases of work:

  1. Research — Map the codebase
  2. Design — Explore options and decide
  3. Structure — Define file-level changes
  4. Plan — Sequence implementation steps
  5. Implement — Execute the plan
  6. Review — Self-assess and hand off

Each phase produces a reviewable artifact (~200 lines) that captures the work at that stage. This creates a durable, auditable record and makes it easy to resume work if a session is interrupted.

Key Concepts

Tickets

A ticket is a markdown file with YAML frontmatter that describes a unit of work. Tickets live in docs/active/tickets/ and track metadata like status, phase, priority, and dependencies.

Phases

Every ticket progresses through all six phases in order. No phases are skipped—even for small changes. This ensures consistent, high-quality work and produces a complete record.

Work Artifacts

Each phase produces an artifact (a markdown file) that lives in docs/active/work/{ticket-id}/. These artifacts are the deliverables of each phase and serve as the input for the next phase.

Dependencies

Tickets can depend on other tickets. Lisa computes the dependency DAG and spawns parallel threads for tickets whose dependencies are satisfied. Multiple agents can work concurrently on different tickets.

Isolated Transactions

When agents commit code changes, they use lisa commit-ticket with an isolated Git index. This ensures that unrelated staged changes aren't accidentally committed with ticket work.

High-Leverage Phases

Research and Design artifacts are the best return on review time. Reviewing ~200 lines of research or design catches problems before they become thousands of lines of wrong code. A comprehensive design document can prevent costly implementation mistakes.

Phase 1: Research

1
Map the codebase

Produce a descriptive, ~200-line document that captures what exists, where it lives, how it connects, and what constraints or assumptions apply.

What to Include

  • Relevant files, modules, and components
  • How they connect (imports, dependencies, data flow)
  • Existing patterns and conventions
  • Constraints and assumptions
  • Architecture and boundaries

What to Avoid

  • Proposals or solutions
  • Prescriptive recommendations
  • Design decisions
Artifact: docs/active/work/{ticket-id}/research.md
💡 Why it matters: A thorough research phase prevents misunderstandings and grounds the design in reality. It answers "what exists?" before tackling "what should we build?"

Phase 2: Design

2
Explore options and decide

Enumerate viable approaches, assess each against the research, choose one, and explain the rationale. Document what was rejected and why.

What to Include

  • Multiple viable approaches (at least 2–3)
  • Tradeoffs of each approach (complexity, performance, maintainability)
  • How each approach fits with the existing codebase (grounded in research)
  • A clear decision with rationale
  • What was rejected and why

Critical Principle

⚠️ The design decision must be grounded in the research, not assumptions. If the research doesn't support a choice, go back and deepen the research. Never design in a vacuum.
Artifact: docs/active/work/{ticket-id}/design.md

Phase 3: Structure

3
Define file-level changes

Specify which files are created, modified, or deleted. Define module boundaries, public interfaces, and internal organization. This is the blueprint—not code, but the shape of the code.

What to Include

  • List of files to create, modify, or delete
  • Module boundaries and public interfaces
  • Internal organization of each module
  • The ordering of changes (where it matters)
  • Any architectural constraints or decisions

Example

Files to modify:
- src/api/auth.ts (add new token refresh logic)
- src/middleware/session.ts (integrate new token handler)
- tests/auth.test.ts (add tests for token refresh)

New files:
- src/api/token-refresh.ts (core refresh implementation)

Deleted files:
- src/api/legacy-auth.ts (replaced by auth.ts)
Artifact: docs/active/work/{ticket-id}/structure.md

Phase 4: Plan

4
Sequence implementation steps

Break the work into ordered steps that can be executed and verified independently. Define the testing strategy and specify what each step produces.

What to Include

  • Ordered implementation steps (usually 5–15 steps)
  • What each step produces (files, code changes, tests)
  • Which steps can be verified independently
  • Testing strategy (unit tests, integration tests, manual verification)
  • Verification criteria for completion
  • Any dependencies between steps

Example

Step 1: Create src/api/token-refresh.ts with core logic
  - Verify: Unit tests pass, logic is sound

Step 2: Add token refresh handler to src/api/auth.ts
  - Verify: Old and new logic coexist, no regressions

Step 3: Integrate into src/middleware/session.ts
  - Verify: Integration tests pass, middleware still works

Step 4: Delete src/api/legacy-auth.ts (old code)
  - Verify: Build succeeds, no broken imports

Step 5: Add end-to-end tests
  - Verify: Full flow works in test environment
Artifact: docs/active/work/{ticket-id}/plan.md

Phase 5: Implement

5
Execute the plan

Follow the plan step by step. For each meaningful unit of work, run lisa commit-ticket with an isolated index. Track progress in progress.md.

Key Rules

  • Use lisa commit-ticket for all ticket-owned code changes. Never use ordinary git add or git commit.
  • Specify paths exactly with the --include flag. Pass only files owned by this ticket.
  • Commit atomic units that can be reviewed and verified independently.
  • Update progress.md as you go, tracking completed steps, remaining work, and any plan deviations.
  • Document deviations if the plan needs adjustment. Explain why and proceed.

Command Example

lisa commit-ticket --ticket-id T-001 \ --message "Add token refresh logic" \ --include src/api/token-refresh.ts \ --include tests/auth.test.ts
⚠️ Before Review: Ensure every ticket-owned source change is committed through lisa commit-ticket. No staged, modified, or untracked files should remain.
Artifact: docs/active/work/{ticket-id}/progress.md

Phase 6: Review

6
Self-assess and hand off

Write two documents: review.md (a summary of changes and concerns) and review-disposition.json (a structured pass/block decision).

review.md Content

  • Summary of what changed (files created, modified, deleted)
  • Test coverage and any gaps
  • Open concerns, TODOs, or known limitations
  • Critical issues that need human attention
  • Recommendations for follow-up work

review-disposition.json

A structured document that signals whether the work is ready to complete or blocked:

Pass (Ready to Complete)

{
  "disposition": "pass",
  "reason": null
}

Block (Work Cannot Complete)

{
  "disposition": "block",
  "reason": "Actionable reason for blocking",
  "remedy_owner": "agent|operator|world",
  "ask": "One sentence describing the action needed",
  "steps": ["optional exact step"],
  "check": "read-only verification command"
}

Choosing remedy_owner

Owner When to Use Example
agent Another coding attempt can fix it Tests are failing; need to fix implementation
operator A person must act Need API keys configured; need manual deployment
world External reality must change Waiting for another team to publish a library

After Writing Review

⚠️ Important: After writing review.md and review-disposition.json, remain on the current ticket and wait. Do not edit phase/status, publish completion yourself, or start another ticket. Lisa will detect the artifacts, prepare the final commit, and confirm completion before releasing the seat.
Artifacts:
  • docs/active/work/{ticket-id}/review.md
  • docs/active/work/{ticket-id}/review-disposition.json

Ticket Format

Tickets are markdown files with YAML frontmatter. They live in docs/active/tickets/.

--- id: T-024-03 story: S-024 title: migrate-climate-calls type: task status: open priority: high phase: ready depends_on: [T-024-01, T-024-02] --- ## Context Description of the work and why it matters. ## Acceptance Criteria - Concrete, verifiable condition 1 - Concrete, verifiable condition 2

Field Reference

Field Type Description
id string Unique ticket identifier (e.g., T-024-03) required
story string Parent story ID (e.g., S-024) optional
title string Kebab-case short name required
type enum task | bug | spike required
status enum open | in-progress | review | done | blocked required
priority enum critical | high | medium | low required
phase enum ready | research | design | structure | plan | implement | review | done required
depends_on array List of ticket IDs that must complete first optional
blocks array Computed automatically from depends_on; do not edit optional

Important Notes

  • Phase field: Lisa automatically updates this as artifacts are completed. Do not edit it manually.
  • Status field: This tracks human workflow state. Lisa uses phase to track agent progress.
  • Dependencies: Lisa computes the DAG and respects dependencies. List all blocking tickets in depends_on.

Work Artifacts

Each ticket has a work directory at docs/active/work/{ticket-id}/. Artifacts are created as each phase completes:

Six Artifacts (One Per Phase)

  1. research.md — Codebase map (~200 lines)
  2. design.md — Option exploration and decision (~200 lines)
  3. structure.md — File-level blueprint (~200 lines)
  4. plan.md — Implementation steps (~200 lines)
  5. progress.md — Progress tracking during implementation
  6. review.md — Self-assessment (~200 lines)
  7. review-disposition.json — Pass/block decision (structured)

Artifact File Naming

Use consistent, descriptive names:

  • research.md — Always this name
  • design.md — Always this name
  • structure.md — Always this name
  • plan.md — Always this name
  • progress.md — Updated during implementation
  • review.md — Always this name
  • review-disposition.json — Always this name

Artifact Purpose

Artifacts serve multiple purposes:

  • Human review: Each artifact is ~200 lines and reviewable at a glance
  • Session recovery: If a session crashes, the latest artifact + ticket is enough to resume
  • Audit trail: The complete workflow is recorded in these documents
  • Feedback loop: Reviewers can approve, request changes, or block based on artifacts

Getting Started

Step 1: Understand the Project

  1. Read CLAUDE.md for the project context and conventions
  2. Review .lisa.toml for Lisa configuration
  3. Explore the existing tickets in docs/active/tickets/

Step 2: Create a Ticket

  1. Write a new ticket file in docs/active/tickets/
  2. Use the ticket format described above
  3. Set phase: ready to signal it's ready for work
  4. Add to the ticket board (git commit + push if using a remote)

Step 3: Run Lisa

  1. Start Lisa (command depends on your setup—check .lisa.toml for runtime config)
  2. Lisa will schedule the ticket and spawn an agent to work on it
  3. The agent will progress through all six phases

Step 4: Review Artifacts

  1. As each artifact is completed, review it for quality and correctness
  2. Provide feedback in the ticket or work directory
  3. Lisa will wait for human approval or adjustment before continuing

Step 5: Verify Completion

  1. Once the Review phase completes, Lisa publishes the work
  2. Verify that code changes are committed and tests pass
  3. Mark the ticket as done
✓ Tip: Start with a small, well-defined ticket to familiarize yourself with the workflow. The smoke ticket T-001 is a good first example.

Frequently Asked Questions

Q: Why do all six phases always run?

A: Because discipline around process prevents bugs later. Research and Design are the highest-leverage phases for catching problems early. Even "small" changes benefit from structured thinking. Skipping phases degrades context and creates inconsistent records.

Q: Why ~200 lines per artifact?

A: It's a forcing function. Long enough to be thorough, short enough to review in 10 minutes. It encourages structured thinking and makes the work digestible for humans.

Q: What if I need to deviate from the plan during implementation?

A: Document the deviation in progress.md. Explain what changed and why. Continue with the implementation. Reviewers will see the deviation and can ask questions.

Q: Can multiple agents work on different tickets in parallel?

A: Yes! Lisa respects ticket dependencies. If ticket A depends on ticket B, Lisa waits for B to complete before starting A. Otherwise, multiple agents work concurrently on different tickets.

Q: What if a session crashes during implementation?

A: The latest artifact plus the ticket is enough information to resume at the correct phase. Source code changes are committed through lisa commit-ticket, so they're durable. Restart the session and continue.

Q: How do I know when a ticket is ready to review?

A: When the agent reaches the Review phase and produces review.md and review-disposition.json. The disposition document will indicate pass or block. If it's a block, the remedy is specified.

Q: Can I edit the phase field manually?

A: No. Lisa updates the phase field automatically as artifacts are completed. Editing it manually will confuse Lisa. Let the process drive the phase.

Q: What does "remedy_owner: world" mean?

A: It means external reality must change before the work can complete. For example, waiting for another team to publish a library, or waiting for an infrastructure change. The Review document will specify what to wait for and how to verify it.

Q: How do I handle dependencies between tickets?

A: Use the depends_on field in the ticket frontmatter. List the IDs of all tickets that must complete before this one starts. Lisa computes the DAG and respects these dependencies.

Q: Can I have tickets that modify the same files?

A: Only if there's an explicit dependency edge. If two tickets modify the same files without one depending on the other, that's a missing dependency in your DAG. Add the dependency to avoid merge conflicts.

Q: What happens if lisa commit-ticket fails?

A: The commit didn't happen. Check the error, fix the issue, stage the changes again, and retry the lisa commit-ticket command. Never use ordinary git commit.
