# 04 · Risks & open questions (verified claim ledger)

> Part of the **Codex client intel packet** (`docs/knowledge/codex-client/`). See [README](./README.md).
> Generated 2026-07-01. Each claim was tested adversarially against official Codex sources (verifiers defaulted to refuted/uncertain unless docs clearly supported it).

## How to read this

- **✅ confirmed** — official sources clearly support it; safe to design around.
- **❌ refuted** — sources contradict it or it does not hold reliably; do NOT assume it.
- **❓ uncertain** — undocumented; must be settled empirically by a spike before committing.

Confidence is the verifier's confidence in its *verdict*, not in the claim.

## Claim ledger

### ❓ UNCERTAIN · A Codex lifecycle hook subprocess (e.g. a Stop hook) inherits environment variables set on the codex process at launch time, so an orchestrator can pass a pane id via env and have the hook script read it back.

**Confidence in verdict:** high

**Evidence:** No official Codex doc confirms that hook command subprocesses inherit the parent codex process environment. The hooks / config-advanced page documents ONLY: (1) working directory -- verbatim "Commands run with the session `cwd` as their working directory."; and (2) a small set of env vars explicitly provided to PLUGIN-bundled hooks -- verbatim "PLUGIN_ROOT is a Codex-specific extension that points to the installed plugin root.", "PLUGIN_DATA ... points to the plugin's writable data directory.", and "Codex also sets `CLAUDE_PLUGIN_ROOT` and `CLAUDE_PLUGIN_DATA` for compatibility with existing plugin hooks." When fetched specifically for env-inheritance language, the hooks page "does not explicitly state whether hook commands inherit the parent Codex process environment, nor does it mention environment variable filtering, a shell_environment_policy, or other mechanisms for controlling which environment variables are passed to hooks." config-reference contains no hook env statement (defers to the Hooks guide). The only documented env-control mechanism, `shell_environment_policy`, is scoped in config-advanced verbatim to "which environment variables Codex passes to any subprocess it launches (for example, when running a tool-command the model proposes)" -- the examples are model-proposed tool/shell commands; the docs are SILENT on whether this policy also governs hook subprocesses. Its default is inherit = "all" (third-party danielvaughan: "The default is inherit = \"all\""), under which an arbitrary launch-time var like PANE_ID would flow through EXCEPT for a default case-insensitive KEY/SECRET/TOKEN name filter (ignore_default_excludes = false by default) -- PANE_ID would survive that filter, but the widely recommended production setting inherit = "core" would strip a custom PANE_ID. GitHub issue #3064 (open enhancement) shows Codex's own shell "does not inherit your terminal's environment variables" in sandboxed contexts, underscoring that inheritance is policy-dependent and non-obvious. Net: the specific claim (hook inherits launch-time env) is plausible under default behavior but is NOT documented for hooks anywhere in official sources, and is undermined if shell_environment_policy applies to hooks with a non-"all" inherit setting.

**Implication for lisa→Codex parity:** Do NOT rely on env-var inheritance to pass a Zellij pane id into a Codex Stop/on-clear hook without empirically testing it on the pinned codex version. Two failure modes: (a) if shell_environment_policy governs hooks and the user/profile sets inherit="core" (the recommended production default), a custom PANE_ID would be dropped; (b) the whole hooks surface is volatile (flag renamed codex_hooks -> features.hooks, open bug #17532 where repo-local hook config does not fire interactively). Safer parity design: pass correlation data through the documented hook stdin JSON payload (session_id, cwd, transcript_path, hook_event_name) rather than inherited env. If env is required, make it explicit via shell_environment_policy.set (though its application to hooks is itself unconfirmed) and pin/verify per version. Lisa's .lisa/hooks/on-stop.sh / on-clear.sh mapping onto Codex Stop / SessionStart(source=clear) should not assume env inheritance until proven.

**Sources:** https://developers.openai.com/codex/hooks, https://developers.openai.com/codex/config-advanced, https://developers.openai.com/codex/config-reference, https://github.com/openai/codex/issues/3064, https://codex.danielvaughan.com/2026/04/28/codex-cli-shell-environment-policy-subprocess-secrets-defence/

### ❌ REFUTED · A Codex 'Stop' hook fires reliably at the end of every agent turn in an INTERACTIVE (TUI) session on the current stable version — i.e. issue #17532 does NOT block using Stop hooks to detect turn completion in a live pane.

**Confidence in verdict:** medium

**Evidence:** Multiple points contradict the strong claim ("reliably", "every turn", "#17532 does not block interactive"):

1) DOCS make no interactive-reliability guarantee. developers.openai.com/codex/hooks only states Stop "run[s] at turn scope" and describes fields (turn_id, stop_hook_active, last_assistant_message) and the continuation shape {"decision":"block","reason":"..."}. It never says Stop fires in interactive TUI, and draws no interactive-vs-exec distinction. No verbatim "fires at end of every turn."

2) #17532 is OPEN and unresolved (closedAt: null; labels bug, hooks; created 2026-04-12). Although titled around repo-local .codex/config.toml, a detailed repro by swchen44 on **codex CLI 0.132.0** (2026-05-21) shows hooks (SessionStart) NEVER fire in BOTH `codex exec` AND interactive `codex` TUI — even with user-level $CODEX_HOME/hooks.json, project trust pre-seeded, and --dangerously-bypass-hook-trust. Quote: "the hook executor itself never runs the command for either mode ... It's specifically the codex client-side dispatch that doesn't deliver the event." Confirmations stack up across versions: 0.128.0 (coladapo), 0.132.0 (swchen44), plus multiple "same"/"+1". So the failure is broader than the repo-local scoping the claim leans on, directly contradicting "#17532 does NOT block ... in a live pane."

3) CONFLICTING evidence prevents a clean "never works": OpenAI COLLABORATOR abhinav-oai (2026-04-15) posted a working Stop-hook setup via .codex/hooks.json and "was not able to repro." So behavior is environment/version-dependent, not "reliable."

4) #22858 (CLI/TUI, 0.130.0) reports Stop does NOT fire when a turn is interrupted with Esc: "After interrupting an active turn with Esc, the configured Stop hook does not appear to run." This directly refutes "end of EVERY agent turn" — interrupted/cancelled turns are not covered, so hook-driven "running->idle" state can get stuck.

5) #21639 reports a regression where .codex/hooks.json hooks (SessionStart, PreToolUse) stopped running entirely after a Codex Desktop update (cli_version 0.129.0-alpha.15), evidence the executor wiring is fragile version-to-version.

Current stable is 0.142.5 (2026-07-01); the most recent interactive-mode confirmation on #17532 is 0.132.0 with no fix/close, so there is no official signal it is resolved on current stable.

**Implication for lisa→Codex parity:** For lisa->Codex parity, do NOT assume a Stop hook is a reliable turn-completion signal in a live interactive pane. It cannot back-stop lisa's on-stop.sh detection: (a) an OPEN bug (#17532), confirmed up to 0.132.0 in interactive TUI (not just repo-local config), reports the executor silently not delivering events on some setups; (b) even where Stop works, it is documented/reported NOT to fire on Esc-interrupted turns (#22858), so "every turn" fails and state can stick on Running; (c) it is a rapidly-drifting, fragile surface (regression in #21639). The safer parity path is headless `codex exec` (single-shot exit = deterministic turn boundary, or `--json` turn.completed events) rather than interactive-TUI Stop hooks. If interactive Stop hooks are required, prefer user-level ~/.codex/hooks.json (standalone JSON, not inline repo config), pin an exact version, and verify empirically per upgrade — never treat it as guaranteed.

**Sources:** https://developers.openai.com/codex/hooks, https://github.com/openai/codex/issues/17532 (OPEN; repro on 0.128.0, 0.132.0 in exec AND interactive TUI; collaborator abhinav-oai non-repro 2026-04-15), https://github.com/openai/codex/issues/22858 (Stop does not fire on Esc-interrupted turn, 0.130.0), https://github.com/openai/codex/issues/21639 (hooks stopped running after Desktop update, 0.129.0-alpha.15), gh release: current stable rust-v0.142.5 (2026-07-01)

### ✅ CONFIRMED · In an interactive Codex session, typing '/clear' resets conversation context in-place and a 'SessionStart' hook with source='clear' fires afterward, giving an orchestrator a detectable 'context was reset' signal.

**Confidence in verdict:** high

**Evidence:** Part 1 (in-place reset): The official slash-commands page describes /clear verbatim as "Clear the terminal and start a fresh chat," with the fuller text "Codex clears the terminal, resets the visible transcript, and starts a fresh chat in the same CLI session" — explicitly contrasted with Ctrl+L which only clears the view. So /clear does reset conversation context within the same running CLI process (in-place). Note a documented contradiction: the /cli/features page reportedly claimed /clear "preserves conversation history"; the authoritative slash-commands page overrides this, and the existence of SessionStart source=clear corroborates a true context reset.

Part 2 (SessionStart source=clear fires): The official /codex/hooks page documents the SessionStart matcher applying to the `source` field with verbatim values "How the session started: `startup`, `resume`, `clear`, or `compact`." SessionStart also supports `hookSpecificOutput.additionalContext` ("That additionalContext text is added as extra developer context"). So a hook can match source=clear and react to the reset.

CRITICAL RELIABILITY CAVEAT (version-dependent): GitHub issue #17532 (OPEN, reproduced on Codex CLI v0.120.0, npm, macOS Apple Silicon) reports verbatim that "codex_hooks do not fire in interactive sessions when configured via repo-local .codex/config.toml" — specifically "no evidence that SessionStart fired" and "no evidence that Stop fired" in interactive sessions, even though the same scripts work when run manually. Also note the enable-flag key drift: the issue uses `[features] codex_hooks = true` (v0.120.0) while current docs use `features.hooks`. So while the source=clear signal is documented, its actual delivery for a repo-local-configured hook in interactive mode is a known open bug.

**Implication for lisa→Codex parity:** For lisa->Codex parity, mapping a Claude-Code-style on-clear hook onto Codex's SessionStart(source=clear) is the correct, documented approach — the "context was reset" signal exists in the schema. However, the orchestrator should NOT rely on repo-local .codex/config.toml hooks for this in interactive sessions due to open bug #17532; prefer user-level hooks (~/.codex/hooks.json or ~/.codex/config.toml), which are independent of project trust and not implicated by the bug. Verify empirically on the pinned Codex version (issue was on v0.120.0; current stable ~0.142.x) and confirm the enable flag is `features.hooks` (renamed from codex_hooks). Also confirm the SessionStart hook actually fires on interactive /clear (not just startup) on the target version, since the whole hooks subsystem is the most volatile automation surface.

**Sources:** https://developers.openai.com/codex/hooks, https://developers.openai.com/codex/cli/slash-commands, https://github.com/openai/codex/issues/17532

### ❌ REFUTED · A Codex 'PostToolUse' hook fires frequently enough during normal agent work to serve as a liveness/heartbeat proxy for stuck-detection (tool-free stretches are short enough not to trip a ~20min stuck threshold falsely).

**Confidence in verdict:** medium

**Evidence:** Official hooks docs (developers.openai.com/codex/hooks) define PostToolUse as purely event-driven: "PostToolUse runs after supported tools produce output, including Bash, `apply_patch`, and MCP tool calls. For Bash, it also runs after commands that exit with a non-zero status." The docs contain NO mention of any heartbeat/timer/periodic firing — every event ties to a discrete tool completion or lifecycle moment, not a time interval. There is no documented cadence guarantee, so "fires frequently enough" is unsupported by any source. Concrete counterexamples where the agent is alive but PostToolUse is silent for potentially >20min: (1) A single long-running tool call (build, full test suite, large download, `sleep`) — PostToolUse fires ONLY after the command returns, so the entire in-flight duration produces zero events, which is precisely a long tool-free stretch that could false-trip a ~20min threshold on a busy agent. (2) Reasoning/planning-heavy or agent_message-only turns produce no tool call and thus no PostToolUse. (3) A PermissionRequest awaiting human approval can sit indefinitely with no PostToolUse. Coverage is also narrower/buggier than the claim assumes: issue #16732 (CLOSED, fixed by PR #18391 "fix(core): emit hooks for apply_patch edits", merged 2026-04-22) confirms that before ~v0.119 PreToolUse/PostToolUse never fired for apply_patch file edits — only Bash — and hardcoded tool_name:"Bash". A third-party governance reference (April 2026) still states "PreToolUse intercepts the shell (Bash) tool only — by design" and that apply_patch, Read/Edit/Write, web fetch, and MCP calls "do not fire it," meaning edit-heavy or MCP-heavy turns could yield no PostToolUse on affected versions. Additionally, issue #17532 (OPEN) reports repo-local .codex/config.toml hooks do not fire at all in interactive sessions. Version-dependence is severe: hooks engine launched v0.114.0 with only SessionStart/Stop and grew to 10 events; apply_patch emission only landed ~v0.119; current stable is 0.142.5.

**Implication for lisa→Codex parity:** For lisa->Codex parity, do NOT rely on PostToolUse as a liveness/heartbeat signal. It is event-driven with no cadence guarantee and has documented dead zones (long single tool calls, reasoning-only turns, approval waits) that can exceed a 20min window while the agent is genuinely working, causing false "stuck" positives; and on some versions/config paths (pre-0.119 apply_patch, repo-local interactive #17532, MCP-only turns) it may not fire at all. A robust stuck-detector should instead consume the `codex exec --json` event stream (turn.started/turn.completed/item.started/item.completed, incl. reasoning and command_execution items) which captures activity that never surfaces as a tool completion, and/or treat a long-running in-flight tool as "alive" explicitly rather than inferring liveness from hook silence. If hooks are used at all, pin an exact Codex version and verify firing empirically per upgrade.

**Sources:** https://developers.openai.com/codex/hooks, https://github.com/openai/codex/issues/16732, https://github.com/openai/codex/pull/18391, https://github.com/openai/codex/issues/17532, https://agenticcontrolplane.com/blog/codex-cli-hooks-reference, https://developers.openai.com/codex/noninteractive

### ❌ REFUTED · The interactive Codex TUI can be driven by injecting keystrokes into a terminal pane (type prompt text, then Enter as a separate write) reliably enough for unattended orchestration, matching how lisa drives Claude Code today.

**Confidence in verdict:** medium

**Evidence:** No official Codex source documents, supports, or recommends driving the interactive TUI via injected keystrokes. Both official pages I fetched steer automation to the non-interactive path instead: the features page says "Automate workflows or wire Codex into your existing scripts with the `exec` subcommand. This runs Codex non-interactively," and the noninteractive page frames `codex exec` as running "from scripts (for example, continuous integration (CI) jobs) without opening the interactive TUI." Neither page mentions keystroke injection or TTY driving as a supported mode.

The load-bearing reliability claim is actively contradicted by the TUI's documented input model plus a cluster of GitHub bugs. The config key `disable_paste_burst` exists specifically because the TUI runs "burst-paste detection" (config-reference: "Disable burst-paste detection in the TUI."). PR #18914 restores a shared 8ms character-to-character burst-detection interval across platforms and confirms the heuristic: rapidly-arriving characters (exactly what a keystroke-injection write produces) are classified as a paste, and Codex's own bot note in that PR states "gaps above this value reset `consecutive_plain_char_burst`, so burst mode never activates and Enter suppression may not apply" — i.e. Enter handling is entangled with, and altered by, burst state. The TUI also "waits briefly before flushing a single typed character while it checks whether a paste burst is forming," so injected input is timing-sensitive.

Concrete failure modes are reported bugs, not speculation: #2006 "Pasted newline auto-submits"; #10065 "Pasting multiline text triggers auto-submit and strips newlines (v0.89.0–0.92.0)" (content loses line breaks, submits without confirmation); #13729/#4401 Windows multiline paste executes immediately / drops characters; #20580 regression where Shift+Enter/Alt+Enter no longer insert a newline (submits instead). These show that whether an injected Enter (or an embedded newline) submits, is swallowed, or strips text is version-, platform-, and timing-dependent. Contrast: lisa itself runs inside Zellij, and Codex explicitly special-cases Zellij (tui.alternate_screen default "auto skips it in Zellij to preserve scrollback"), i.e. terminal-environment quirks are a known variable.

**Implication for lisa→Codex parity:** For lisa->Codex parity, do NOT assume the Claude-Code-style "write prompt text, then write Enter separately into the pane" drives Codex reliably. It may work opportunistically but is unsupported and fragile: the 8ms paste-burst heuristic can buffer the injected text as a paste, an embedded/near-simultaneous newline can auto-submit early or get stripped, and Enter suppression during burst mode is version/platform-dependent. If pane-injection must be used, mitigate with `disable_paste_burst = true` and send Enter as a distinct write separated well beyond the burst interval — but treat this as best-effort. The parity-preserving path is to drive Codex through `codex exec` (single-shot, `--json`/`-o`, resume for continuity), which OpenAI documents for exactly this orchestration use case, rather than TUI keystroke injection. This aligns with lisa's spawn-and-track model without depending on undocumented TUI input behavior.

**Sources:** https://developers.openai.com/codex/cli/features, https://developers.openai.com/codex/noninteractive, https://developers.openai.com/codex/config-reference, https://github.com/openai/codex/pull/18914, https://github.com/openai/codex/issues/2006, https://github.com/openai/codex/issues/10065, https://github.com/openai/codex/issues/13729, https://github.com/openai/codex/issues/4401, https://github.com/openai/codex/issues/20580

### ✅ CONFIRMED · Under '--dangerously-bypass-approvals-and-sandbox' (--yolo), Codex raises no approval/PermissionRequest prompts, so there is effectively no 'awaiting human input' state for an orchestrator to handle (unlike Claude Code's AskUserQuestion).

**Confidence in verdict:** medium

**Evidence:** Official docs support the core mechanic. agent-approvals-security / cli/reference describe --dangerously-bypass-approvals-and-sandbox (--yolo) as "No sandbox; no approvals (not recommended)" and "Run every command without approvals or sandboxing. Only use inside an externally hardened environment." So documented behavior: no approval/PermissionRequest gate fires and Codex does not pause for human sign-off. The noninteractive page separately confirms codex exec "does not pause for human input" and runs to completion; -a never / --ask-for-approval never also "skips approval checks entirely" (and unlike --yolo keeps the sandbox). Codex's hooks engine has a distinct PermissionRequest event that fires before an approval prompt; with no approvals requested, no such prompt/event occurs — consistent with the claim. CAVEATS that lower confidence to medium: (1) The claim's absoluteness ("effectively no awaiting-human-input state") is contradicted in practice by a SEPARATE gate — the directory-trust prompt. OPEN issue #14345 (codex-cli 0.114.0) reports "--dangerously-bypass-approvals-and-sandbox flag no longer suppresses directory trust prompts"; users still get "Do you trust the contents of this directory?" ("That defeats the purpose of using the --dangerously-bypass-approvals-and-sandbox option"), suspected regression from PR #11874. That IS an awaiting-input state surviving --yolo. (2) Historical CLOSED bug #4565 (v0.42.0): "codex exec --dangerously-bypass-approvals-and-sandbox ... hangs forever" at exec_approval_request for an rm command — evidence the bypass has intermittently failed to actually skip approval. (3) The comparison "unlike Claude Code's AskUserQuestion" is not in any official doc — Codex has no documented AskUserQuestion-equivalent blocking question tool; the model can still emit clarifying questions as free text (in the interactive TUI a human could answer; in headless exec the run just proceeds/ends and never blocks). This part is inferred, not documented. Version-dependent: approval/trust behavior around --yolo is actively churning (issues on v0.42, v0.114; current stable ~0.142.x).

**Implication for lisa→Codex parity:** For lisa->Codex parity: with --yolo (or the safer -a never -s workspace-write / deprecated --full-auto), Codex generally will NOT surface a mid-task tool-approval gate that an orchestrator must answer, so lisa does not need a Claude-Code-style AskUserQuestion/permission-response path for command execution. BUT do not treat "no awaiting-input state" as guaranteed: (a) a first-time directory-TRUST prompt can still block even under --yolo (open bug #14345) — mitigate by using headless `codex exec` (which does not pause), pre-trusting the project (projects.<path>.trust_level="trusted"), and/or --skip-git-repo-check, rather than relying on --yolo to suppress it; (b) prefer `codex exec` for deterministic no-input behavior since the interactive TUI is where trust/clarification prompts appear; (c) verify empirically on the pinned Codex version because this behavior has regressed across releases.
