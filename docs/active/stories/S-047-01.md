**Scope:** Make the lisa-loop experience state its own point, in words an agent can quote to a nontechnical person. Two surfaces: (1) the context Lisa injects into every agent session — the workflow preamble and assignment framing in crates/lisa-cli/src/templates.rs — opens with the S-046-07 purpose paragraph (runs your coding agents against a ticket board; no per-step approvals; evidence trail you can audit), byte-consistent with that story's copy, not re-worded; (2) a post-run narrative — when a loop session ends (and in `lisa status` where a completed board makes it true), Lisa summarizes the win in plain language with real numbers and real paths: how many tickets completed, that zero manual approvals were requested, and where the evidence lives (.lisa/provenance.jsonl, the completion journal, per-ticket work docs). Measured by the landing-probe series (docs/knowledge/landing-probes/README.md): the next probe entry on this surface must flip Benefit and Evidence to yes.

**Story acceptance:** String tests assert the injected context opens with the purpose paragraph before mechanism vocabulary and that it matches S-046-07's canonical sentence; the post-run summary is asserted against fixture runs with known counts, reports only true states (a run with failures says so — the summary never launders a bad run into a good sentence), and names the ledger paths only when the files exist. A scored landing-probe entry on the 0.4.1-rc surface is recorded in the series table with rubric columns 1–3 yes.

**Honest boundary:** Copy and reporting only — no changes to scheduling, completion gating, or state machinery; the summary reads existing state, it never writes or infers it. The probe run is manual and metered (John operates), same evidence discipline as the Chromebook-test tickets: absent run evidence means a named blocked state, not an assumed pass. Cross-epic dependency on T-046-07-02 is deliberate — same file, same sentence, serialized edits.
