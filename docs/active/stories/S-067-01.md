**Scope:** When startup is not observed on a pane, `begin_startup_recovery` types
a shell-readiness probe into it. Against a live agent that probe cannot be
answered — and on a desk whose agents are correctly written, it **must not** be.

Measured on `screen-design`, 2026-08-13, from the agent's own transcript:

```
19:45:36  user       command printf '%s' '{"ticket_id":"T-019-03","attempt_id":2}' \
                     > '.lisa/signals/pane-1.shell-ready.tmp.2-…' && command mv …

19:45:49  assistant  That's lisa's attempt-2 ready signal, not something I should write —
                     rail and its agents never write into `.lisa/signals/`; lisa owns that
                     file. Running it from here would tell the scheduler a pane is ready
                     when it isn't.
```

**The agent was right.** That project's invariants say an agent never writes into
`.lisa/` — *"a monitor that can perturb what it monitors is not one"*. So the
probe was refused, no `.shell-ready` ever arrived, the seat failed, and the pane
died with a working agent inside it.

## Lisa already knows this path is wrong

`crates/lisa-plugin/src/lib.rs:4776`, in lisa's own words:

> *"This is deliberately not `begin_startup_recovery`. That path interrupts the
> pane and probes it for a shell, which is a dead end against a live TUI: a
> `--dangerously-skip-permissions` session executes the probe command on the
> scheduler's behalf and **forges the readiness proof**."*

`T-062-01-04`'s era shipped `test_unobserved_startup_on_a_resident_pane_re_exits_instead_of_probing`
for the leg where residency is *proven*. These panes proved nothing, so they took
the old branch — and the old branch has two outcomes and both are bad:

| the agent | what happens |
| --- | --- |
| runs the probe | forges a readiness proof for a pane that is not ready |
| refuses it | the seat is never recovered and the pane dies |

**A well-behaved agent gets the worse one.** Every project that teaches its agents
not to write into `.lisa/` is a project where this reset always fails.

## What triggered it here

WezTerm crashed. The zellij server outlived it, both agents kept working, and the
scheduler kept stamping — the work was fine. What lisa saw was startup evidence it
could not confirm, so it reset two live seats twelve minutes into their attempts.

**The crash cost nothing. The recovery cost both seats.**

## And the ledger recorded none of it

`T-019-01` and `T-019-03` each have two attempt directories with assignment files,
and:

```
grep 'T-019-01' .lisa/provenance.jsonl         → nothing
grep 'T-019-01' .lisa/completion-journal.jsonl → nothing
```

Two assignments written, twelve minutes of agent work, a reset, a dead pane — and
the record says no attempt ever happened. Both tickets sat at `phase: review` with
no seat and no artifacts, which is a state nothing on the board can explain.
`T-067-01-02` is that half.

**Non-goals.** Not removing recovery. A pane whose startup genuinely failed still
needs a way back. Not weakening the rule agents follow — `read-only-projects` is
right, and a scheduler that depends on agents breaking it is the thing to fix.
