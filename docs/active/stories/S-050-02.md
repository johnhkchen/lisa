**Scope:** Old projects should learn about new knobs without reading release notes. (1) **Upsert new sections.** Re-running `lisa init` on an existing project adds missing config sections to `.lisa.toml` as commented stubs — `[agent]`, `[guards]`, `[triage]`, and any missing `[scheduling]` keys — each with a one-line plain-English comment saying what it does and its default. Existing values, comments, and ordering are preserved per init's established merge discipline; only genuinely absent sections are appended. This closes the memorized field gap (re-init never adds the missing `[agent]` section to old `.lisa.toml` files) and makes the release audit's "undiscoverable config" finding structurally impossible for future knobs. (2) **One source for descriptions.** The stub comments and the README configuration table draw from a single source (or are byte-sync-tested the way the bundled workflow doc is), so a future knob cannot ship without its kitchen-table description landing in both places — adding a config key without describing it plainly becomes a CI failure, not a review nitpick.

**Story acceptance:** Fixture tests: a 0.4.3-era `.lisa.toml` (dirs + scheduling only) re-inits to gain all current sections as commented stubs with prior bytes preserved in place; a fully current file re-inits to a no-op; a file with customized values keeps every one. The description source is single: a test enumerates all parsed config keys (config.rs/types.rs) and fails if any lacks a description entry; README table sync is test-pinned. Stub comments pass the brand-voice bar (no jargon, verb-forward).

**Honest boundary:** Upsert adds commented stubs only — it never changes an effective value, never uncomments, never reorders. The enumeration test guards keys parsed by the CLI config; plugin-internal tuning stays out of scope. No new knobs are added here; this story is plumbing for describing the ones that exist.
