**Scope:** Putting a machine on a channel should be `brew install lisa-nightly`, or
one line in an apt sources file. `S-068-01` made it `lisa upgrade --channel nightly`
into `~/.local/bin`, which means a box has to *leave* its package manager to join
the fleet. That is backwards, and it is the reason the Mac mini's setup begins with
`brew uninstall lisa`.

## The channel primitive already exists, twice

A package manager's answer to "which line of this software do you want" is the
package you install. Homebrew says it with the formula name — `python@3.11`,
`postgresql@16`. Debian says it with the suite — `stable`, `testing`, `unstable`.
Neither needs teaching. **Both are already what `brew install` and `apt-get install`
mean to anyone who has used them.**

Lisa publishes into exactly one of each. Verified 2026-08-14:

| where | what is there | what it means |
| --- | --- | --- |
| `johnhkchen/homebrew-lisa` | one `Formula/lisa.rb` | one line, and with `publish-prereleases = true` it is the newest of anything |
| the apt repo | one suite — `dists/stable`, hardcoded through `scripts/build-apt-repository.sh` | one line |

So the Mac mini, on Homebrew `lisa 0.4.4` since 2026-08-06, is not on "no channel."
**It is on canary, with a manual trigger nobody pulls** — `brew upgrade lisa` would
take it to a release candidate, because the one formula named `lisa` publishes
prereleases.

**Correction, from `screen-design`'s measurement of the machine on 2026-08-14:
the mini is not stale.** An earlier draft of this story called it five days
behind. It is not behind anything — `v0.4.4` is the newest release that is not a
prerelease and has been since 2026-07-19, so the machine has been exactly current
on the line it should be on for four weeks. What is broken is that nothing on it
can say so: `brew outdated` reports `0.4.4 < 0.5.0-rc.2` and is wrong about what
that means. The machine is fine; the channel it is subscribed to is a lie. That
is a sharper statement of this story's case than staleness was.

## What this changes about `S-068-01`

**Channel stops being a file.** `T-068-01-01` put it in a per-user config because
there was nothing else to read. On a package-managed box, `brew list` and `dpkg -l`
already answer it — and a config file that can disagree with the installed package
is a second source of truth that will eventually be wrong.

**Soak inverts.** Today it is a client-side rule: `DEFAULT_SOAK_HOURS = 24` in
`channel.rs`, with every machine running its own clock against the release list. If
channels are packages, soak belongs to the *publisher* — a release lands in canary
at once and is promoted into nightly a day later if nothing superseded it. Decided
once, centrally, instead of twenty boxes each deciding it again. **Then `brew
upgrade` on its own is correct, with no Lisa logic in the path at all.**

**What stays Lisa's is the part no package manager does.** The 04:30 schedule, the
refusal to move under a live Zellij session, the alarm that leaves the machine, and
`doctor` naming the gap. `lisa nightly` keeps all of it; only the fetch-verify-swap
step delegates.

## The sharp edge: rollback

Apt gets it free — the pool keeps old versions, so `apt-get install lisa=<version>`
is a real rollback with no extra machinery.

**Homebrew does not.** `brew switch` was removed, and pinning an old version means
checking out an old tap commit or maintaining `lisa@<version>` formulae forever.
This is the one thing the shell installer does better, and it is why `lisa upgrade
--tag` should survive as the escape hatch on brew boxes rather than being deleted.
Say this plainly in the runbook instead of discovering it during an incident.

**Non-goals.** Not deleting `lisa upgrade` — source-built and curl-installed boxes
still need it, and it is brew's rollback path. Not changing what a tag means or how
`auto-release.yml` cuts one. Not building a fleet control plane; `brew upgrade` on a
cron and `lisa doctor --json` remain the whole of it.
