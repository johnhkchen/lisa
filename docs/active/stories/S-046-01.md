**Scope:** Lisa learns what Zellij versions it actually supports and says so out loud. lisa-core gains a comparable version type and a declared supported range — floor 0.43.0 to match the pinned zellij-tile minor (the hard API floor is 0.41.0 via `write_chars_to_pane_id`/`write_to_pane_id`; document that in code comments, but enforce the tested floor, not the theoretical one). `lisa doctor` parses `zellij --version` output into that type and reports detected-vs-required; `lisa loop` preflight refuses to start against an out-of-range or unparseable system Zellij with a named error stating the detected version, the required floor, and the remedy. Touches crates/lisa-core (new version module), crates/lisa-cli/src/doctor.rs, crates/lisa-cli/src/loop_cmd.rs.

**Story acceptance:** Unit tests parse real-world `zellij --version` strings (release, prerelease, garbage) into in-range / below-floor / unparseable verdicts; unparseable is treated as unsupported with its own named message, never a pass. A stubbed 0.40.1 binary makes `lisa loop` fail preflight loudly — the error names 0.40.1, names the floor, and names the remedy — and a stubbed 0.43.x/0.44.x passes. Doctor output shows the detected version against the supported range in both the pass and fail cases.

**Honest boundary:** Stub binaries only — no live Zellij, no tokens. This story prevents the silent-below-floor death by *refusing to start*, not by making old hosts work; the remedy string initially points at Zellij's prebuilt static binaries and is upgraded to "Lisa's managed runtime" wording when S-046-02 lands. Version constants live in one place so the zellij-tile bump ritual updates floor, pin, and docs together.
