**Scope:** On 2026-08-14 a `lisa loop` on the `renderer` board went quiet with a
ticket ready and nothing running. Getting it going again took twenty minutes and
**every recovery command lisa offers pointed at something that did not exist.**

The board, measured on the machine:

```
Status: 35 done, 1 in progress, 1 ready, 0 blocked
Ready to schedule: T-004-01              ← real work, waiting
```

Nothing was running. `ps` showed one zellij server on the box and it belonged to
a different session. The scheduler's own record named `zellij_pid 15340`, and
that pid was gone.

## What was tried, in order, and what each said

```
zellij kill-session renderer-3      succeeded — the session went away
lisa release-seats --release        "a scheduler is holding these seats …
                                     stop it with: zellij kill-session renderer-3"
lisa schedulers --stop renderer-3-…  "Error: `zellij kill-session renderer-3`
                                     exited exit status: 1. Nothing was stopped."
rail loop                            lisa refused in the pane: a run stays on the
                                     board until its session ends
```

**Both recovery commands tell you to end a session that has already ended, and
one of them is implemented as that exact failing command.** There is no third
option. The board was freed by moving `.lisa/schedulers/<id>.alive` and
`.lisa/scheduler.alive` out of the directory by hand — which is not a thing an
operator should be reading a story to learn.

## Why it happened

`.lisa/schedulers/renderer-3-49ded6ab.alive` holds both facts:

```json
{"scheduler_id":"renderer-3-49ded6ab","session_name":"renderer-3",
 "zellij_pid":15340,"started_at":1786768820,"stamped_at":1786771390,
 "poll_interval_secs":5}
```

**Liveness is judged from `stamped_at` freshness. The record already carries
`zellij_pid`, and nothing checks whether it exists.** A stamp is evidence that a
process was alive when it wrote; a pid is a question you can ask right now, and
lisa was holding the answer the whole time.

The stamp also stayed fresh for the wrong reason: a later `lisa loop` that
**refused** still touched it, so each recovery attempt renewed the lock it was
trying to break.

## What this story does not change

Not the guards themselves. `release-seats` refusing while something might be
working is right, and its message — *"a stamping scheduler is a process that
exists, not a ticket being worked"* — is the correct distinction, well said. The
bug is that lisa states that rule and then does not check whether the process
exists.
