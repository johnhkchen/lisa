**Scope:** Lisa now runs on several machines, and which version each one has is an
accident of how Lisa was put there. Nothing on a box records what the box is *for*,
so nothing can keep it at the version its job deserves.

Measured 2026-08-14, against the live release list:

| how it was installed | what it is running | age |
| --- | --- | --- |
| `curl … lisa-cli-installer.sh` | v0.4.4 — GitHub's "Latest" skips prereleases | 26 days |
| Homebrew tap | v0.5.0-rc.2 — `publish-prereleases = true`, `dist-workspace.toml` | 5 days |
| apt repo | whatever `scripts/build-apt-repository.sh` last pushed | unknown |
| `cargo build` (dev desk) | `main` | now |

The machines that went stale did not choose to. They ran the one-command install a
month ago and have been frozen at v0.4.4 ever since, while the desk that builds from
source moved four weeks ahead. **Freshness is a property of install history, not of
intent** — and that is the whole bug.

## The Mac mini is the first machine with a stated job

It runs background work. Real work, on a real schedule — but nothing whose failure
costs us anything in front of anyone. Its job in the fleet is to **be the machine
that finds the bug first**: run the next release against actual workloads for long
enough that we wake up to a broken Mac mini instead of a broken user.

That job has a hard requirement most of this design does not: **it only works if the
mini actually moves.** A nightly box that waits for a human to upgrade it is a stable
box with extra steps, and it will drift into staleness exactly the way the others
did. Insurance you have to remember to renew is not insurance.

It also has a soft requirement: **it must be loud.** A mini that quietly breaks and
sits there is worth nothing. The failure has to reach us the same morning.

## Three channels, one train of tags

| channel | resolves to | who it is for |
| --- | --- | --- |
| **canary** | the newest tag, period | the dev desk. Breakage is the job. |
| **nightly** | the newest tag, including `-rc`, once it has soaked | the Mac mini. Real workloads, no reputation at stake. |
| **stable** | the newest non-prerelease, and **never on its own** | workload machines. "Don't change just because." |

Soak has no telemetry to lean on, so soak is time: a tag is nightly-eligible once it
is older than a set window and has not been superseded by a hotfix. Cheap, honest,
and it stops the mini from picking up an rc that gets replaced twenty minutes later.

## Why this is not a branching strategy

Canary/nightly/stable is usually three branches because most projects must backport
fixes into a frozen line. Lisa does not. `auto-release.yml` runs a single train off
`main`, and the workspace version string already carries the stability claim: `-rc.N`
means unproven, a bare `0.4.4` means promoted. Promotion is already a real ritual —
drop the suffix in `Cargo.toml`, merge, and main ships it.

**Keep the one train. Add three subscription policies.** Three branches would buy
cherry-picking and merge conflicts in exchange for nothing a solo owner needs.

## What is actually missing

1. **A machine cannot say what it is.** Channel is a property of the box, not the
   project — it belongs in machine-level config, not `.lisa.toml`. (`.lisa.toml`'s
   `version` records what set the *project* up. Different fact, leave it alone.)
2. **There is no upgrade path.** No `lisa upgrade`. Every box is updated by
   hand-running an installer, which is why they stop being updated. Channels mean
   nothing without a command that honours them.
3. **The fleet is not askable.** `lisa doctor` reports zellij, claude and git
   versions and says nothing about whether Lisa itself is behind. We learned about
   this drift by noticing it.
4. **Package managers cannot carry three channels.** One Homebrew formula, one apt
   suite. The shell installer plus a self-updater is the only channel-aware path
   that works on every box. Brew and apt stay as the hands-off stable door for
   people who are not us.

None of this touches the release workflow. `auto-release.yml`, `release.yml` and
`dist-workspace.toml` keep working exactly as they do today; everything here is on
the receiving end.

**Non-goals.** Not branching `main`. Not backporting. Not building telemetry or a
fleet control plane — a machine that knows its own channel and a `doctor` line that
names the gap is the entire ask. Not changing how brew or apt publish.
