**Scope:** A new pure `completion` module in lisa-core (sibling to provenance.rs/route.rs, re-exported from lib.rs): the lifecycle state enum, the typed event enum, attempt/completion identity newtypes plus a correlation id, the effect-command + Transition + non-boolean CompletionRejection outcome types, the total `reduce` function, and the level-triggered `reconcile`/eligibility derivation. No Zellij/WASM imports; `thiserror` is added to lisa-core deps for error display/source only. lisa-plugin's scattered `request_completion` callers (lib.rs:1106, check_artifact_advances ~3046, auto_complete_review ~3669, manual `[d]one` ~5101) are untouched — the effect adapter is a follow-on epic.

**Story acceptance:** Feeding the module's `reduce` any typed event from any legal state yields exactly one `Result<Transition, CompletionRejection>` — either an accepted Transition carrying at most one effect command, or an exhaustive non-boolean rejection variant (already-pending, stale-lease, disposition-blocked, dependency-blocked, launch-failed); and `reconcile`, given durable inputs (current-lease artifact admission + explicit pass disposition) plus aggregate state, returns a request effect for an eligible ticket with no pending/confirmed transaction and returns none once one exists — all proven by per-transition unit tests. A CommandInFlight state without a correlation id is unrepresentable, and the reducer launches nothing and mutates no external state.

**Honest boundary:** Everything here is pure-domain and unit-proven with zero tokens and no Zellij runtime — the reducer never launches a command or touches scheduler state. The lisa-plugin effect-adapter that executes effect commands, derives eligibility on real polls/reload, and renders the distinct variants in the dashboard is the named follow-on epic (b), deferred here, not hidden inside a ticket. The disposition verdict is consumed as a provider-neutral typed input; E-040's concrete disposition parser is the prerequisite, referenced not reimplemented.
