**Scope:** A board with every ticket done reports as an error.

```
$ lisa validate
docs/active/tickets/: readiness: no tickets with phase 'ready' and all
                      dependencies satisfied

1 error(s) found. Fix and re-run `lisa validate`.
Error: 1 error(s) found. Fix and re-run `lisa validate`.
```

That board was `lisa` itself on 2026-08-16, at 235 of 235, clean tree, nothing
waiting. Four of the desk's five boards said the same thing that morning, having
finished everything overnight — and the operator's first read of the fleet was
*four boards are broken*, which took a command each to disprove.

## The distinction that is missing

**"No ready tickets" has two causes and they are opposites:**

- **Everything is done.** The board finished. This is the outcome the work is
  for, and lisa currently calls it an error, tells you to *fix it*, and exits
  non-zero.
- **Work remains and none of it can be reached.** Every remaining ticket is
  blocked, or depends on something unsatisfied. That is a real stall and worth an
  error — it is the case this check was written for.

`crates/lisa-cli/src/init.rs:1618` cannot tell them apart, because it asks only
whether the ready set is empty. The ticket counts that separate them are already
in hand at that line.

## Why this is worth a story rather than a one-line severity change

Downgrading it to a warning would silence the second case, which is the one that
matters. The fix is to **say which of the two it is** — the same shape as
`a-tools-own-account-of-its-failure-is-not-evidence` on the screen-design desk:
a check reported the ending it reached rather than the state of the world, and
one word covered two worlds.

## What this story does not change

Not the exit code for a genuinely stalled board, and not the check's existence.
A board where nothing can be scheduled and work remains should still fail loudly.
