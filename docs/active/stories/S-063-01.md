**Scope:** Closing a loop's pane does not stop its scheduler. `lisa loop` starts a
zellij *client*; the plugin that schedules the run lives in the zellij *server*,
and the server outlives the client. Quit the pane, kill the `lisa loop` process,
close the window — the scheduler keeps polling, keeps holding seats, and keeps
draining `.lisa/signals/`.

Nothing on the desk shows this. `lisa status` reads normally. `lisa loop` starts
another one.

Measured on `lisa` itself, 2026-08-12 13:2x, after the operator had quit every
loop they could see:

```
9450   blossoming-cymbal       started Wed Aug 12 09:31   → /Users/johnchen/swe/repos/lisa
38463  inventive-triceratops   started Tue Aug 11 19:40   → /Users/johnchen/swe/repos/lisa
30186  fascinating-drum        started Tue Aug 11 19:37   → /Users/johnchen/swe/repos/lisa
```

Three schedulers on one board. Two of them **seventeen hours old**. `ps aux |
grep 'lisa loop'` returned `0` the whole time, and `.lisa/scheduler.alive` was
being stamped every five seconds.

## Why three is worse than one that lingers

`.lisa/signals/` is single-consumer by design — `signal.rs` reads a signal and
removes it. That contract holds for one reader. With three, each scheduler sees
roughly a third of the signals and the other two silently eat the rest.

Every symptom of the day follows from that one fact:

- **A `pane-N.started` drained by the wrong scheduler never reaches the live
  one.** The live scheduler concludes startup was not observed, enters
  `begin_startup_recovery`, and types its shell-readiness probe into a pane where
  Claude is already running. `lib.rs:4776` already names this outcome: *"a dead
  end against a live TUI: a `--dangerously-skip-permissions` session executes the
  probe command on the scheduler's behalf and forges the readiness proof."*

  Ten of the last twelve agent sessions received that probe as their first and
  only prompt instead of an assignment. The split is unambiguous:

  | first prompt | sessions | transcript |
  | --- | --- | --- |
  | `Read and follow the complete assignment…` | 2 | 1.0–1.3 MB |
  | `command printf '%s' '{"ticket_id":…}' > '…pane-1.shell-ready.tmp…'` | 10 | 57–165 KB |

  The ten died in about sixty seconds each, having done nothing.

- **Two schedulers disagree about the current generation.** A usage row written
  at 12:22 records `"attempt_lease":{"ticket_id":"T-062-01-01","attempt_id":8}`
  while `pane-0.lease` on disk said `attempt_id: 10`. A completion arriving under
  generation 10 matches nothing the other scheduler knows about.

- **Finished work never advances.** `T-062-01-01`, `-03` and `-04` each wrote
  `review.md` and `{"disposition":"pass","reason":null}` between 12:19 and 12:26,
  committed their work in six commits, and stopped. The Stop hook fired for all
  three — token captures landed for panes 0, 1 and 2. All three sat at
  `phase: implement` twenty minutes later and never moved.

## The heartbeat has one writer's name and N writers

`.lisa/scheduler.alive` is a single file. Three schedulers stamp it, so it never
goes stale while any one of them lives — and the two commands built to rescue
this state both key on exactly that file:

```
$ lisa release-seats --dry-run
Nothing to release: a run is holding these seats. Lisa's scheduler said it was running 4s ago.
  skip     .lisa/signals/pane-0.lease (a run may still be holding it)

$ lisa reset-ticket T-062-01-01 T-062-01-03 T-062-01-04 --apply
Error: A Lisa run is using this board, so nothing was changed.
Evidence: Lisa's scheduler said it was running 40s ago.
```

Both refusals are correct given what they can see, and both are wrong about the
world. A zombie scheduler holds the board hostage from every supported recovery
lisa has.

## What it took to clear

`kill <pid>` on all three servers did nothing — they were still holding
`repos/lisa` three seconds later. Only `zellij kill-session <name>` ended them.
Finding the names at all took `lsof` across every zellij server on the machine to
see which ones had a handle on the project directory.

That is not a recovery an operator can be expected to derive.

**Non-goals.** Not changing the single-consumer signal contract, which is right
for one reader. Not preventing a detached run — running a loop without a visible
client is legitimate. This is about a board that cannot tell how many schedulers
are on it, and an operator who has no way to find out.
