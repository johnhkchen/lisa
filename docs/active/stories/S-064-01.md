**Scope:** `lisa status --json` describes a board thoroughly and says nothing
about what is executing it. The whole `config` block is three fields:

```json
{"max_threads": 2, "phase_timeouts": {}, "session_timeout_secs": 3600}
```

`.lisa.toml` knows the answer — the layout this desk runs carries
`client "claude"` — and the envelope does not carry it out.

**Why it matters now.** A consumer on this desk is being built to watch six
boards across three machines from a phone, where the operator's main judgement is
*which board to send work to next*. The fact that decision turns on is which
model a board runs: three of the six are deliberately on token-efficient models
and three are not. That fact is reachable only by reading `.lisa.toml` on each
host — which is a private file on a remote machine, i.e. exactly the kind of read
the JSON envelope exists to make unnecessary.

**Why it is cheap now and expensive later.** `lisa.cli/v1` is at
`schema_version: 1` and has one known consumer. Adding a field to `config` is
additive and a consumer that pins `SCHEMA_VERSION` keeps working — `rail` already
implements that discipline and refuses an envelope newer than it understands.
Once more than one reader depends on the shape, the same addition needs a
migration conversation.

**Non-goals.** Not exposing credentials, endpoints, or anything an API key is
part of. Not a per-attempt record — provenance already carries `requested` and
`actual` per attempt, and this is the board's configured intent, which is a
different fact and the one a consumer needs before any attempt exists.
