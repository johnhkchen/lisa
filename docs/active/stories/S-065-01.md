**Scope:** The desk is building a strip where one press files work and another
press sets it running (`screen-design` `S-014`, `S-016`). Both presses land on
lisa, and lisa cannot take either one safely today.

Filing a ticket means hand-authoring frontmatter and hoping `lisa validate`
accepts it afterwards. Getting a running loop to notice it means quitting and
starting again — and starting again is how this board got three schedulers on it
yesterday.

So the button that would make the loop self-refilling is, today, a button that
reproduces `S-063-01`.

## The three gaps, measured

**A running loop does not pick up a ticket filed after it started.**
`rebuild_dag()` and `schedule_ready_tickets()` are called from `keep_working()`
(`lib.rs:10651`), which is reachable only by pressing Enter in the quit-
confirmation modal. `poll_tick()` never calls either. The 5-second poll
(`POLL_INTERVAL_SECS`) is documented as rescanning ticket files *"to detect phase
changes"* — it maintains the DAG it already has and does not acquire a new one.

**There is no word for filing a ticket.** The CLI has `init validate status notes
unblock already-done doctor clean proposal loop release-seats reset-ticket` and a
plumbing set. None of them writes a ticket. `steer cross` already drafts one that
passes `ask-lint` and `premises`; there is nothing on this side to hand it to.

**The refusal to be a second scheduler exists and did not fire.** `loop_cmd.rs:38`
is titled *"Refuse to start a second scheduler on a board that already has a live
one"* and has a test at line 707. On 2026-08-12, on a board whose loop session was
still alive, `lisa loop` printed:

```
Session: lisa-2 (another session already holds "lisa" — `zellij list-sessions` shows it)
```

It detected the live session and used the fact **to pick a name**, then started.
Twelve seconds later a watcher on the desk reported `2 schedulers on one board`.

That is the important one. The check that would have stopped it was keyed on
`scheduler.alive`, and the first loop had finished its board — 204 of 204 — so its
stamp had gone stale while its zellij session, and the plugin inside it, were
still running. **A finished run is not an absent one**, and the only evidence
consulted could not tell those apart.

## Why the buttons make this urgent rather than merely untidy

A person restarting a loop by hand does it a few times a day and looks at what
happens. A slot does it whenever the board runs dry, unattended, possibly from a
phone, possibly while another surface is doing the same. Every one of the three
gaps above is survivable at human frequency and none of them is survivable at
button frequency.

`S-014` in `screen-design` has the operator's own framing of why the slot is
wanted:

> *loop finishes → sweep → 0 ready → ......... → operator files tickets → loop*
> *↑ this arrow is a person remembering, and nothing on the desk points at it*

This story is what has to be true underneath before that arrow can be a keystroke.

**Non-goals.** Not deciding whether an agent's drafted ticket goes onto the board
unreviewed — that is the fork the operator deferred in `S-014` and it is a policy
question, not this one. Not automatic refilling. Lisa's job here is to make filing
and resuming *possible and safe*; what triggers them belongs to the consumer.
