**Scope:** Three defects that compose into an unrecoverable board. (1) `TransactionLock::acquire`
(`crates/lisa-cli/src/commit_transaction.rs` ~403) takes the guard with a single
`try_lock_exclusive()` — no retry, no backoff — so at `max_threads ≥ 2` a concurrent completion
dies on `os error 35` rather than waiting its turn. (2) An empty include-path diff
(`commit_transaction.rs` ~750–758) is a hard error, so once a ticket's work is committed no
completion attempt can ever succeed again — which is exactly the state a lost race leaves
behind. (3) The resulting rejection has no exit: `lisa unblock` returns the ticket to the phase
that failed, the loop re-attempts `MarkDoneKey` on every start, and a direct `complete-ticket`
that *does* commit writes no journal transition, so board and journal disagree permanently.

**Story acceptance:** Four concurrent commit transactions all seal, none dies on the guard. A
ticket whose intended commit is already at HEAD under its completion key completes as a
convergent no-op, reporting that commit — while an empty diff for any other reason still fails.
A rejected completion is clearable through a documented command that leaves a terminal journal
record, and the loop stops re-attempting once it is clear. A disposition written from a failed
internal command never presents that command's error text as a review reason.

**Honest boundary:** The guard still serializes — it waits instead of dying (N4, no locking
redesign). The reducer's shape in `lisa-core/src/completion.rs` is unchanged; only which
observations map to which transitions moves. Correlation ids, generation keys and the journal
format stay as E-042 left them. Emptiness alone never means success — convergence is proven by
the key (N3).

## DAG

```
T-055-01-01  guard-waits-its-turn
     │
     ├── T-055-01-02  already-sealed-is-sealed

```

Wave rationale: the guard fix is the head because it is the only one of the three that prevents
the state rather than repairing it, and because both repairs need its concurrency fixture to
demonstrate anything. The two repairs are independent of each other — one is the transaction's
view of an empty diff, the other is the operator's route out — and share no file, so they run in
parallel behind it.

**Out of this slice:** Any change to what `lisa unblock` means, a locking redesign, changes to
review-phase disposition authoring, and the archive/retire workflow an operator reaches for when
all else fails.
