**Scope:** S-057-01 changes what a Lisa project looks like. This story is how a project that was
set up by an older Lisa gets there — and how its operator finds out it needs to.

Lisa already has *half* an upgrade path, and the half it has is the polite half. `lisa init` is
re-runnable and additive: `plan_owned_template` (`crates/lisa-cli/src/init.rs` ~257–283) refreshes
a Lisa-owned document when its bytes match a known generation and preserves it otherwise,
`upsert_missing_config_keys` fills in `.lisa.toml` keys that appeared since, and `version_is_stale`
compares the project's recorded version against the binary's. What none of that does is **remove**
or **rewrite**. Init can add a file; it cannot retire one. It can add a config key; it cannot drop
a dead one. It cannot touch a ticket whose `phase:` names a phase that no longer exists.

That gap was survivable while every change was additive. The 0.5.0 cut is not: a 0.4 project
carries a `CLAUDE.md` and `AGENTS.md` Lisa generated and no longer maintains, a
`docs/knowledge/rdspi-workflow.md` describing a workflow the scheduler stopped running, a
`.lisa.toml` with a `scheduling.auto_advance` key that means nothing, tickets whose frontmatter
says `phase: structure`, and `docs/active/work/` directories full of `research.md` and `plan.md`
files nothing will ever read again.

And there is no way for the operator to *learn* any of that. `lisa doctor` today reports on the
tools Lisa needs — zellij, the client binary, PATH. Ask it whether this project is current and it
has no opinion, because nothing has ever computed one.

Three commands, one shared idea. **`lisa doctor` tells you what is stale. `lisa init` brings
forward what it safely can. `lisa clean` removes what init deliberately would not.** The
progression is by escalating consent: doctor only looks, init only acts where the bytes prove
nobody edited them, clean acts where a person has said to.

**Story acceptance:** A project fixture initialised by 0.4.4 — generated context files, the old
workflow document, `auto_advance` in `.lisa.toml`, tickets at retired phases, work directories of
retired artifacts — is diagnosed by `lisa doctor` in terms an operator can act on, migrated by
`lisa init` without a single hand edit and without destroying anything a person wrote, and reduced
to a current project by `lisa clean`. A project already current is reported as current by all
three, and `lisa clean` on it removes nothing.

**Honest boundary:** the destructive command in this trio is `lisa clean`, and P1 is the whole
constraint on it — Lisa must not silently destroy user-owned content. Every removal it performs
has to be one the operator can see before it happens and would recognise as Lisa's own litter.
This story does not give Lisa a general-purpose cleaner for a repository, and the boundary between
"Lisa's litter" and "the project's files" is the design work in T-057-02-03, not an implementation
detail inside it.

**Out of this slice:** the release itself (S-057-03). Anything that changes what a *current*
project looks like — that is S-057-01, and this story only migrates toward whatever it lands.
Undo or rollback of a migration; the existing history mechanism (`lisa init --with-history`) is the
answer there and is not extended here.

## DAG

```
T-057-02-01  doctor-knows-what-stale-means
     │
     └── T-057-02-02  init-retires-what-it-once-wrote
              │
              └── T-057-02-03  lisa-clean
```

Wave rationale: a strict chain, and the order is the escalating-consent order rather than a file
dependency. T-057-02-01 is first because it has to define, in one place, what "stale" *is* — a
project-currency inventory the other two read rather than each re-deriving. It is also the ticket
worth landing even if the other two slipped: an operator who can see that their project is three
versions behind can fix it by hand. T-057-02-03 is last because `lisa clean` is defined by
subtraction — it removes exactly what T-057-02-02 decides it must not touch, and writing it before
that decision exists would be guessing.
