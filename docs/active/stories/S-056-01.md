**Scope:** `lisa unblock` refuses a ticket with a reason that is not true, and the refusal cannot
be cleared by doing what it asks. From the 0.4.4 field run on `tabular-recipes`: ticket T-010-03
sits in Waiting-on-you, its reviewer note asks the operator to run `npm run verify:mobile` and
promises "Lisa will pick it up from there". The operator ran it. It passed — 710 pages built,
2130 page views checked, exit 0. Then:

```
$ lisa unblock T-010-03
That didn't work yet — No build at dist/. Run: npm run build
$ echo $?
1
```

There is a build at `dist/` — 709 `index.html` files, sampled present 40/40 over 40 seconds with
no build running. The work under the ticket has already passed review. The sentence on screen is
false in every part: nothing was missing, and running the command it names changes nothing.
Seven-plus retries across stale and fresh `dist/`, busy and idle trees, sandboxed and unsandboxed
shells, and the operator's own terminal pane all failed identically. The operator's only escape
was to hand-edit `docs/active/work/T-010-03/review-disposition.json`.

Three defects compose into that. (1) **The check never sees the project.** `run_check`
(`crates/lisa-cli/src/unblock.rs` ~177–192) spawns the recorded check with
`.current_dir(snapshot.path())` — a `tempfile::tempdir()` filled by `git ls-files -z --cached
--others --exclude-standard` (~348), which by construction omits every gitignored path. `dist/` is
line 2 of that project's `.gitignore`. So `node scripts/check-touch.mjs` — a relative path, no
`--root` — resolved `dist/` against the tempdir, found nothing, and said so. This is the only
spawn in Lisa that redirects cwd away from the project root (`proposal.rs` ~249,
`triage_agent.rs` ~44, `loop_cmd.rs` ~487 all use `.current_dir(root)`), and nothing in the
disposition schema (`disposition.rs` ~402 parses `check` as an opaque string) tells the reviewer
who wrote that check where it would run. (2) **The refusal reports someone else's words as
Lisa's finding.** `decline_message` (~164) prefixes the first non-empty stderr line
(`observed_line`, ~275) with "That didn't work yet —". The project's script exits 2 meaning *I
could not look*; Lisa relays it as a verdict meaning *it did not pass*, with no indication of
what command ran, from what directory, or with what exit code — and there is no flag anywhere on
`lisa unblock` to override it. (3) **Two ceilings behind the first.** `CHECK_TIMEOUT` is a
hardcoded 5 seconds (~22) while the recorded check is a ~20-minute headless-browser sweep, and
the before/after tree fingerprint (~236) rejects any check that writes — so fixing (1) alone
turns this into "it took longer than 5 seconds", and a `build && verify` check into "it tried to
change project files".

**Story acceptance:** A fixture repository whose `.gitignore` ignores `out/`, with a real
`out/marker` on disk and a blocked ticket whose check is `test -f out/marker`, unblocks —
`UnblockOutcome::Reopened`, exit 0 — where today it declines. A check that cannot run reads as
inconclusive, not as a verdict, and prints the command, the working directory, and the exit code
alongside the captured output. An operator who has done the ask can always get through, by a
documented flag, with the override recorded. A check that could never pass is refused while the
reviewer who wrote it is still there, and the sandbox's real constraints are written down where
checks are authored.

**Honest boundary:** One thing the field trace could not establish: the child process's own
working directory was never captured — it exits too fast for `lsof`, and only the parent's cwd
(`/Users/johnchen/swe/repos/tabular-recipes`, correct) was read directly. The cwd claim rests on
the code path plus a byte-for-byte reproduction of the snapshot by hand, not on a live capture of
the child. Everything else here is observed. Unblock's meaning does not change: it still verifies
what changed and lets a waiting ticket run again (N4). The `already-done` route added by S-055-01
stays as it is — this story is about the check gate, not about completion recording.

## DAG

```
T-056-01-01  say-what-was-run-and-where
     │
     └── T-056-01-02  the-check-can-see-the-project
              │
              └── T-056-01-03  no-check-that-cannot-pass
```

Wave rationale: strict chain, because all three edit `run_check` and its result type in
`crates/lisa-cli/src/unblock.rs` and would collide on the same lines. The order is by
independence of value, not by depth: the diagnostic ticket is the head because it is the only one
that helps an operator who hits the *next* variant of this — it is worth landing even if the
root cause were something else entirely, and it gives the two that follow the vocabulary
(`Inconclusive`, a reported command and cwd) to assert against. The root-cause fix is second
because the ceilings only become reachable once a check can see the project at all.

**Out of this slice:** T-010-03 itself — the operator already cleared it by hand, and that repair
belongs in `tabular-recipes`, not here. Also out: any change to how the review phase decides to
write a `block`, any redesign of the parking/remedy schema beyond the fields these tickets need,
and the `run_world_rechecks` automation policy (world-owned remedies still never auto-act on a
non-pass; only their silence changes).
