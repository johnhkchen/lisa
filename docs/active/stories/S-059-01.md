**Scope:** Lisa computes the numbers an operator wants — how many tickets are ready, which
attempts are in flight, what is blocked and why — and then formats them for a human and throws the
structure away. `lisa status` and `lisa validate` have no `--json`. The Zellij plugin does not care,
because it reads the signal queue directly. Everything else has to scrape prose or re-derive the
answer from the ledgers.

**The evidence this is written from.** `rail` is a status strip in a narrow wezterm pane on the
same desk, watching a lisa run in the pane beside it
(`~/swe/repos/screen-design/rail`). It is read-only by design and it is not the plugin. To show
"how many tickets are ready to start", it runs `lisa validate --check-tools`, takes the exit status
as the verdict, and then does this to the output:

```rust
/// Lisa says `All checks passed. 9 tickets, 1 ready, DAG valid.` today, and
/// this reads it as "the number next to the word ready" rather than as that
/// sentence — either side of the word, punctuation ignored, so a reworded
/// pre-flight keeps working and a rewritten one degrades to None.
fn ready_count(text: &str) -> Option<usize>
```

That is a careful piece of work and it should not have to exist. It hunts for the token `ready`
and takes whichever neighbour parses as a number, because the sentence is prose and prose is
allowed to change. The author's own comment concedes the failure mode: a rewritten pre-flight line
degrades to "a start is available and I cannot say how many".

The second half is worse. To show which seats are working, rail joins
`.lisa/signals/pane-<id>.lease` against `attempt_lease` in `provenance.jsonl` and treats a seat as
live when its attempt has no closing record. That join is correct — the key is published on both
sides — but it is rail reimplementing scheduler bookkeeping from artifacts, and it is the third
substrate it tried. The first two failed for a reason that is documented policy rather than
accident: `lisa hooks-guide` states that the plugin *reads and deletes* signal files and that they
are ephemeral. Any second reader loses that race by design. Rail spent a full ticket discovering
that `.heartbeat`, `.awaiting` and `.error` are unobservable to it, and rewrote its whole worker
model onto the append-only ledgers as a result.

**Why this is a story and not a flag.** The question underneath is what Lisa promises to a reader
that is not its plugin. Today the honest answer is "nothing" — the signal queue is single-consumer
by design, the ledgers are artifacts rather than an interface, and the CLI's output is prose. That
is a defensible position, but it is not the one the CLI implies: `status` and `validate` are the
commands the everyday path points at (`init → validate → status → loop`), they already compute
exactly the right structure, and the only thing missing is not discarding it.

Adding `--json` is therefore a commitment, not a formatting change. It says: this shape is stable
enough to build against, these fields mean what they say, and a reader that is not the plugin has a
supported way to ask. That is worth deciding deliberately — including deciding against it, and
saying so, which would at least let a downstream reader stop guessing.

**What it would replace.** With `lisa status --json`, rail deletes `ready_count` and its comment,
stops joining leases to ledger rows to infer residency, and stops inferring a blocked count from a
signal it cannot reliably observe. Three inference layers become one call. Lisa gains nothing from
those layers existing; it loses the ability to reword a sentence without breaking something
downstream.

**Non-goals.** This is not a request for a daemon, a socket, a watch mode, or for the plugin's
internal state to be published. One-shot commands that already run, printing what they already
computed. Nor is it a request to make `.lisa/signals/` a public interface — the ephemeral,
single-consumer contract is fine and should stay as it is. The point of this story is that a
supported alternative should exist for readers that contract excludes.
