## First-User Readiness

Lisa works on itself. Now it needs to work for someone else, on a project
that isn't lisa. The dogfood runs surfaced small bugs (double state
transitions, `--print` preventing idle hooks from firing, dead code warnings)
and UX gaps that would confuse a first user. This sprint fixes those issues
and validates the full `lisa init` → `lisa loop` pipeline on an external
project.

**T-009-01 — Bug sweep** (parallel): Fix `--print` in spawn command (breaks
idle signal hooks), eliminate double state transitions in poll_tick, clean up
dead code warnings across the plugin crate.

**T-009-02 — Init hardening** (parallel): Verify `lisa init` generates
correct files for an external project (idle hook config, rdspi-workflow path,
CLAUDE.md template). Ensure `lisa validate` catches what a new user would get
wrong.

**T-009-03 — External project dogfood** (depends on 01, 02, 04): Run the
full `lisa init` → validate → `lisa loop` pipeline on a real external
project. Document any issues for follow-up.

**T-009-04 — LLM-driven validate loop** (depends on 02): Make
`lisa validate` output machine-parseable so an LLM can iteratively fix
issues until the project passes — like `cargo check` but for lisa readiness.

DAG for 2-agent concurrency:
```
Wave 1: T-009-01 + T-009-02  (independent, parallel)
Wave 2: T-009-04             (blocked by T-009-02)
Wave 3: T-009-03             (blocked by T-009-01, T-009-02, T-009-04)
```
