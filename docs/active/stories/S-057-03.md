**Scope:** Put 0.5.0-rc.1 in front of a real user — this machine — through the channel a real user
would install from.

S-057-01 removes four phases and the context-file scaffolding. S-057-02 gives an old project a way
to reach the new shape. Neither is proven by its tests. The claim this cut actually makes is that a
coding agent handed a well-specified ticket, a `lisa commit-ticket` contract, and a disposition
schema does *better* work than one marched through six artifact phases — and the only place that
claim can be tested is a run against a real board. That needs a released binary, because the whole
premise of Lisa is that it carries between projects as an installed tool.

The version is `0.5.0-rc.1`: minor, because 0.5.0 breaks the phase vocabulary and the init
contract; a release candidate, because the field evidence that would justify a stable cut does not
exist yet and this story is how it gets collected.

Everything about the mechanics already exists and is documented.
`docs/knowledge/release-checklist.md` is the version-parameterized maintainer runbook — 557 lines,
current cut `v0.4.4` — and `dist-workspace.toml` carries a cargo-dist configuration that already
publishes prereleases to the Homebrew tap deliberately (`publish-prereleases = true`, ~33–36) while
apt publishing skips them. `just release` (`justfile` ~20–36) reads the version from Cargo.toml,
refuses a tag that exists, and pushes. None of that is being changed.

**What is being tested at the boundary:** whether Lisa can run a release ticket the way it runs any
other — the agent preparing everything up to the authorizing action, then blocking honestly with
`remedy_owner: operator` because a person must publish, and the recorded `check` verifying the
published reality afterward. That is exactly the shape S-056-01 built the check contract for, and a
release is its most honest use: nothing an agent can do makes a Homebrew formula appear.

**Story acceptance:** `brew install johnhkchen/lisa/lisa` (or `brew upgrade`) yields 0.5.0-rc.1, and
`lisa --version` on this machine reports it.

**Honest boundary:** only John authorizes publication, and the checklist says so in its opening
lines. Preparing this story is not authorization. The ticket is written so the agent stops at that
line rather than approaching it — the block is the deliverable, not a failure.

**Out of this slice:** the stable 0.5.0 cut. Publishing to apt (cargo-dist skips prereleases there
by design, and that is correct). Changing any release mechanism, CI workflow, or cargo-dist
setting — if the RC exposes one that is broken, that is a new ticket with the failure in hand.
Running the first real 0.5.0 board; that is what the RC exists to make possible, and it is not a
ticket.
