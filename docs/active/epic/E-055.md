_Hand-authored 2026-08-02 (John + Claude), from a 0.4.4 field run: a 34-ticket board at
`max_threads = 4` where one completion lost the guard race and the board could not be recovered
through any documented command._

## Intent — the bigger-picture play

E-041 and E-042 promised idempotent completion: a ticket+attempt+generation key so that
"replay converges on the existing commit rather than duplicating it" (P1). That promise holds
for the duplicate-commit direction. It does not hold for the other one. **When replay converges
so far that there is nothing left to commit, the transaction calls it an error.**

The field sequence, in full, because each step is individually reasonable and the composition is
a trap:

1. Two tickets reach the commit transaction at once. `TransactionLock::acquire`
   (`crates/lisa-cli/src/commit_transaction.rs` ~403) calls `try_lock_exclusive()` — **one
   non-blocking attempt, no retry, no backoff**. The loser dies immediately with
   `Resource temporarily unavailable (os error 35)`.
2. That failure is transient by nature and is recorded as such, but the reconciliation deadline
   passes before a retry lands, and the completion is `rejected` with
   `retryability: action-required`.
3. The operator does the documented thing: `lisa unblock`. The ticket unparks back into
   `review` — which is the phase that already failed.
4. Every subsequent loop start re-attempts `MarkDoneKey`
   (`crates/lisa-plugin/src/lib.rs` ~661, ~2655). That calls `complete-ticket`, which stages the
   include paths and finds an empty diff, because the work was committed on the first pass. It
   returns `ticket <id> has no changes in the requested include paths`
   (`commit_transaction.rs` ~750–758).
5. That refusal is written back as a review disposition of `block`, **whose reason string is the
   text of the failed command rather than any judgement about the work**. The ticket parks
   again, and the cycle is closed. It cannot terminate, because the condition it retries on is
   the condition its own success created.

The board and the journal then disagree permanently, and nothing on the board can be edited to
make them agree. In the field run the only escape was to move the ticket out of Lisa's view
entirely — archiving it — which is the operator discovering that the supported commands have no
answer.

## Value to the design

Advances P1 — at-most-one-commit already holds; this makes **at-least-one-resolution** hold
beside it, so a completion that has already happened is recognised as having happened. And P5 —
a real field failure closed by a proven boundary rather than a plausible patch: the guard race
is reproducible with two concurrent transactions, and the unbreakable retry is reproducible with
one already-committed ticket.

It also repairs an N2 violation hiding in plain sight. N2 asks that recovery be bounded and end
in a named actionable state, never infinite retries or silent babysitting. The retry here is
bounded per attempt but **unbounded across loop starts**, and the state it ends in is named but
not actionable — `action-required` with no action that works.

## Done looks like

Four concurrent completions at `max_threads = 4` all seal; none dies on the guard. A ticket
whose work is already committed completes cleanly, reporting the commit that already carries its
key rather than refusing. A completion that genuinely cannot proceed says so once, in a state
the operator can clear with a documented command, and the loop stops re-attempting it. And a
disposition of `block` always carries a reason about the work — never the text of a failed
internal command.

## Context & constraints

Grounds against `crates/lisa-cli/src/commit_transaction.rs` (the guard and the include-path
staging), `crates/lisa-core/src/completion.rs` (the reducer's `rejected_transition` and
`Retryability`, ~800–840), and the operator-authority path in `crates/lisa-plugin/src/lib.rs`
(`MarkDoneKey` ~661, `OperatorRequested` ~672/~2655/~2676/~2692/~2802).

**PRESERVE, do not re-open:** E-041's typed reducer is domain and stays domain — this epic does
not change the state machine's shape, only which observations map to which transitions. E-042's
journal, correlation ids and generation keys stay exactly as they are; the fix is that a
convergent no-op produces a terminal record instead of none. E-034's attempt fencing and
E-031's commit isolation are untouched: **the guard must still serialize, it must simply wait
its turn instead of dying** (N4 — the smallest contract, not a locking redesign).

**A named honesty constraint (N3, P2):** an empty include-path diff is only convergence when the
intended commit is genuinely already at HEAD under this completion key. An empty diff for any
other reason is still a failure and must stay one. Proving the difference — by the key, not by
the emptiness — is the substance of the middle ticket; treating every empty diff as success
would trade a livelock for a lie.

**A second constraint, cheap and load-bearing:** a disposition written from a failed internal
command must not present that command's error text as a review reason. The field operator
reasonably read `block` as a verdict on twelve recipes and went looking for what was wrong with
them. Nothing was.

Field evidence for the decomposition to test against: both completion tracks for the stuck
ticket (`attempt_id: "1"` and `attempt_id: "operator"`) terminate at `rejected`, and two
subsequent `complete-ticket` invocations that **did** commit successfully wrote no journal
transition at all — so a successful operator seal left the journal still reading rejected. Any
fix that does not close that third gap leaves the operator able to seal the work and still
unable to convince Lisa of it.

Out of scope and left to DecomposeEpic: the ticket breakdown. Out of scope entirely: changing
what `lisa unblock` means, a locking redesign, and any change to how review dispositions are
produced by the review phase itself.
