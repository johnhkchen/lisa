## Intent — the bigger-picture play

The Arcade Midsummer T-009-01-01 field incident showed our completion path is a scatter of boolean, edge-triggered calls: a Codex attempt wrote a complete review.md and stopped, but the ticket sat in `phase: review`, the ~10-min timeout re-injected a generic finish-up prompt over an already-good artifact, `[d]one` operator recovery failed to close it, and only a hand-relaunched `lisa complete-ticket` produced the commit. The bigger-picture play NOW is to make completion a single, inspectable domain contract: model the legal lifecycle as a Rust enum whose variants carry only state-valid data (Eligible, Requested, CommandInFlight{correlation}, Rejected{reason,retryability}, Confirmed) and fold typed poll/artifact/disposition/stop/timeout/reload/manual-result events through one pure reducer that returns an explicit transition outcome plus effect commands — never launching commands or mutating unrelated scheduler state itself. This is the load-bearing core: a completion aggregate that makes 'admitted passing Review' converge, by construction, on one authoritative Done, and that the plugin adapter, journal, operator-authority, and regression epics can each build on. We stop at the domain contract; wiring, persistence, and the Arcade harness are downstream epics, not this card's decomposition.

## Value to the design

Realizes a provider-neutral completion contract in lisa-core that replaces boolean pass/fail returns with exhaustively-matched, distinct outcome variants (already-pending, stale-lease, disposition-blocked, dependency-blocked, launch-failed, accepted). Because states carry only valid data and the reducer is total and pure, published completion state can correspond to durable reality rather than an accidental in-memory edge (P2); at-most-one-live-completion-effect and at-most-one-authoritative-Done become compile-checked/property-checked invariants that also prevent duplicate completion commits by design (P1); and the exact field livelock becomes generated, deterministic regression evidence via proptest over permuted event orderings (P5). Modeling completion once, provider-neutrally, means Claude and Codex clear through the same contract without forcing an identical handshake (respects N1).

## Done looks like

lisa-core carries a pure completion module with no Zellij/WASM dependencies: the lifecycle is a Rust enum of state-valid variants, events are a typed enum, and the reducer returns `Result<Transition, CompletionRejection>` with explicit effect commands and exhaustive non-boolean rejection variants. Fed the recorded T-009-01-01 sequence (review present before phase→review, stop, ~10-min timeout, reload) it yields exactly one completion Request and, on the confirming manual result, exactly one authoritative Confirmed/Done — never a re-injected finish-up over an existing artifact. proptest over permuted event orderings holds the invariants (an admitted passing Review is never stranded, a blocked Review never completes, at most one live completion effect, at most one authoritative Done). `cargo test --workspace` passes and lisa-plugin still builds to wasm32-wasip1 within the existing size budget.

## Context & constraints

Grounds against the existing lisa-core (types/ticket/dag) vs lisa-plugin (scheduler.rs/ui.rs) split: the completion aggregate belongs in lisa-core as pure domain; the Zellij/WASM effect adapter that actually launches `complete-ticket` and renders variants stays in lisa-plugin. PREREQUISITE, not hidden scope: E-040's structured Review pass/block gate and explicit pass disposition already exist and are the eligibility input — this epic delivers reliable completion INTO that gate and transaction and must never bypass either. Respects N4 (isolate the smallest completion contract; do not rewrite the scheduler, commit isolation, or attempt fencing) and N2 (reconciliation is bounded and carries a correlation ID, ending in a named actionable state, not infinite retries or silent babysitting). PE-7 — the full demand signal is genuinely SEVERAL epics; this card scopes only (a) the pure typed reducer + aggregate. Follow-on epics that depend on it: (b) the lisa-plugin effect-adapter wiring that executes reducer effect commands, derives eligibility level-triggered on every poll and plugin load, and renders the distinct variants in the dashboard/activity ledger (advances P4, N3); (c) a durable minimal completion intent/result journal with atomic persistence (or unambiguous reconstruction) plus a ticket+attempt+completion-generation idempotency key so replay converges on the existing commit rather than duplicating it (advances P1); (d) `[d]one` reworked as auditable operator authority distinct from the active attempt's authority; (e) the Arcade-shaped deterministic regression + generated transition-sequence tests proving one commit, one Done, seat release, and dependent scheduling. Out of scope here: any plugin/effect wiring, journal persistence, operator-authority changes, a macro-generated FSM (keep the state machine handwritten and inspectable; `thiserror` only for error display/source plumbing), and any subscriber-only `tracing` island. proptest / proptest-state-machine enter as dev-only dependencies.
