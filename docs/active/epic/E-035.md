## Intent — the bigger-picture play

T-034-03-02 caught a critical, provider-neutral startup defect: in two freshly built isolated Zellij controls, the first long launch command was delivered truncated (zsh left hanging at `dquote>`) while lisa had already named the pane and published the seat as assigned/owned — no Codex or Claude process ever started. A later in-process assignment worked, so the fault lives at the fresh-loop pane-readiness / partial-input-delivery boundary, not in any provider's parser. The play is to close that boundary: make first-assignment command delivery atomic or positively acknowledged, and withhold the Owned/assigned publication until the provider process demonstrably starts, with bounded recovery when it does not. This is the load-bearing correctness gap in the whole fresh-loop startup path and it warrants clearing now.

## Value to the design

Realizes trustworthy startup semantics — published seat ownership corresponds to a live process (P2 state means what it says), delivered identically for Codex-first and Claude-first launches from the scheduler/operator view (P3 parity), so a supervisor reading the panes sees no phantom Owned seat (P4 operable at a glance). It converts a real field failure into a deterministic regression that proves the exact lifecycle boundary (P5), without forcing providers into an identical handshake (N1) or unbounded babysitting (N2).

## Done looks like

Running the exact isolated Codex-first and Claude-first harness against freshly built lisa, with no manual command repair and no manual trust intervention, a seat is published Owned only after its provider process is observed to start; a truncated or missing closing input never yields an Owned seat but instead a bounded, named recovery/failure state; and a real Zellij integration regression exists that fails on truncated/missing-closing-quote delivery and asserts no phantom Owned state — all while E-033 acknowledgement and E-034 lease fencing still hold.
