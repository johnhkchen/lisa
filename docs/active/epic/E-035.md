## Intent — the bigger-picture play

T-034-03-02 caught a critical, provider-neutral startup defect: in two freshly built isolated Zellij controls, the first long launch command was delivered truncated (zsh left hanging at `dquote>`) while lisa had already named the pane and published the seat as assigned/owned — no Codex or Claude process ever started. A later in-process assignment worked, so the fault lives at the fresh-loop pane-readiness / partial-input-delivery boundary, not in any provider's parser. The play is to close that boundary with a two-stage native-TUI contract: launch the provider without an inline ticket prompt, wait for its positive startup signal, then inject a bounded in-chat assignment that points at an atomically written attempt-scoped assignment file. Owned follows positive assignment submission/acceptance, not merely process start. Missing startup or assignment acknowledgement takes bounded same-pane recovery before fencing. This is the load-bearing correctness gap in the whole fresh-loop startup path and it warrants clearing now.

## Value to the design

Realizes trustworthy assignment semantics — published seat ownership corresponds to a live provider that positively accepted the current attempt's ticket, not merely a process that started (P2 state means what it says). Codex-first and Claude-first may use provider-specific hooks but expose the same `Starting → ReadyForAssignment → Delivering → Owned` scheduler contract (P3 parity), so a supervisor sees neither phantom processes nor prompt-missed Owned seats (P4 operable at a glance). It converts a real field failure into a deterministic regression that proves both lifecycle boundaries (P5), without forcing providers into an identical handshake (N1) or unbounded babysitting (N2).

## Done looks like

Running the exact isolated Codex-first and Claude-first harness against freshly built lisa, with no manual command repair and no manual trust intervention, the shell receives only a bounded provider launcher with no inline assignment prompt. A matching process-start signal moves the seat to `ReadyForAssignment`; lisa then pastes a bounded, attempt-tagged chat instruction referencing an atomically written assignment file, and only a matching prompt-submission/acceptance acknowledgement publishes Owned. A truncated or missing closing input that leaves the shell at `dquote>` never yields an Owned seat: lisa interrupts the incomplete shell input, positively verifies that the same pane is shell-ready, rotates the attempt lease, and retries once in that pane before consuming a spare or fencing it. A real Zellij integration regression proves both delivery stages, `dquote>` recovery, no prompt-missed or phantom Owned state, no stale-attempt publication, and no unbounded retry — all while E-033 acknowledgement and E-034 lease fencing still hold.

## Context & constraints

Grounds against docs/active/epic/E-033.md (acknowledgement) and E-034.md (lease fencing), which this epic must preserve, not re-open. A process-start signal proves readiness to receive an assignment; it does not prove ticket ownership. Fresh and recycled seats both bind ownership to attempt-tagged prompt acceptance, using provider-specific positive evidence behind one scheduler state contract. Reproduction origin is T-034-03-02. Shell recovery must distinguish four states: no provider process plus an incomplete shell command (`dquote>`), a started provider ready for assignment, a provider with an assignment pending acknowledgement, and a genuinely hard-silent owned provider. The first gets a bounded interrupt-and-retry in the same pane; a missed in-chat assignment is retried or the started provider is gracefully recycled within a bound; only an unresponsive owned process or failed bounded reset reaches E-034 fencing. The full prompt must not be a positional provider argument or shell payload: write it atomically under the attempt and inject only a bounded chat instruction referencing it. Prerequisite (name it as such, not hidden scope): the Codex-first path needs macOS fixture paths canonicalized before the Codex trust pregrant, or the harness rerun cannot proceed trust-free; treat that canonicalization as an enabling prerequisite for the rerun, not the core of the delivery fix. Scope boundary (N4): touch only the fresh-loop startup / pane-readiness / input-delivery and ownership-publication contract plus its regression harness — no broad scheduler rewrite. The harness rerun is validation of done-looks-like, not additional build scope. Out of scope: changing provider handshakes to be uniform (N1), any unbounded retry loop (N2), and treating a green dashboard label or process-start signal as proof that a ticket was accepted (N3).
