## Intent — the bigger-picture play

T-035-03-02's live acceptance run exposed a critical bootstrap deadlock in E-035's own design: E-035 split provider launch from in-chat assignment and gates the first prompt on a positive SessionStart signal, but Codex 0.144.1 emits SessionStart only AFTER that first prompt creates a thread. A bare Codex launch therefore waits for a signal that can never arrive without the prompt the wait is blocking — it sits in Starting forever, while Claude-first (which does emit SessionStart on process start) succeeds. The play is to make bootstrap readiness provider-aware without weakening the shared ownership contract: keep Claude's positive SessionStart path unchanged, and for Codex — where no truthful pre-prompt readiness hook exists — let a bounded, named time-based startup grace PACE the initial prompt, while never treating elapsed time as readiness or ownership evidence. After the grace, lisa submits the bounded attempt-tagged in-chat assignment, stays explicitly non-Owned, and only the exact current-attempt UserPromptSubmit acknowledgment publishes Owned. A missed submission retries or recycles inside a finite named state, preserving E-034 attempt fencing and stale-signal rejection. This closes the last correctness gap keeping the Codex-first control red; it warrants clearing now.

## Value to the design

Realizes truthful, provider-parity bootstrap: published Owned continues to mean 'this attempt's prompt was positively accepted', never 'enough time passed' (P2 — state means what it says; time paces, it never proves). Claude uses positive SessionStart evidence for Starting → ReadyForAssignment → Delivering; Codex uses a named Starting grace that paces the send directly into Delivering without ever claiming pre-prompt readiness. Both converge on the same acknowledgement-gated Delivering → Owned boundary through provider-specific bootstrap behavior rather than one forced handshake (P3 parity, honoring N1). A supervisor sees a Codex seat progress or fail into a named actionable state instead of a permanent silent Starting (P4 operable at a glance). The deadlock caught in the field becomes a deterministic delayed-send and prompt-miss regression that proves the bootstrap boundary that failed (P5).

## Done looks like

Running the exact fresh, installed, isolated Codex-first AND Claude-first startup harness against freshly built lisa, unattended and with no manual command or trust repair, BOTH live controls pass. A bare Codex launch no longer hangs in Starting: after a bounded named startup grace lisa attempts the bounded attempt-tagged chat assignment and moves directly to Delivering, never claiming ReadyForAssignment from elapsed time; it remains non-Owned and publishes Owned only on a matching current-attempt UserPromptSubmit acknowledgment. Claude-first still uses positive SessionStart to reach ReadyForAssignment before Delivering. A missed prompt submission resolves inside a finite, observable, named state (bounded retry or graceful recycle) and never yields Owned; stale-attempt signals are rejected and E-034 fencing still terminates an unrecoverable seat. No-inline-prompt launch and same-pane dquote recovery still hold. Deterministic delayed-send and prompt-miss tests exist and pass. The epic is not Done unless both live controls pass; a review that reports unmet acceptance is not auto-published Done.
