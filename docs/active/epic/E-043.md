## Intent — the bigger-picture play

Lisa recycles Claude panes via /clear, but LISA_TICKET_ID is frozen at process birth and the on-stop `lisa capture-usage` hook keys the usage file by that stale env var. Every recycled session's usage is therefore filed under the pane's FIRST ticket, overwriting the true owner's record — six confirmed overwrites in one experiment run, with some ticket usage lost entirely. Sessions with no ticket env blend into one mutable `last.usage.json`. A silent no-write path (masked by the hook's `2>/dev/null || true`) drops other captures with no trace. This makes every loop's cost-accounting and provenance quietly wrong, and the product is now building cost accounting on top of these files. The play: stop trusting inherited env for attribution — key usage to the scheduler's pane×time knowledge of who owned the pane at capture, keep every run's record instead of overwriting, hold unattributable usage aside rather than blending it, and make a failed write loud instead of silent. Correctness of the record, not new reporting.

## Value to the design

Restores P2 (state means what it says): published usage/cost/provenance correspond to the run that actually happened, and a capture that cannot be attributed or written surfaces as a visible, recoverable condition instead of being mislabeled as clean data or silently lost. Advances P5 by converting a documented real-world incident into a durable regression guard against re-corruption.

## Done looks like

Across a multi-ticket run that recycles panes, each ticket's usage is filed under the ticket that actually ran on that pane at that time (no record overwritten by a later recycle); usage that cannot be confidently attributed is visibly quarantined by session id rather than folded into a shared bucket; and a capture that writes nothing produces an operator-visible failure signal rather than a silent gap. The bug-report's repro no longer reproduces misattribution.

## Context & constraints

Field evidence and merged fix design already exist in docs/active/workspace/retro/bug-report-usage-attribution.md (T-PROP-CP2): six confirmed overwrites, mechanism, repro, and acceptance tests — this epic clears against that report, not a fresh investigation. Touch points live in crates/lisa-cli (capture-usage / provenance) and the pane×time ownership state the scheduler already tracks (crates/lisa-plugin/scheduler.rs). SCOPE IS CORRECTNESS-ONLY. Explicitly OUT OF SCOPE and deferred: Claude-vs-codex cache-split parity (Claude capture recording only input/output vs codex's 4-dimension capture) — that is a separate parity concern, not part of removing the misattribution failure. PREREQUISITE (name, do not absorb): the scheduler must expose, or already durably hold, which ticket owned a given pane at a given capture time — attribution-by-env is being replaced by attribution-by-pane×time, so that ownership signal must be reachable at capture. RIGHT-SIZING: this reads as slightly larger than one 2-hour block — plausibly 3-4 stories for DecomposeEpic (pane×time attribution; append-only per-run records; unattributable-usage quarantine; surfacing silent no-writes). If it will not land as one ~2h feature block, DecomposeEpic should split along those seams; the intent here stays one cohesive correctness fix. Respects N3 (this is a scheduler/record correctness fix, not a dashboard relabel) and N4 (isolate the capture/attribution contract; no broad rewrite).
