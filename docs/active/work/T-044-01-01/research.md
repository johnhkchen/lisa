# Research: orient and separate help

## Ticket boundary

- The ticket is `T-044-01-01`, titled `orient-and-separate-help`.
- Its current phase is `research`.
- Its only acceptance criterion concerns the output of `lisa --help`.
- The criterion asks for an orientation line naming the everyday path.
- The named path is `init → validate → status → loop`.
- The criterion also identifies four plumbing commands.
- Those commands are `agent-exec`, `capture-usage`, `commit-ticket`, and
  `complete-ticket`.
- They must not remain interleaved with the five operator commands.
- The five operator commands are `init`, `validate`, `status`, `doctor`, and
  `loop`.
- A new `cargo test -p lisa-cli` snapshot must cover the orientation and the
  separation.
- The ticket does not request changes to command behavior.
- The parent story explicitly limits the source scope to help metadata in
  `crates/lisa-cli/src/main.rs` and a CLI help-surface snapshot test.
- The parent story reserves per-command purpose copy and examples for the
  dependent ticket `T-044-01-02`.

## CLI definition

- The executable crate is `crates/lisa-cli`.
- Its binary target is named `lisa`.
- The binary entry point is `crates/lisa-cli/src/main.rs`.
- The top-level parser is the private `Cli` struct.
- `Cli` derives `clap::Parser`.
- The parser metadata currently supplies `name`, `about`, and `version`.
- The current about line is `Runs your coding agents through a project's
  tickets.`
- `Cli` has one field, `command`, which is a Clap subcommand.
- The command model is the private `Commands` enum.
- `Commands` derives `clap::Subcommand`.
- Each enum variant corresponds to a command name generated by Clap.
- Clap converts Rust variant names such as `AgentExec` to kebab-case names such
  as `agent-exec`.

## Operator commands

- `Init` is the first operator command in source order.
- It has `display_order = 0`.
- Its current summary is `Set up a project to run with Lisa.`
- `Validate` has `display_order = 1`.
- Its summary describes checking tickets and project setup.
- `Status` has `display_order = 2`.
- Its summary describes ready and waiting tickets.
- `Doctor` has `display_order = 3`.
- Its summary describes checking required tools.
- `Loop` has `display_order = 4`.
- It is physically declared after the plumbing variants in the enum.
- Its explicit display order nevertheless places it before them in generated
  help.
- Its summary describes starting a run over ready tickets.
- All five variants are visible in top-level help.
- Their runtime match arms call the existing implementation modules.

## Plumbing commands

- `AgentExec` has `display_order = 20`.
- It is a Codex signal-producing wrapper retained for diagnostics and headless
  automation.
- `CaptureUsage` has `display_order = 21`.
- Hooks invoke it with a payload on standard input.
- `CommitTicket` has `display_order = 22`.
- Agents invoke it to make ticket-owned source changes durable through an
  isolated Git index.
- `CompleteTicket` has `display_order = 23`.
- Lisa invokes it as part of completion publication.
- All four commands are real, supported parser entry points.
- Other source modules and templates call these names directly.
- Hiding a command from generated top-level help does not remove its parser
  entry point.
- The commands' detailed `--help` output is generated from their existing
  fields and documentation.
- The ticket does not authorize changing those fields or runtime match arms.

## Already-hidden commands

- `SetupGuide` has `hide = true`.
- `HooksGuide` has `hide = true`.
- `Version` has `hide = true`.
- These commands remain resolvable despite being absent from the top-level
  command listing.
- This establishes an existing project pattern for hiding a command from the
  main help surface while retaining its contract.
- The built-in Clap `help` subcommand is also shown in the top-level listing.
- The built-in `--version` option remains generated from the top-level
  `version` setting.

## Current rendered surface

- Running `cargo run -q -p lisa-cli -- --help` succeeds.
- The output begins with the about line.
- It then renders `Usage: lisa <COMMAND>`.
- It has a single heading named `Commands:`.
- Under that heading, all five operator commands appear first.
- All four plumbing commands immediately follow the operator commands.
- The built-in `help` command follows the plumbing commands.
- There is no blank-line or heading boundary between `loop` and `agent-exec`.
- Therefore display order creates a lower band but not a semantic group.
- The current output has no everyday-path orientation line.
- The current output ends with the generated `Options:` block.

## Existing help tests

- The relevant integration test is
  `crates/lisa-cli/tests/help_surface.rs`.
- It invokes the compiled binary through `CARGO_BIN_EXE_lisa`.
- It uses `std::process::Command`, matching other black-box CLI tests.
- `all_twelve_subcommands_resolve` checks every Lisa-owned command.
- That test includes visible, plumbing, and already-hidden commands.
- It proves hidden commands still parse when addressed directly.
- `hook_commands_are_set_apart_and_internal_hidden` examines top-level help.
- Its helper searches for a command at a two-space listing indentation.
- It asserts every plumbing command occurs after `loop`.
- It does not require a separate heading or block boundary.
- It would pass for the current single undifferentiated `Commands:` list.
- `about_line_and_operator_help_are_jargon_free` checks brand terminology.
- It reads the first nonempty line as the about line.
- That assumption is coupled to the current absence of `before_help` content.
- The test does not compare complete help output with an expected snapshot.
- The crate has no `insta`, `snapbox`, or `assert_cmd` development dependency.
- No `.snap` fixture currently exists for CLI help.
- A deterministic snapshot can therefore use a checked-in expected string and
  `assert_eq!` without adding a dependency.

## Clap capabilities and constraints

- The workspace lockfile currently resolves Clap 4.6.1.
- Clap's top-level `Command` supports `before_help` and `after_help` metadata.
- Clap supports changing the single subcommand heading with
  `subcommand_help_heading`.
- Clap's standard renderer has one generated subcommand list.
- `next_help_heading` applies to arguments and does not provide independent
  generated subcommand sections.
- A variant's `hide = true` removes it from the generated subcommand list.
- Hidden variants remain accepted by the parser and retain direct help.
- Static `after_help` content can render a separate curated plumbing section.
- The top-level derive metadata is the narrow place where orientation and a
  separate static section can be added.
- Clap includes the built-in `help` entry in the generated subcommand block.
- Exact snapshot output is affected by headings, whitespace, wrapping, and the
  resolved Clap version.
- The integration test captures non-interactive stdout, giving the snapshot a
  deterministic rendering context within a locked dependency graph.

## Runtime boundary

- `main` calls `Cli::parse()` and matches every `Commands` variant.
- Help rendering exits inside Clap before normal dispatch.
- Help metadata changes do not alter the variant payloads.
- They do not alter `resolve_path` or any command implementation.
- They do not change scheduler behavior, ticket parsing, Git transactions, or
  hook processing.
- The acceptance surface is therefore isolated from the command execution
  surface.

## Observed acceptance gaps

- No line currently names the everyday command path.
- The generated heading does not distinguish operator commands from plumbing.
- The plumbing entries share the same column and list as the operator entries.
- Existing relative-order assertions cannot detect that semantic gap.
- Existing tests are not full-output snapshots.
- The first-line about assertion will need to account for any new content that
  intentionally appears before the about line.

## Assumptions surfaced by the code

- The four plumbing names are stable contracts because multiple modules invoke
  them.
- Visibility in top-level help is independent from command availability.
- The dependent ticket will extend the same help surface later.
- This ticket should not preempt the dependent ticket's command examples.
- The exact top-level text can be curated because the parent story explicitly
  names the current command set as an honest static boundary.
- A snapshot should cover the whole top-level output so a plumbing entry cannot
  silently move back into the generated operator list.
- Direct subcommand resolution should remain separately tested to prevent
  accidental removal while demoting entries from top-level help.
