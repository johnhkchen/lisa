## Auto-release workflow

`.github/workflows/auto-release.yml` runs after successful CI on `main`.

It can also be started with `workflow_dispatch`.

Its concurrency group is `auto-release-main` with cancellation disabled.

The workflow checks out the exact successful CI head SHA.

It reads the `lisa-cli` version with `cargo metadata`.

It derives the tag as `v<workspace-version>`.

If that remote tag does not exist, it creates an annotated tag and pushes it.

If the GitHub release already exists, it stops without dispatching.

Otherwise it dispatches `release.yml` on `main` with the tag as an input.

The workflow needs the explicit dispatch for tags pushed with `GITHUB_TOKEN`.

GitHub suppresses ordinary workflow events caused by that token.

`workflow_dispatch` is an explicit exception to that suppression.

The release workflow grants contents write; auto-release also grants actions write.

## Duplicate-run observation

The rc.8 release history contains two release runs for the same tag and commit.

Run `29229574778` was triggered by the human tag push.

Run `29229651672` was triggered by workflow dispatch shortly afterward.

Both planned and built the same four platform archives.

Both completed all platform and global artifact jobs successfully.

The dispatched run reached `gh release create` first and succeeded.

The tag-push run reached the same command seconds later.

It failed only because the release with that tag already existed.

Its Homebrew and announce jobs were skipped as a consequence.

The failure is a duplicate-publication race, not an artifact-build failure.

The current auto-release guard checks for an existing release.

It does not check for an already queued or running release workflow.

Between tag push and release creation, the existing-release check is false.

That interval permits the observed duplicate dispatch.

The GitHub CLI can list release runs filtered by commit SHA.

Its JSON includes status, event, database ID, and URL.

Non-completed statuses include queued, requested, waiting, pending, and in-progress.

## Release workflow

`.github/workflows/release.yml` is generated by cargo-dist with local extensions.

It accepts pull requests, matching version-tag pushes, and manual dispatch.

Manual dispatch requires an existing version tag.

The plan outputs consistently select the dispatch input before `github.ref_name`.

Every checkout also selects the dispatch tag before the event ref.

This makes a dispatch on `main` build the immutable tag, not current branch drift.

The plan job installs pinned dist 0.30.4.

It creates a JSON distribution manifest for the selected tag.

The local build matrix is derived from that manifest.

The current configured targets are two Darwin and two musl Linux targets.

Each local job installs the WASI target and builds the release plugin first.

The shared build setup verifies the WASM header and requires embedding.

Cargo-dist then builds and packages the native CLI archive.

Musl matrix jobs run `scripts/verify-musl-release.sh` before upload.

The script requires static ELF linkage and no interpreter segment.

It checks that the CLI contains the WASM and managed-runtime checksum.

It runs the executable in Debian Bullseye.

The global job creates checksums, shell installer, formula, and source archive.

The host job gathers every artifact and creates the GitHub release.

The Homebrew job publishes the generated formula to the tap.

`publish-prereleases = true` causes prerelease formulas to publish too.

Stable releases also publish and should converge the tap with `latest`.

## Stable-cut mechanics

All three Lisa workspace packages inherit the workspace version.

Cargo.lock records `0.4.0-rc.8` for `lisa-cli`, `lisa-core`, and `lisa-plugin`.

A stable cut needs `Cargo.toml` and the three lockfile records at `0.4.0`.

That version change must land on the intended release commit before tagging.

Because auto-release follows successful main CI, merging the version bump is
the publication-authorizing action when automation is enabled.

A manual dispatch is the recovery path when a tag exists without a release.

Tags should remain immutable; a failed cut should be repaired without retagging.
