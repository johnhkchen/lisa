# T-035-01-01 Design — process-start signal producer

## Decision summary

Add one shared POSIX hook, `on-start.sh`, bound to native Claude and Codex
`SessionStart[startup]`. Each fresh provider launch exports its immutable attempt ID.
The hook compares the launch-bound ticket/attempt pair with the scheduler-owned pane
lease marker and, only on an exact match, atomically copies that lease to
`pane-<pane>.started`.

## Signal contract

- Path: `.lisa/signals/pane-<LISA_PANE_ID>.started`.
- Payload: the exact compact JSON `AttemptLease` bytes from the pane lease marker.
- Scope: pane, ticket, and attempt.
- Producer: native TUI `SessionStart` with source/matcher `startup`.
- Publication: temporary file in the signal directory followed by atomic rename.
- Failure behavior: fail closed and leave no `.started` file.
- Provider semantics: identical script and identical payload for Claude and Codex.

## Option 1 — timestamp-only start signal

The hook could write the current UTC timestamp, matching old idle/stop conventions.

Advantages:

- Minimal script.
- Easy to inspect manually.

Rejected because:

- A timestamp does not bind the signal to a ticket or attempt.
- A stale provider could promote a replacement assignment.
- It conflicts with the attempt-scoped contract established by E-034.
- A later consumer would need unreliable mtime/deadline inference.

## Option 2 — blindly copy the pane lease marker

The hook could mirror `on-heartbeat.sh` exactly and copy the current marker.

Advantages:

- Reuses the existing atomic lease payload pattern.
- Requires no launch-command changes.

Rejected because:

- The marker is mutable scheduler state, not immutable process identity.
- A late predecessor SessionStart could copy a successor marker.
- The resulting bytes would falsely attribute the old process to the new attempt.
- Fixture rejection of stale/mismatched starts would be impossible at production time.

## Option 3 — capture SessionStart stdin as provider evidence

Separate Claude and Codex scripts could retain their lifecycle JSON payloads.

Advantages:

- Preserves provider session metadata.
- Could aid diagnostics.

Rejected because:

- Provider payloads do not carry Lisa's attempt lease.
- The consumer would need provider-specific parsing.
- It creates parity through translation rather than at the signal boundary.
- It expands scope into session metadata not required for ownership gating.

## Option 4 — launch-bound identity plus marker comparison

Export `LISA_ATTEMPT_ID` beside existing pane/ticket variables. At startup, construct
the expected compact lease JSON from immutable process environment and require exact
equality with the pane marker before publishing `.started`.

Advantages:

- Binds the signal to the process launch and scheduler authority.
- Rejects predecessor, wrong-ticket, missing-marker, and malformed-marker cases.
- Produces the same normalized payload for both providers.
- Uses only POSIX shell built-ins and standard file utilities.
- Leaves current lease validation available to the later scheduler consumer.

Selected because it is the smallest producer-side proof that cannot borrow a successor's
identity.

## Hook algorithm

1. Create `.lisa/signals`.
2. Require non-empty `LISA_PANE_ID`, `LISA_TICKET_ID`, and `LISA_ATTEMPT_ID`.
3. Require `LISA_ATTEMPT_ID` to contain digits only and be non-empty.
4. Read `.lisa/signals/pane-<pane>.lease` as a single exact value.
5. Construct expected compact JSON from ticket and attempt identity.
6. Require marker bytes to equal expected bytes.
7. Copy the marker to a pane-scoped temporary start path.
8. Rename the temporary file atomically to `pane-<pane>.started`.
9. Remove the temporary on any copy/rename failure.

Ticket IDs are generated by Lisa's ticket parser and are not arbitrary shell source. JSON
comparison uses the exact compact serialization Lisa already writes. This intentionally
fails closed if the marker format changes until producer and scheduler evolve together.

## Native configuration

Both generated configs retain their existing `SessionStart[clear]` group and add a second
group with matcher `startup` invoking the shared start hook. `ensure_hook` already supports
multiple matcher values on the same event and preserves user-owned commands.

The start matcher excludes `resume`, `clear`, and `compact`. Those lifecycle events do not
prove that a newly launched provider process began for a fresh assignment. `clear` retains
its distinct `.cleared` handshake.

## Launch identity threading

`SpawnContext` gains `attempt_id: u64`, populated directly from the minted lease. Both
adapters export `LISA_ATTEMPT_ID` in fresh launch commands. The Claude helper accepts the
attempt ID explicitly so tests and callers cannot accidentally omit it.

Reused-session prompts do not launch a new process and therefore do not emit startup.
Their existing clear/ack contracts remain unchanged. Cross-provider recovery launches use
the same context and naturally receive the current attempt ID.

## Upgrade behavior

- Add `ON_START_HOOK` and an empty initial legacy-generation list.
- Add `on-start.sh` to init's managed hook script inventory.
- Add startup bindings through both merge functions.
- Extend validation to require the script and startup command.
- Existing divergent user files remain safety-skipped by owned-template rules.
- Existing hook JSON retains user groups and gains one Lisa startup command idempotently.

## Verification design

- Parse both generated configs and assert separate `startup` and `clear` groups.
- Merge existing configs twice and assert exactly one start command.
- Execute the hook in a temporary fixture root with a matching marker; assert exact output.
- Execute with stale attempt and wrong ticket markers; assert no output.
- Execute with missing identity/marker; assert no output.
- Assert an untouched fixture directory has no signal, representing no provider start.
- Update exact Claude/Codex launch tests to require `LISA_ATTEMPT_ID`.
- Run CLI, plugin, and workspace tests to catch init and scheduling regressions.

## Scope exclusions

- Do not consume `.started` in the scheduler.
- Do not add pending-start/Owned state transitions.
- Do not add retry or timeout behavior.
- Do not modify `agent-exec`.
- Do not alter the first-launch transport mechanism.
