## Distribution configuration

`dist-workspace.toml` is the authoritative dist configuration.

It pins cargo-dist, now named `dist`, to version `0.30.4`.

It enables shell and Homebrew installers.

It currently names four release targets.

The Darwin targets are `x86_64-apple-darwin` and `aarch64-apple-darwin`.

The Linux targets are `x86_64-unknown-linux-gnu` and `aarch64-unknown-linux-gnu`.

The distributed package is `lisa-cli`.

The build profile is `dist`, inherited from the release profile.

The release profile enables `lto = true` with no thin-LTO override.

Rust therefore applies fat LTO for release and dist builds.

The current script install strategy is `install-path = "CARGO_HOME"`.

That strategy installs into `$CARGO_HOME/bin` when set.

It otherwise installs into `$HOME/.cargo/bin`.

The release config does not currently override the success message.

The config preserves a customized release workflow through `allow-dirty = ["ci"]`.

The Homebrew tap and formula are configured independently of the shell path.

## Pinned dist behavior

The pinned v0.30.4 documentation lists both requested musl triples as supported.

They are `x86_64-unknown-linux-musl` and `aarch64-unknown-linux-musl`.

The same documentation describes them as static-musl targets.

The `install-path` setting accepts a home-relative path.

`~/.local/bin` is therefore a supported direct configuration value.

The shell installer creates that directory when it does not exist.

It writes an `env` helper inside the configured install directory.

It updates common shell startup files unless path modification is disabled.

It cannot change the already-running parent shell's environment.

When needed, it prints a restart-or-source PATH instruction.

The pinned version also supports `install-success-msg`.

That message is emitted immediately after binaries are placed.

The success message is a package-local configuration value.

The generated PATH remediation text itself is part of cargo-dist's template.

There is no project-local installer template in this repository.

## GNU and musl installer selection

Cargo-dist computes a platform-support preference list for each host platform.

Its v0.30.4 source classifies matching GNU artifacts as host-native.

It classifies static-musl artifacts on GNU Linux as imperfect-native.

Host-native candidates sort ahead of imperfect-native candidates.

The shell installer tries candidates in that computed order.

It uses the first candidate whose runtime conditions pass.

With both GNU and musl archives present, a new-enough glibc host gets GNU.

An older glibc host can fall back to musl.

That coexistence behavior does not make musl the normal Linux download.

With only musl Linux archives, the static artifact supports GNU Linux hosts.

The parent story explicitly permits dropping GNU artifacts.

No separate repository consumer requires GNU ABI behavior at runtime.

It has plan, local-build, global-build, and host stages.

The local build matrix comes from the JSON plan.

Each local build checks out the selected tag or pull request ref.

It then injects `.github/build-setup.yml` before installing and running dist.

`github-build-setup` is referenced relative to the workflow directory.

The current reference is `../build-setup.yml`.

The build setup installs the `wasm32-wasip1` Rust target.

The resulting source is `target/wasm32-wasip1/release/lisa.wasm`.

The setup currently does not assert that this file is non-empty.

The current local WASM artifact is a valid WebAssembly module.

## WASM embedding boundary

`crates/lisa-cli/build.rs` owns the copy into the CLI build output.

It finds the workspace from `CARGO_MANIFEST_DIR`.

It looks for the release WASM at the workspace target path.

When present, it copies the file to `OUT_DIR/lisa.wasm`.

When absent, it writes an empty placeholder for developer builds.

`crates/lisa-cli/src/templates.rs` embeds that output using `include_bytes!`.

The resulting `PLUGIN_WASM` constant is compiled into every native CLI target.

`lisa loop` refuses to launch when that byte slice is empty.

The release build setup is what distinguishes distributable builds from placeholders.

The same setup runs once in every platform-specific matrix job.

A musl CLI build will therefore use the same target-independent WASM source.

## Managed-runtime manifest boundary

The default runtime resolver lives in `crates/lisa-cli/src/runtime.rs`.

It pins managed Zellij to version `0.43.1`.

That version matches the plugin's `zellij-tile = "0.43"` SDK family.

Dependent ticket `T-046-02-02` owns fetch, verification, and atomic storage.

That ticket requires checksums to be baked into Lisa rather than fetched at runtime.

No managed-runtime checksum manifest exists in the repository today.

No checksum constant is currently embedded by the CLI.

Zellij v0.43.1 publishes no-web archives through its official GitHub release.

Linux archive names include the complete Rust target triple.

The requested Linux assets are static-musl archives.

The x86 archive is `zellij-no-web-x86_64-unknown-linux-musl.tar.gz`.

The arm64 archive is `zellij-no-web-aarch64-unknown-linux-musl.tar.gz`.

The release also publishes no-web Darwin archives for Lisa's Darwin targets.

The upstream `.sha256sum` files hash the unpacked `zellij` binary.

Their contents do not name or hash the compressed tarball.

The future downloader's verification order must account for that distinction.
