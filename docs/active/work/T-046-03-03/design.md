# T-046-03-03 Design — xz-free-shell-installer

## Goal

The exact README one-liner must succeed on the no-`xz` Chromebook fixture for
arm64 and amd64, installing Lisa to `~/.local/bin`, while preserving
verified-release (checksums, static-ELF/WASM/runtime-manifest checks, bullseye
execution) and static-musl properties. Release CI must verify both Linux
archive paths.

## Options considered

### A. Switch archive format to `.tar.gz` via `unix-archive` (chosen)

Set `unix-archive = ".tar.gz"` in `dist-workspace.toml`. cargo-dist then
produces `lisa-cli-<target>.tar.gz` for all four unix targets, and the
generated shell installer extracts with gzip — `tar` + `gzip` are both
Priority: required in Debian and present in the fixture (and effectively every
Linux/macOS host). No installer patching, no template fork; checksum embedding
and `.sha256` sidecars are format-agnostic and survive unchanged.

- **Fixes the actual failure**: extraction no longer needs a decompressor the
  fixture lacks.
- **One declarative line** in the config cargo-dist already owns; the installer,
  archive names, homebrew formula URLs/checksums all regenerate consistently at
  release time.
- **Cost**: gzip compresses worse than xz (roughly 25–40% larger archives for
  Rust binaries). One-time download per install; irrelevant next to a 100 GB/mo
  Pages budget that only applies to apt anyway (release assets are on GitHub
  Releases, not Pages).
- **Applies to macOS archives too** (`unix-archive` is unix-wide). Harmless:
  macOS bsdtar handles gzip natively; Homebrew formula regenerates with new
  URLs and shas automatically.

### B. Keep `.tar.xz`, make the installer fall back (rejected)

The installer is generated by cargo-dist from its own templates. Making it
try `xz` then fall back to something else means forking/patching the template
or post-processing the generated script in CI. Post-processing a signed-off,
checksum-carrying installer in a hand-maintained sed step is exactly the kind
of fragile customization `allow-dirty = ["ci"]` was scoped to avoid spreading;
and there is no xz-free fallback to fall back *to* unless we also publish a
second archive format, doubling assets for no benefit over Option A.

### C. Publish raw binaries alongside archives (rejected)

`dist.extra-artifacts` could ship bare `lisa-<arch>` binaries, but the
generated shell installer would not use them — it installs from the archives.
We would end up writing and maintaining our own installer script, abandoning
cargo-dist's checksum verification, receipt handling, and PATH guidance.
Violates "preserve the existing verified-release properties" in spirit and
duplicates a solved problem.

### D. `.zip` or `.tar.zstd` (rejected)

`unzip` and `zstd` are not in the fixture (not Priority: required in Debian).
Same failure class as xz, different binary name.

## Decision

**Option A**, plus CI verification updates so the acceptance criteria are
checked by the release pipeline rather than assumed:

1. `dist-workspace.toml`: add `unix-archive = ".tar.gz"` with a comment noting
   the Chromebook fixture constraint (gzip-only floor).
2. `scripts/verify-musl-release.sh`: expect `lisa-cli-$target.tar.gz`; extract
   it **inside a `debian:bookworm` container that first asserts `xz` is
   absent** — this turns "the archive path needs no xz" from an artifact of
   runner tooling into a checked invariant, per Linux target, on the native
   per-arch runners release CI already uses. Keep every existing check
   (single static ELF, no INTERP, ldd, embedded WASM magic, embedded
   runtime-manifest sha, bullseye execution) unchanged.
3. `scripts/verify-shell-installer.sh` (new) + a step in
   `build-global-artifacts`: after `dist build --artifacts=global` produces
   `lisa-cli-installer.sh`, run the *generated installer itself* in a
   no-network-dependency rehearsal: serve `target/distrib/` over a local HTTP
   server, then execute the installer in a fresh `debian:bookworm` container
   (assert `xz` absent first) with the installer's documented base-URL
   override pointing at the local server. Assert exit 0, `~/.local/bin/lisa`
   exists, `lisa --version` runs, and the printed PATH guidance names
   `~/.local/bin`. This exercises the same code path the README one-liner
   uses — download → checksum → extract → place — minus only the public URL.
   The global job runs on amd64; this rehearses the amd64 leg end-to-end.
   The arm64 archive-extraction leg is covered natively by (2) on the
   `ubuntu-22.04-arm` local job; qemu-emulating a full arm64 installer run in
   the amd64 global job adds a flaky dependency (binfmt setup) for little
   marginal proof and is deliberately out.
4. `scripts/package-debs.sh`: read `lisa-cli-${rust_target}.tar.gz`.
5. `aur/PKGBUILD`: point `source_x86_64`/`source_aarch64` at the `.tar.gz`
   asset names (makepkg picks the extractor from the extension).
6. `docs/knowledge/release-checklist.md`: update the expected-asset lists so
   the checklist John executes matches what the pipeline now produces.

## Why this satisfies the acceptance criteria

- **AC1 (fixture install works, both arches)**: the installer's Linux archives
  become gzip; the fixture has tar+gzip. CI proves extraction xz-free per arch
  (2) and rehearses the full installer flow (3). The exact README command
  against the *published* release becomes true at the next stable cut
  (T-046-03-02's checklist); the runbook fixture probe is the post-cut check.
  PATH guidance is unchanged from T-046-03-01 (`~/.local/bin` + success msg)
  and is asserted in (3).
- **AC2 (no xz/Rust/compiler; CI verifies both archive paths; checksum +
  static-musl preserved)**: nothing new is installed in the fixture; the
  no-xz assertions in (2)/(3) make regression structural. Checksum sidecars
  and installer-embedded sha256 verification are cargo-dist behavior
  independent of format; static-musl checks in `verify-musl-release.sh` are
  retained verbatim.

## Risks and mitigations

- **`unix-archive` behavior in 0.30.4**: verified locally before commit by
  installing dist 0.30.4 and running `dist plan` (artifact names must show
  `.tar.gz`) and generating the installer to inspect its extraction and
  checksum logic. If `dist generate` wants to rewrite CI, `allow-dirty=["ci"]`
  already covers our extended `release.yml`.
- **Base-URL override name drift**: the rehearsal script must use the override
  the 0.30.4-generated installer actually honors; confirmed against the
  locally generated installer during implementation, not assumed.
- **Stale-format references**: research enumerated every `.tar.xz` coupling
  point (verify script, deb packaging, AUR, checklist); all are updated in
  this ticket. Docs archives (`docs/archive/**`) are historical records and
  stay untouched.
- **In-flight release**: no tags are being cut mid-ticket; format flips
  atomically at the next tag, and `publish-apt-repository`/brew consume
  regenerated metadata, not hardcoded names.
