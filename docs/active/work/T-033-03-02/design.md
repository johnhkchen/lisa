# T-033-03-02 Design — consecutive reuse live proof

## Decision summary

Add one native plugin regression that drives two resident physical panes through
ten consecutive Codex reassignments, deliberately loses the original
acknowledgment on assignment six, and then runs an equivalent ten-assignment
Claude control through the same release-and-reschedule loop.

The test will emit stable pipe-delimited evidence rows. A small shell harness
will run that focused test with output capture, independently validate the row
counts and allowed outcomes, and optionally render a Markdown run report. The
checked-in report will be generated by an actual harness run.

No production scheduler logic, adapter contract, configuration, or public API
will change.

## Design goals

The proof must be:

- consecutive: one scheduler state repeatedly releases and reuses resident
  physical panes;
- plural-pane: assignments alternate naturally across two named pane IDs;
- faithful: production scheduling, assignment, timeout, recovery, release, and
  adapter transitions are exercised;
- exhaustive per row: exactly one of the two allowed Codex outcomes is recorded;
- fault-bearing: one original-generation acknowledgment is intentionally absent;
- parity-protecting: Claude uses `WaitingForClear` and immediate ownership;
- deterministic: no process, network, Zellij, model, or sleep;
- reportable: a reviewer can inspect a durable table without test source;
- honest: “live-style” is distinguished from a token-consuming live client run.

## Option 1 — shell-only lifecycle simulator

A standalone script could loop over ten assignments, update textual states,
force one timeout, and write a report.

### Advantages

- simple output capture;
- no Rust test additions;
- easy to run on any host with Bash.

### Drawbacks

- duplicates the scheduler contract instead of testing it;
- could remain green while production transitions regress;
- cannot prove adapter reset behavior or real launch cardinality;
- weakens the field evidence into an illustrated specification.

### Decision

Rejected. The report must derive from production state transitions.

## Option 2 — full interactive Zellij plus live Codex and Claude

Launch `lisa loop`, provision tickets, wait for model sessions, force one ack
loss at the hook boundary, and inspect panes and artifacts.

### Advantages

- highest host fidelity;
- covers Zellij input delivery and installed client behavior;
- genuinely token-consuming field evidence.

### Drawbacks

- cannot run safely inside the Lisa-managed session working this ticket;
- nondeterministic model latency and cost;
- Claude and Codex authentication become environmental prerequisites;
- forcing a precise lost event needs mutation of live hook transport;
- difficult to make a standing CI regression;
- a failure could conflate scheduler, host, auth, network, and model causes.

### Decision

Rejected for the committed regression. The artifact will state that terminal
and installed-client transport remain outside the native proof.

## Option 3 — one giant native test with human-only assertions

Drive the production state machine through ten Codex and ten Claude assignments
and rely solely on Rust assertions.

### Advantages

- faithful and deterministic;
- automatically included in the plugin test suite;
- minimal new files.

### Drawbacks

- no durable harness run report;
- Cargo's pass/fail line does not expose assignment-by-assignment outcomes;
- a reviewer cannot verify the forced fault or pane distribution without
  reading the implementation.

### Decision

Insufficient alone. Selected as the behavioral core, with structured output and
a report wrapper.

## Option 4 — native production-state test plus reporting harness

Use a private test helper to construct multi-ticket states, drive the real
scheduler lifecycle, emit stable rows, and wrap the test in a validating shell
runner that generates Markdown.

### Advantages

- production state is the behavioral authority;
- all timing boundaries are injected;
- normal `cargo test -p lisa-plugin` runs the regression;
- report generation is repeatable and separately validates evidence counts;
- the shell layer contains no copied transition model;
- report rows identify tickets, panes, generations, outcomes, and stalls.

### Drawbacks

- test output becomes a small interface consumed by the harness;
- the unit test is longer than a focused one-edge test;
- the report is environment-stamped evidence, so future reruns will change it;
- native host substitution cannot prove actual terminal keystroke delivery.

### Decision

Selected. It is the narrowest approach satisfying both regression and report
requirements without falsely claiming a live model run.

## Fixture design

Add a test-local `consecutive_reuse_state(agent, pane_ids, ticket_count)` helper
near `pane_name_schedule_state`.

It creates a temporary ticket directory containing sorted ticket IDs:

```text
T-CODEX-01 ... T-CODEX-10
T-CLAUDE-01 ... T-CLAUDE-10
```

Each ticket is `status: open`, `phase: ready`, and carries the requested agent.
Tickets are independent. `Dag::get_ready_tickets` sorts IDs, so scheduling is
predictable.

The state enables permissions and discovered slots, sets `max_threads` equal to
the two-pane count, sets `wind_down_secs = 0`, and uses a one-second assignment
ack timeout. Both pane slots begin with resident sessions from the tested
provider. This guarantees every scheduled ticket takes a reuse path; there is
no initial fresh-pane exception.

Two pane IDs, 10 and 11, demonstrate reuse across multiple physical seats. Five
rounds schedule two tickets each. After each round resolves, both threads are
marked completed and both slots are released before the next scheduling poll.

## Codex scenario design

For each of five rounds:

1. call `schedule_ready_tickets`;
2. collect the two active tickets and pane IDs;
3. assert each seat is `AssignedPendingAck` with no deadline and transport is
   `WaitingForClear`;
4. deliver the cleared signal, then assert the deadline is armed and the seat
   remains unowned;
5. for every ordinary assignment, send an exact matching current-generation
   payload and assert the single promotion to `Owned`;
6. on sequence six, omit the current acknowledgment and evaluate its
   exact original deadline;
7. assert `Recovering`, backdate exit grace, and invoke transition timeouts;
8. count exactly one fresh recovery launch for that ticket;
9. acknowledge the recovery generation and assert `Owned`;
10. emit exactly one evidence row per assignment;
11. complete and release both tickets.

Because generations are allocated monotonically, the fault row's recovery
generation affects later generation numbers. The report records observed
generation values instead of assuming sequence equals generation.

Ordinary rows use outcome `ack-then-owned`. The fault row uses
`timeout-then-fallback`. No third Codex outcome is permitted.

## Exactly-one-outcome invariant

The native test owns an in-memory vector of row records or counters. Each
scheduled ticket is inserted once after reaching `Owned`. Duplicate ticket rows
or missing scheduled tickets fail the test.

At the end:

```text
Codex row count = 10
ack-then-owned count = 9
timeout-then-fallback count = 1
silent stall count = 0
unique ticket count = 10
pane set = {10, 11}
```

The fallback row must also have `fallback_launches = 1`; ordinary rows must
have zero recovery launches. Every final assignment state must be `Owned`.

## Claude control design

Build a separate two-pane state with ten Claude tickets and resident Claude
sessions. Run the same five-round scheduling, completion, release, and
rescheduling pattern.

Immediately after scheduling, every Claude pane must be:

```text
transport = WaitingForClear
assignment = Owned
owned = true
```

Call `handle_cleared_signal` for each pane and assert:

```text
transport = Idle
assignment = Owned
active Codex generation = None
```

Emit one row per assignment with control outcome
`clear-then-owned-unchanged`. This label is outside the Codex outcome domain and
is validated separately.

At the end:

```text
Claude row count = 10
control outcome count = 10
pending/recovering states observed = 0
pane set = {20, 21}
```

Ten control rows make “equivalent” literal: same assignment count, pane count,
release cadence, and consecutive reuse structure.

## Structured output contract

The focused test prints only prefixed evidence records intended for the harness:

```text
T0330302|assignment|provider=codex|sequence=01|ticket=T-CODEX-01|pane=10|generation=1|outcome=ack-then-owned|fallback_launches=0|final=owned|silent_stall=false
T0330302|assignment|provider=claude|sequence=01|ticket=T-CLAUDE-01|pane=20|generation=none|outcome=clear-then-owned-unchanged|fallback_launches=0|final=owned|silent_stall=false
T0330302|summary|codex=10|ack_then_owned=9|timeout_then_fallback=1|claude=10|silent_stalls=0
```

Field names and outcome spellings are stable and deliberately grep-friendly.
The Rust assertions remain authoritative; output is evidence, not a substitute
for assertions.

## Harness design

Create `docs/active/work/T-033-03-02/harness/run.sh`.

The runner:

- accepts optional `--report PATH`;
- uses `CARGO` if supplied, otherwise `cargo`;
- runs only the named test with `--nocapture --test-threads=1`;
- captures combined output in a temporary file;
- normalizes prefixed evidence records;
- validates ten Codex rows, ten Claude rows, one forced fallback, nine ordinary
  acknowledgments, zero silent stalls, and the expected summary;
- validates both pane IDs occur for each provider;
- prints a concise PASS receipt;
- renders a Markdown table and environment header when `--report` is supplied;
- cleans temporary output on success and failure.

The wrapper does not interpret scheduler state. It validates the emitted
contract and makes the run inspectable.

## Report design

Generate `docs/active/work/T-033-03-02/run-report.md` by executing:

```text
docs/active/work/T-033-03-02/harness/run.sh \
  --report docs/active/work/T-033-03-02/run-report.md
```

The report will contain:

- date, Git revision, Rust and Cargo versions;
- exact harness command and proof boundary;
- a 10-row Codex table;
- a 10-row Claude table;
- summary counts and verdict;
- explicit note that no live client or Zellij process ran;
- broader verification commands and outcomes added after the harness run.

The generated report is committed as evidence, while the script makes it
reproducible.

## Verification design

Run in increasing scope:

1. focused test with `--nocapture`;
2. harness with checked-in report output;
3. rerun harness to a temporary report and compare stable table/summary facts;
4. `cargo test -p lisa-plugin`;
5. `cargo test --workspace`;
6. `cargo fmt --all -- --check`;
7. `cargo clippy -p lisa-plugin --all-targets -- -D warnings`;
8. `cargo check -p lisa-plugin --target wasm32-wasip1`;
9. `bash -n` and, if available, `shellcheck` for the runner;
10. `git diff --check` on exact owned paths.

## Commit design

The meaningful implementation unit is the native scenario, runner,
documentation, and generated report. Commit exact paths through Lisa:

```text
lisa commit-ticket --ticket-id T-033-03-02 \
  --message "test: prove consecutive acknowledged Codex reuse" \
  --include crates/lisa-plugin/src/lib.rs \
  --include docs/active/work/T-033-03-02/harness/README.md \
  --include docs/active/work/T-033-03-02/harness/run.sh \
  --include docs/active/work/T-033-03-02/run-report.md
```

The six phase artifacts remain for Lisa's completion transaction and are not
part of the source commit.

## Risks and mitigations

### Test-output parsing drift

Cargo may prefix the first captured line. The runner extracts from the unique
`T0330302|` marker rather than requiring it at column zero.

### Generation-number coupling

The test reads active generations from state. It never hard-codes generation
six after a fallback increments the allocator.

### Ticket phase mutation

Scheduling advances fixture tickets from Ready to Research on disk. The helper
uses a temporary directory, and each ticket is scheduled only once.

### Release cooldown

The fixture uses zero wind-down. Release still exercises production code but
does not introduce sleeps.

### False live claim

README and report label the harness native live-style evidence and list the
uncovered terminal/client boundary explicitly.

## Design conclusion

The selected design turns the acknowledged-assignment contract into a repeated
two-pane lifecycle proof, gives the fault path one precise successful recovery,
and makes Claude parity visible in the same evidence format. The scheduler
remains unchanged; only its standing regression evidence expands.
