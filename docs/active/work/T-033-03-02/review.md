## Acceptance-criterion assessment

### At least ten consecutive Codex reassignments

Met. Ten unique tickets are scheduled in one state across five rounds. Each
round releases two completed reservations while preserving resident Codex
sessions, rebuilds the fixture DAG, and schedules the next two tickets into the
same pane IDs.

The test starts both panes resident, so all ten assignments are reuses; there is
no fresh initial assignment hidden in the count.

### Across reused panes

Met. Both Codex pane 10 and pane 11 appear in every round, five assignments per
pane. The harness rejects any pane set other than `10 11`.

### Includes one forced lost-ack case

Met. Sequence six intentionally does not call the original generation's
acknowledgment edge. It evaluates the exact armed deadline read from production
state and asserts the resulting recovery generation and unowned state.

The fresh attempt is acknowledged successfully so the row resolves to the
ticket's allowed `timeout-then-fallback` outcome rather than the separately
covered terminal `RecoveryFailed` outcome.

### Exactly one named Codex outcome per assignment

Met. The test emits exactly one row after each ticket reaches `Owned`. In-memory
unique-ticket sets reject duplicates. The shell validator requires exactly nine
`ack-then-owned`, exactly one `timeout-then-fallback`, and exactly ten Codex
rows. Unknown or extra records make the harness fail.

### Zero silent stalls

Met within the native scheduler boundary. Every row explicitly ends
`final=owned|silent_stall=false`; the runner requires 20 such rows, rejects any
`silent_stall=true`, and requires one recovery launch for the fault row.

No row can remain pending, recovering, or recovery-failed and still be emitted
as passing evidence because the Rust test asserts `SeatAssignmentState::Owned`
before output.

### Equivalent Claude control unchanged

Met. Ten Claude tickets use the same two-pane, five-round schedule / complete /
release / recompute cadence. Each row asserts the established shared clear
transport and immediate Claude ownership before and after `handle_cleared_signal`.

The validator requires ten `clear-then-owned-unchanged` outcomes on panes 20 and
21 with no generations or fallback launches.

### Harness run report

Met by `run-report.md`. The report shows all assignment rows, totals, toolchain,
command, verdict, and limitations. It is reproducible with `harness/run.sh
--report ...`.

## Determinism assessment

The regression has no sleeps. Original and recovery deadlines are read from the
state that production created and supplied directly to injected-time evaluators.
Exit grace is made eligible by backdating the existing private timestamp.

Ticket files live under `tempfile::TempDir`. Each consumed fixture ticket is
explicitly advanced to Done before the real DAG is rebuilt, modeling the
completion boundary without invoking artifact polling unrelated to this test.

Active ticket/pane pairs are sorted before evaluation and reporting. Evidence
sequence therefore does not depend on hash-map iteration.

The harness uses temporary raw and normalized captures and removes them with a
trap. It has no network, authentication, client installation, token, or Zellij
dependency.

## Implementation deviation and correction

The first design draft incorrectly described native Codex reuse as `FreshExec`.
The first focused run observed the real state—`WaitingForClear` plus unarmed
`AssignedPendingAck`—and exposed the assumption immediately.

The test and all prior artifacts were corrected before implementation continued.
Both native adapters share the clear-handshake transport. Their contract differs
after scheduling: Claude is immediately owned; Codex stays unowned until the
cleared handler submits the generation-tagged prompt and the matching provider
ack arrives.

This correction improved the proof because it now protects both the unchanged
shared transport and the provider-specific ownership boundary. No production
defect or source change resulted.

## Open concerns and limitations

### Native live-style, not installed-client live

The harness does not launch Zellij, Codex, or Claude. It does not prove terminal
keystroke delivery, actual client response latency, authentication, network
behavior, or real hook-file transport across ten model turns.

This is intentional and explicit in both README and report. The proof exercises
the real scheduler and adapter lifecycle boundary deterministically, while
`T-029-01` remains the installed-client empirical precedent.

### Private-state coupling

The regression is intentionally coupled to private assignment and transport
states. That is appropriate for a contract regression, but state renames will
require test and report-schema review. The coupling is confined to `#[cfg(test)]`.

### Evidence-output schema

The runner consumes stable printed records from the Rust test. A future field
rename must update the runner and regenerate the report together. Native Rust
assertions remain the correctness authority; parsing cannot make a failing test
pass.

### Test size

The combined two-provider scenario is larger than a focused unit test. It is
kept as one test because the acceptance criterion requires an equivalent control
over the same cadence and one combined report. Smaller predecessor tests still
pin individual edges and failure modes.

## Critical issues requiring human attention

None.

The only review judgment is whether the ticket's phrase “live-style harness” is
intended to require an actual token-consuming Zellij/client run. The story's
standing-regression scope and predecessor harness conventions support the native
interpretation used here, and the artifact makes the limitation impossible to
miss. If a real-client certification is desired, it should be run as a separate
environment-stamped empirical exercise rather than replacing this deterministic
regression.
