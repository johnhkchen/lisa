# Design: one-source configuration table

## Objective

Bind the root README configuration table to `config::CONFIG_KEYS` so the normal
Rust test suite rejects drift in key coverage, default values, or descriptions.
Keep README rendering human-readable while treating the in-code catalog as the
canonical configuration metadata.

## Required invariant

The complete chain after this change is:

1. `COMPLETE_CONFIG_FIXTURE` represents every fixed key accepted by the parsed
   `.lisa.toml` structure.
2. `config_catalog_covers_every_parsed_key_exactly_once` binds that fixture to
   `CONFIG_KEYS`.
3. Existing config and init rendering tests bind `.lisa.toml` stubs to
   `CONFIG_KEYS`.
4. A new README test binds every configuration table row to `CONFIG_KEYS`.

Together, the tests make a parsed-key addition incomplete until the catalog has
metadata and README carries the same metadata.

## Option 1: build-time README generation

### Shape

- Add a generator executable or build script.
- Read `CONFIG_KEYS` and rewrite the root README table.
- Invoke it during a build or as a maintenance command.

### Advantages

- README bytes can be physically generated from the catalog.
- Contributors do not hand-edit data rows.
- Ordering naturally follows catalog order.

### Costs and constraints

- A Cargo build script cannot directly import ordinary crate source without
  duplicating or restructuring modules.
- Rewriting a tracked source document during a normal build is surprising.
- A separate generator command can still be forgotten unless a sync test exists.
- It introduces a new tool surface for a 17-row table.
- It complicates package builds where the crate readme points outside the crate.
- It does not inherently provide the requested diagnostic for a fake missing
  description.

### Assessment

Viable, but disproportionate to the repository's existing unit-test sync pattern.

## Option 2: render an expected Markdown block and compare bytes

### Shape

- Add a test-only renderer over `CONFIG_KEYS`.
- Extract the README table block.
- Compare expected and actual Markdown byte-for-byte.

### Advantages

- Very small implementation.
- Table order, punctuation, and descriptions cannot drift.
- Closely resembles the bundled-workflow byte-sync test.
- The expected table is visibly a direct rendering of the catalog.

### Costs and constraints

- A single byte mismatch diagnostic usually prints a large left/right diff.
- A missing fake key is reported as a block mismatch, not specifically as a
  missing description.
- Markdown formatting details become part of the invariant even where they do
  not affect configuration metadata.
- Version and string-default presentation still need an explicit conversion.
- Additional targeted validation would be needed to satisfy the requested
  missing-description error cleanly.

### Assessment

Viable, but its strongest property is stricter than the acceptance criteria while
its default diagnostics are weaker than requested.

## Option 3: parse and validate README rows against the catalog

### Shape

- Include the root README in the existing `config.rs` unit tests.
- Locate the exact configuration-table header.
- Parse its three cells into key, default, and description strings.
- Compare every catalog record with the row sharing its dotted path.
- Reject missing rows, mismatched defaults, mismatched descriptions, duplicates,
  and undocumented extra rows.
- Return structured-enough textual errors from the helper.

### Advantages

- Directly matches the ticket's explicitly allowed parsed-table mechanism.
- Diagnostics can name the exact dotted path and field.
- A fake catalog record naturally exercises the absent-description path.
- The comparison ignores irrelevant alignment formatting.
- It needs no dependencies and no production runtime behavior.
- It composes with the existing parsed-key catalog coverage test.
- It preserves ordinary README editing while making metadata drift a test failure.

### Costs and constraints

- The parser supports the repository's simple table rather than all Markdown.
- A pipe character in a future description would require Markdown escaping logic.
- Row order is not automatically enforced unless compared separately.
- README remains a committed rendering, so contributors must update it alongside
  catalog changes.

### Assessment

Best fit for the acceptance criteria and current codebase.

## Option 4: snapshot file outside README

### Shape

- Render catalog metadata into a separate fixture.
- Snapshot-test the fixture.
- Embed or reference that fixture from README tooling.

### Advantages

- Isolates generated bytes from prose.
- Snapshot diffs are straightforward.

### Costs and constraints

- Markdown cannot include another local file in GitHub rendering.
- README would still require duplicated data or a publishing step.
- A fixture sync test would not itself bind the visible README.

### Assessment

Rejected because it does not close the actual operator-facing edge.

## Decision

Use Option 3: a test-local Markdown row parser and catalog verifier in
`crates/lisa-cli/src/config.rs`.

This decision is grounded in three repository facts:

- the catalog and its integrity tests already live in that module;
- root documentation is already included from CLI unit tests elsewhere; and
- the ticket explicitly accepts a parser that asserts key/default/description
  equality.

## Canonical data and presentation

`CONFIG_KEYS` remains canonical for:

- dotted key path;
- TOML default literal; and
- exact plain-English description.

README supplies only Markdown presentation around those values.

The verifier will compare descriptions exactly, including punctuation. This is
important because accepting merely non-empty descriptions would allow the catalog
and README to develop independent wording again.

The verifier will display TOML defaults in README form:

- a default surrounded by ordinary double quotes loses only those outer quotes;
- booleans remain unchanged;
- integers remain unchanged; and
- `{}` remains unchanged.

Examples:

- `"\"managed\""` becomes `managed`;
- `"false"` remains `false`;
- `"600"` remains `600`; and
- `"{}"` remains `{}`.

This preserves the README's established convention while deriving the expected
value from the catalog.

## Table discovery

The parser will search for the exact two-line header:

```markdown
| Key | Default | Description |
|-----|---------|-------------|
```

Data rows begin immediately afterward and continue while lines begin with `|`.
The first blank or non-table line ends the table.

This avoids coupling the test to unrelated text in the Configuration section.
Failure to find the header returns an actionable error rather than panicking in
the parsing helper.

## Row parsing

For every table line:

- remove the leading and trailing pipe;
- split into exactly three cells;
- trim surrounding whitespace;
- remove one surrounding backtick pair from key and default cells;
- retain the description cell as trimmed prose;
- store the result by dotted key path; and
- reject duplicate key rows.

The catalog's existing single-line-description test prevents newlines. A row with
more than three cells is rejected with a malformed-row diagnostic. If a future
description needs a literal pipe, the parser and renderer convention must be
extended explicitly.

## Verification behavior

For each `ConfigKey`:

1. Look up a README row by `path`.
2. If absent, return an error saying the README table is missing the description
   for that named path.
3. If its description is empty, return the same class of named error.
4. Compare the README default with the catalog-derived display default.
5. Compare the README description exactly with the catalog description.

After catalog records pass, reject any README row whose key is absent from the
catalog. This prevents stale rows after a key is removed or renamed.

The error ordering deliberately checks existence/description before default. That
makes a new catalog record fail with the ticket's required missing-description
message rather than a less useful count mismatch.

## Tests

### Positive sync test

`readme_config_table_matches_catalog` will pass the real `CONFIG_KEYS` and embedded
root README to the verifier. It will panic with the returned diagnostic on drift.

This single test covers:

- all 17 current keys;
- exact defaults after README presentation normalization;
- exact descriptions;
- guards rows;
- triage rows;
- duplicate rows; and
- stale extra rows.

The existing parsed-key coverage test supplies the parsed-config side of the
acceptance criterion.

### Negative fixture test

`readme_config_table_names_missing_fake_description` will create a local catalog
vector from the real entries and append a fake `ConfigKey`.

The fake record will have a dotted path not in README and otherwise valid metadata.
The verifier must return an error containing both:

- `missing description`; and
- the fake dotted path.

This test demonstrates the contributor-facing failure without intentionally
breaking the suite.

## README update

Replace the current eight rows with all 17 catalog rows in catalog order. Use:

- catalog dotted paths;
- catalog-derived display defaults; and
- catalog descriptions verbatim.

This includes `version`, `runtime.zellij`, every scheduling setting, guards, and
triage.

## Rejected additions

- No public API: README verification is a repository maintenance concern.
- No runtime README reads: operators should pay no execution cost.
- No new crate or dependency: line parsing is sufficient.
- No marker comments: the existing exact table header gives an unambiguous anchor.
- No mutation command: the acceptance criterion asks for sync enforcement, and the
  parsed-table approach is explicitly permitted.
- No ticket frontmatter edits: Lisa owns phase progression.

## Expected maintenance flow

When a contributor adds a parsed fixed config key:

1. The parsed-key coverage test requires a catalog record.
2. Catalog voice/default tests require valid metadata.
3. Init rendering tests require that metadata on `.lisa.toml` surfaces.
4. README sync fails with the named missing-description error.
5. The contributor adds the matching README row.
6. The suite passes only when default and description match exactly.

That failure chain makes undocumented knobs visible during development and CI.
