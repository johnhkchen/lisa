## Context

**Read `S-059-01` first.** It states what is being committed to and why it is an interface
decision rather than a flag, including the option of deciding against it.

`lisa status` and `lisa validate` compute structured answers and print prose. The everyday path
points at both (`init → validate → status → loop`), and neither has `--json`:

    $ lisa status --json
    error: unexpected argument '--json' found

The downstream reader that prompted this is `rail`, a read-only status strip in the pane beside a
running loop (`~/swe/repos/screen-design/rail`). What it does today, and what this ticket should
let it delete:

- **The ready count.** `rail`'s `readiness_from` takes `lisa validate --check-tools`'s exit status
  as the verdict, then scans the output for the token `ready` and takes whichever adjacent token
  parses as a number. Deliberately loose, so a reworded sentence degrades to "cannot say how many"
  rather than to a wrong number.
- **Which seats are working.** A join of `.lisa/signals/pane-<id>.lease` against `attempt_lease`
  in `provenance.jsonl`, treating a seat as live when its attempt has no closing record. Correct,
  but it is scheduler bookkeeping reconstructed from artifacts.
- **The blocked count.** Inferred from `.awaiting` signal files, which `lisa hooks-guide` says the
  plugin reads and deletes. Unobservable to a second reader by design.

The third of those is the one worth noticing: a reader outside the plugin has no supported way to
ask "what is happening right now", so it reaches for the queue, loses the race, and ends up
reconstructing state from ledgers. Everything it needs is already computed inside `status`.

## Acceptance Criteria

- `lisa status --json` and `lisa validate --json` print one JSON document on stdout and nothing
  else — no banner, no progress line, no trailing prose — so the output can be piped without
  filtering. Human output is unchanged when the flag is absent.
- The payload carries at least what the human output already says: for `status`, the per-ticket id,
  title, status, phase and `depends_on`; the wave or dependency structure it prints; the counts it
  summarises (done, in progress, ready, blocked); any outstanding notes with the ticket they belong
  to; and, for each attempt currently in flight, its ticket id, attempt id and pane. For
  `validate`, the verdict and the ready count, plus each problem it found in a form that names the
  file and the reason.
- Exit status keeps its current meaning under `--json`, unchanged. `validate`'s exit code is what
  rail already treats as authoritative for "could a run start here" — a JSON body must be an
  addition to that contract, never a replacement for it.
- A machine-readable failure is still machine-readable: when the command fails, `--json` prints a
  JSON error document rather than a bare message, so a caller does not have to parse two formats
  depending on the outcome.
- The document carries a version or schema marker, and the field-stability rules are written down:
  which fields a consumer may rely on, that unknown fields must be ignored rather than treated as
  errors, and what a consumer should expect when a field it knows disappears.
- The shape is documented where a consumer will look — `lisa help`, and the same guide-level
  treatment `lisa hooks-guide` gives the signal contract. A stable shape nobody can find is not an
  interface.
- Both commands share one serialisation path, so the two cannot drift into different spellings of
  the same concept. If the two are split into separate tickets, they must still share it.
- Tests assert the documents parse, carry every field the human output states, and agree with it —
  a JSON body that disagrees with the prose beside it is worse than no JSON at all.
- The in-flight attempt list agrees with the scheduler's own view, not with a re-derivation from
  the ledger. If that is not reachable from where `status` runs, say so in the review and state
  what the number does mean, so a consumer knows which question it answers.

## Notes

- Deciding against this is a valid outcome and should be recorded as such rather than quietly
  narrowed to something smaller. If the answer is "the CLI's output is for humans and the ledgers
  are the machine interface", then say that plainly and document the ledger formats as an
  interface, because a downstream reader will use them either way — `rail` already does.
- Worth checking while in `status`: several of the numbers it prints are already assembled into
  structs to be formatted. If so, this is mostly a serialisation surface and the cost is in the
  stability commitment, not the code.
- `.lisa/signals/` should stay exactly as it is. Its single-consumer, ephemeral contract is
  correct for the plugin, and this ticket is not an argument for publishing it. It is an argument
  that readers excluded by that contract need somewhere else to go.
- The consumer is `rail` and it is available to test against: `rail snapshot` renders its whole
  state headlessly in about 4ms, and `rail agent-instructions` describes how it reads a project. If
  a shape is proposed, it can be tried against a real second reader before it is committed to.
