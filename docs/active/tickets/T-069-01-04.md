## Context

**Read `S-069-01` first.**

`crates/lisa-cli/src/upgrade.rs` already knows where a Lisa came from —
`classify_install` recognises `/Cellar/`, `/homebrew/`, `/linuxbrew/` and apt paths
— and it currently uses that knowledge to *refuse*:

> *"this lisa is managed by {manager} … and lisa upgrade will not write over a file
> it owns"*

The refusal even prints `brew update && brew upgrade lisa`. It is one step from
doing the right thing instead of describing it.

Two things follow from channels being packages.

**Channel is readable, not recorded.** `T-068-01-01` put channel in a per-user
config file because nothing else could answer. On a package-managed box the
installed package answers, and a config field that can disagree with it is a second
source of truth waiting to be wrong.

**Upgrading is the package manager's job.** Lisa keeps the parts no package manager
does — the schedule, the refusal to move under a live Zellij, the alarm, the drift
report — and hands off fetch, verify and swap.

## Acceptance Criteria

- **Channel is derived from the install on package-managed boxes**, not read from
  the config file. `lisa-nightly` installed means the channel is nightly, and no
  local edit can claim otherwise.
- **The config field still governs curl-installed and source-built boxes**, which
  have no package to ask. Say clearly which source wins where, because a box that
  answers two ways is the bug this ticket exists to prevent.
- **`lisa upgrade` delegates instead of refusing.** On a brew box it runs the brew
  upgrade for the installed formula; on an apt box, the apt equivalent. It reports
  what it ran and what moved, in the same before-and-after shape `upgrade` already
  uses.
- **`lisa upgrade --channel <name>` switches packages** — the uninstall-and-install,
  or the sources-line change plus `apt-get update`. Whatever it cannot do safely on
  its own it prints for the operator to run, rather than half-doing.
- **The mid-run guard still applies to the delegated path.** `busy.rs` refuses to
  move Lisa while any Zellij session is up, and that must hold when the mover is
  `brew` — otherwise delegation quietly drops the safety `T-068-01-03` was built
  around.
- **Rollback tells the truth per platform.** On apt, `apt-get install lisa=<version>`
  works and should be what is named. **On Homebrew it does not** — `brew switch` is
  gone — so `lisa upgrade --tag` stays as the escape hatch there, and the runbook
  says so before an incident rather than during one.
- **`doctor` reports the channel it derived and where it derived it from** — the
  formula, the suite, or the config file. An operator reading a surprising channel
  needs to know which of the three to go fix.

## Notes

- Keep `lisa upgrade`'s own download-and-swap path. It is what curl-installed and
  source-built machines use, and on Homebrew it is the only rollback there is.
- Worth deciding in review: what happens on a box with both a brew `lisa` and a
  `~/.local/bin/lisa`. It is a real state — the mini would have reached it if
  `S-068-01`'s plan had been followed — and PATH order deciding which one runs is
  how `installed_lisa()`'s bug happened in the first place. Reporting it as a
  problem in `doctor` is probably the whole fix.
- `lisa nightly` is unchanged by this ticket except for the mover it calls. The
  schedule, the alarm and the health record stay exactly as `T-068-01-03` built them.
