## Context

**Read `S-068-01` first.**

Today a box gets its Lisa version from whichever installer touched it last, and
nothing on disk records what that box is *for*. The result, measured 2026-08-14:
curl-installed machines have been on v0.4.4 since 2026-07-19 because GitHub's
`/releases/latest` skips prereleases, Homebrew-installed machines are on
v0.5.0-rc.2 because `dist-workspace.toml` sets `publish-prereleases = true`, and
the dev desk builds `main`. **Nobody chose any of that.**

There is also no way to act on a choice once made. `lisa-cli` has no `upgrade`
subcommand; every machine is updated by a human re-running an installer, which is
exactly why they stop being updated.

This ticket gives a machine a channel and a command that honours it.

### The three channels resolve against the tags that already exist

`auto-release.yml` tags `v<workspace version>` on every green `main`, so the tag
list is already the whole release history. The channels are selection rules over
it, not new artifacts:

| channel | resolves to |
| --- | --- |
| `canary` | the newest tag, prerelease or not |
| `nightly` | the newest tag, prerelease or not, that has soaked and was not superseded |
| `stable` | the newest non-prerelease tag |

## Acceptance Criteria

- **Channel is machine state, not project state.** It lives in a per-user config
  file, not in `.lisa.toml`. `.lisa.toml`'s `version` field records the Lisa that
  set a *project* up and keeps that meaning untouched. `directories::ProjectDirs`
  is already a dependency and already used in `doctor.rs` for Zellij's paths — use
  the same mechanism rather than inventing a path.
- **`lisa upgrade` exists and defaults to the machine's channel.** With no channel
  set anywhere, it behaves as `stable` — the conservative end, so an unconfigured
  box never surprises anyone.
- **`lisa upgrade --channel <name>` sets the channel and upgrades in one step**, so
  putting a machine on a channel is one command and not a config-file edit followed
  by a second command.
- **The three rules above are the resolution, and each is tested against a fixed
  release list** — including the case that started this: with v0.5.0-rc.2 newest and
  v0.4.4 the newest stable, `stable` must resolve to v0.4.4 and `canary` to
  v0.5.0-rc.2.
- **Soak is a stated window, not a guess.** Say what the window is, where it is
  configurable, and what "superseded" means when a newer tag exists but has not
  soaked either. A nightly box must never land on a tag that a hotfix replaced
  twenty minutes later.
- **An upgrade names the version it is moving to and from, before it moves.** A box
  that upgrades silently is one we cannot debug after it breaks.
- **`lisa upgrade --tag <tag>` pins to an exact release.** This is the rollback, and
  `T-068-01-03` depends on it working.
- **Nothing in the release pipeline changes.** `auto-release.yml`, `release.yml` and
  `dist-workspace.toml` are untouched by this ticket; all of it is on the receiving
  end.

## Notes

- Brew and apt cannot carry three channels — one formula, one suite — so `upgrade`
  should reuse the shell installer path (`install-path = "~/.local/bin"`) and say
  plainly what it does when it finds a brew- or apt-managed Lisa instead of
  fighting the package manager for the same file.
- Worth deciding in review: whether channel resolution reads the GitHub releases
  API directly, and what `upgrade` does with no network. Failing loudly and leaving
  the current version in place is the safe answer.
- The apt repo is described in the README as Lisa's "stable channel" and should stay
  that way. This ticket does not change who publishes there.
