## Context

**Read `S-065-01` first**, and `S-063-01`, which is the damage this prevents.

`crates/lisa-cli/src/loop_cmd.rs:38` already carries the right title:

> *"Refuse to start a second scheduler on a board that already has a live one"*

with a refusal message at line 63 and a test at line 707. **It did not fire.**

Measured 2026-08-12, on a board whose loop session was still running:

```
Session: lisa-2 (another session already holds "lisa" — `zellij list-sessions` shows it)
Max threads: 2 (panes: 4)
```

Lisa saw the live session, wrote a sentence naming it, **used that fact to choose
a session name**, and started. A watcher on the desk reported `2 schedulers on one
board` within a minute, and `.lisa/signals/` — which is single-consumer — then had
two readers.

### Why the guard missed it

The refusal keys on `scheduler.alive` through `assess_run`. That board had just
finished — 204 of 204 tickets — so the first loop's scheduler had stopped
stamping while its zellij **server**, and the plugin inside it, kept running.
`assess_run` correctly reported no live run. It was answering a different question
than the one that mattered.

**A finished run is not an absent one.** The session outlives the work, and
`scheduler.alive` cannot distinguish "no scheduler here" from "a scheduler here
with nothing left to do".

And the evidence that would have answered it was already on screen. The naming
logic knew a session held this board.

## Acceptance Criteria

- **A live zellij session holding this board is grounds to refuse**, on its own,
  without asking `scheduler.alive` anything. The fact the naming logic already
  computes is the fact the refusal needs.
- **A finished run that is still resident is caught.** Reproduce it: complete a
  board, leave the session up, run `lisa loop` again. Today that starts `lisa-2`.
- The refusal says what to do — which session holds the board and how to end it.
  `zellij kill-session <name>` worked on 2026-08-12 when `kill <pid>` did not, and
  an operator should not have to find that out with `lsof`.
- **Attaching is a legitimate answer and refusing outright may not be.** Say
  whether `lisa loop` against a board that already has one should offer to attach
  to the running session rather than only decline; a slot that presses this
  unattended needs an outcome that is not an error.
- `scheduler.alive` staying as evidence is fine. It must stop being the *only*
  evidence.
- The `-2` suffix path is examined and either removed or justified in writing. A
  second session on the same board is the failure this whole story exists for, and
  the code currently has a naming convention for it.

## Notes

- This was caused by the assistant's own stray shell command, which is the fairest
  possible test: the guard has to hold against an accident, not only against a
  deliberate second run.
- `T-063-01-01` added `note_other_schedulers` to `poll_tick`, so a running plugin
  now *notices* company. This is the other half — refusing to become company.
  Detection after the fact does not unspill the signals.
- Cheap to check and expensive to miss: two schedulers on one single-consumer
  directory cost this desk ten agent sessions and most of a morning.
