## Context

**Read `S-062-01` first.**

The stack's expanded member should be the pane that most recently produced
output, changed only while the operator's focus is outside the stack.

### What lisa already knows

The plugin consumes `.lisa/signals/` and holds the seat state. `pane-N.heartbeat`
is written on every tool call — *"copies the scheduler-owned attempt lease into an
atomic liveness signal"* — so **the newest heartbeat is the most recently active
pane**, and it is already being read. No new source is needed.

A pane with no lease is not a candidate at all, however recently anything touched
it.

### The two constraints, in order

**Focus is never moved.** This is the one that decides the design. If the
operator's focus is inside the stack, lisa does nothing — no re-expansion, no
reordering, nothing. The stack is theirs while they are in it.

That makes the first thing to establish a plain question of fact: **can the
expanded member of a zellij stack be changed without moving focus?** If the
plugin API cannot do it, this ticket is a finding rather than a fix, and saying
so with the API call you tried is a complete outcome.

**No static `expanded=true`.** It was tried and it re-applied on every terminal
resize, snapping focus to the first pane. Whatever this does happens at runtime,
in response to state, not in the generated layout.

### Where the churn goes

With two agents working, "most recently active" changes every few seconds. That
is fine and is the operator's explicit choice, *because* it can only change while
they are not in the stack. A design where the flipping is visible is the wrong
one even though it satisfies the words.

## Acceptance Criteria

- With the operator's focus on the plugin pane, the expanded stack member is a
  pane holding a lease, and follows the newest heartbeat. Reproduce the reported
  state first — focus the plugin, press `v`, observe an idle pane expanded — then
  show it fixed.
- **Focus never moves.** Say how you are sure, and cover the case that started
  this: focus outside the stack, state changes, focus stays where it was. If the
  API cannot separate the two, report that instead of shipping something that
  moves focus.
- **With focus inside the stack, nothing happens.** The operator reading pane 2
  while pane 3 wakes up sees no change. This is the criterion most likely to be
  missed, because it is a non-event.
- A resize changes nothing. That is the previous attempt's failure and it must
  not return; test a resize with the loop running.
- No pane with a lease is ever collapsed in favour of one without. An idle spare
  is never the answer while any seat is working.
- With every seat idle — between runs, or before the first assignment — behaviour
  is unchanged from today. There is nothing to promote and nothing should move.
- The pane count and the `2 × max_threads` reasoning are untouched.
- The generated layout still carries no `expanded` attribute.

## Notes

- Reported from a desk running three stations, where the loop pane is a 70%
  region the operator glances at rather than works in. That is the case this
  helps: the value is in what the loop looks like when you are *not* using it.
- If the honest answer is that zellij can only expand by focusing, say so plainly
  — a smaller version exists (promote only at the moment a ticket is assigned,
  when a focus change is arguably wanted) and the operator explicitly declined it
  when asked. Do not quietly build it.
