## Context

**Read `S-069-01` first.** `T-069-01-04` built `shadowed_install_report()` for
exactly this hazard and its doc comment states the case correctly:

> *"a box can carry a package-manager Lisa **and** one the shell installer wrote
> into `~/.local/bin`, and then PATH order decides which one runs — including
> which one a nightly job upgrades."*

**The check cannot see the case it was written for.** Measured on this MacBook,
2026-08-14:

```
/opt/homebrew/opt/lisa/bin/lisa    lisa 0.4.4      (brew keg, present and runnable)
/opt/homebrew/bin/lisa             absent          (the keg is unlinked)
~/.local/bin/lisa                  lisa 0.5.0-rc.2
~/.cargo/bin/lisa                  lisa 0.4.4
```

Three runnable lisas. `lisa doctor` on the same machine:

```
lisa install    one lisa, at .../target/debug/lisa    OK
```

**"one lisa", on a box with three, reported OK.**

### Why

`shadowed_install_report()` derives the packaged copy from the *running* binary:

```rust
let method = crate::upgrade::classify_install(&exe, home.as_deref());
let packaged = crate::upgrade::install_channel::package_lisa_path(&method, &exe);
```

`classify_install` answers "what installed *this* exe". If the running binary is
not the Homebrew one, `method` is not `Homebrew`, `packaged` is `None`, and the
match arm that reports two lisas is unreachable.

So the check fires only when the brew copy is the one running — **the safe
case.** The dangerous case is the opposite one: a brew keg that is *not* what
answers `lisa`, because then `brew upgrade lisa` moves a binary nobody executes
and the machine's channel describes something that never runs. That is the case
that reports OK.

`screen-design` hit this from the other side while certifying the Mac mini and
put it plainly: *"brew is wrong about what runs."*

## Acceptance Criteria

- **The check asks the machine, not the running process.** Whether a
  package-managed Lisa exists is a question about the box — `brew list`, the
  keg path, the dpkg record — not about which binary happens to be executing.
- **An unlinked keg counts.** `/opt/homebrew/bin/lisa` being absent while
  `/opt/homebrew/opt/lisa/bin/lisa` runs is the measured state here, and it is
  the one where `brew upgrade` is most misleading.
- **More than two counts.** `~/.cargo/bin/lisa` is a third real location on this
  box. The report says "two lisas"; say the number found and list them.
- **The row names which one answered `lisa`.** `first_lisa_on_path()` already
  exists and is already used in the two-lisa arm — a machine with one lisa should
  still say which one, so an operator reading a surprising version knows what
  they are reading.
- **Reproduce it:** a fixture box with a package-managed Lisa that is *not* first
  on `PATH`, and assert the report is not `OK`.
- **`doctor --json` carries the same list**, so a fleet asked by script sees what
  a person sees.

## Notes

- `T-069-01-04`'s own ticket flagged this in its review notes — *"a box with both
  a brew `lisa` and a `~/.local/bin/lisa` … PATH order deciding which one runs is
  how `installed_lisa()`'s bug happened in the first place"* — and the
  implementation covered the half where the packaged copy is running. This is the
  other half.
- Worth deciding in review: the channel row says `installed 0.5.0-rc.3` when
  `~/.local/bin/lisa` is `0.5.0-rc.2`, because it reports the running build. The
  row's own wording is *"this build"*, so it is not lying, but `upgrade.rs`
  deliberately reports the `~/.local/bin` copy instead — `installed_lisa()` exists
  because getting that wrong broke rollback. Two commands on one machine
  answering "installed" differently is worth a deliberate decision rather than an
  accident.
- Homebrew vocabulary trap, worth a line in the runbook wherever brew output is
  quoted: `brew info` prints `lisa: 0.4.4 → stable 0.5.0-rc.2`. Homebrew's
  "stable" means *the formula's non-HEAD version*, not *not a prerelease*. Brew
  will call a release candidate stable in those words, which is the opposite of
  what this story means by the word.
