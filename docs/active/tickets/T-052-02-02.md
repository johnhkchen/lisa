## Context

After the source fixes, some lines legitimately recur — a warning that fires on consecutive polls, a sweep retried. Today each occurrence appends, and the 100-entry ring (`MAX_ACTIVITY_LOG`, crates/lisa-plugin/src/lib.rs ~960, evicting oldest at ~3329) fills with echoes that scroll real news off the end. Fold at append time in `log_activity`: when the incoming event renders identical to the newest entry, bump that entry's count and refresh its timestamp (T-052-01-01's stamps make "latest occurrence" meaningful) instead of pushing. Render the fold the way it was asked for: a trailing (x2), (x3) tag on the single line, wearing the latest age. Append-time bookkeeping only — the UI projection stays a pure pass over the log, no render-time rescans (the render path runs every five seconds; it is not the place for O(n) dedup).

_Advances: a fact that repeats costs one line and an honest multiplier — the ring holds 100 facts, not fourteen facts times seven (P4)._

## Acceptance Criteria

- [ ] Three identical consecutive events render as one line tagged (x3) carrying the latest timestamp; a different event arriving between identical ones breaks the fold (both unit-tested).
- [ ] Ring accounting counts a folded line once: 100 distinct facts fit regardless of how many echoes each absorbed (tested at the cap).
- [ ] Folding happens in `log_activity` (or its immediate seam), not in the renderers — the projection remains a pure map over stored entries (N4).
- [ ] Negative fixture: near-identical events that differ in any rendered content (different ticket, different phase) never fold.
- [ ] `just check` green (fmt, clippy, WASM check, workspace tests).
