## Context

**Read `S-065-01` first.**

**This ticket was filed with a factually wrong Context and is rewritten here.**
The original claimed a running loop never picks up newly-filed tickets, on the
strength of finding `rebuild_dag()` in `keep_working()` and reading only the first
forty lines of `poll_tick()`. The reviewer of attempt 1 refused it, and was right.

At HEAD, `poll_tick()` calls `self.rebuild_dag()` (`lib.rs:9458`) and
`self.schedule_ready_tickets()` (`lib.rs:9527`), and `rebuild_dag()` opens with
`ticket::scan_tickets()` — a fresh `read_dir` of the ticket directory. **A ticket
filed while a live board runs is already picked up on the next five-second tick,
and has been since `73f6d1d` on 2026-02-10.** `keep_working()` adds exactly two
things the poll does not: `terminated = false`, and re-arming the timer.

### The real bug, which is one line

When `check_all_done()` fires, the tick returns without re-arming
(`lib.rs:9578-9582`):

```rust
self.terminated = true;
// Don't re-arm the timer — loop is complete
return;
```

**A board that has finished stops ticking forever.** No rescan, no scheduling,
and — because `stamp_scheduler_alive()` leads the tick — no heartbeat either.

Both symptoms this desk hit on 2026-08-12 fall out of that single `return`:

- **Three tickets filed onto a finished board sat at `ready` and were never
  picked up.** The loop was alive, its session was up, and its timer was gone.
- **`lisa loop` started a second scheduler (`lisa-2`).** The refusal keys on
  `scheduler.alive`, whose stamp had gone stale because the tick that writes it
  had stopped. `S-063-01` has what that cost.

`T-065-01-03` fixed the refusal's evidence. This fixes the reason the evidence
went stale.

### Why it matters more than a resumed loop

A refill slot — `screen-design`'s `S-014` — presses into a board **that has just
gone quiet**, by definition. That is precisely the state where nothing is
listening.

## Acceptance Criteria

- **A board that has completed keeps ticking**, or stops in a way that something
  can wake. Say which, and why the idle cost is acceptable if it keeps ticking.
- **`scheduler.alive` keeps being stamped for as long as the plugin is resident.**
  A scheduler with nothing to do is still a scheduler, and every recovery command
  on this desk reads that file to decide whether one is present.
- **A ticket filed onto a drained board is picked up without a keystroke.**
  Reproduce it: complete a board, leave the loop up, file a ready ticket, and show
  it assigned. This is the case that was actually broken.
- **Rescan cost is bounded.** A full `read_dir` and parse of every ticket every
  five seconds is what happens today on a live board, and the original ticket's
  own criterion called that not-the-answer. Say what triggers a rebuild and why
  that is enough.
- **An unparsable ticket is reported where a person can see it.** Today it is
  skipped and mentioned by `eprintln!` from inside WASM, which no operator reads;
  `scan_tickets_with_diagnostics` exists and is used only at `load()`.
- The quit-modal `keep_working()` path keeps working and stops being the only way
  a drained board resumes.

## Notes

- **The original Context is not preserved above** because it was not a wrong
  diagnosis of a real thing — it asserted behaviour that does not exist. What is
  worth keeping is how it happened: a grep that found `rebuild_dag` in one place
  and a partial read of the function that also calls it.
- The reviewer declined to rewrite the acceptance criteria itself, on the grounds
  that it is the product owner's call. That was the right line, and this rewrite
  is that call being made.
- Its warning is worth repeating: an attempt following the original literally
  would have added a duplicate `rebuild_dag()`, watched new tickets get picked up,
  and passed criteria that were already passing — while the drained-board case
  stayed broken.
