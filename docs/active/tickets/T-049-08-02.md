## Context

Stable-0.4.4 blocker, confirmed at HEAD. `lisa proposal apply` (crates/lisa-cli/src/proposal.rs) runs `validate_apply` then `apply_steps` first; the operator `ProposalActionRecord` and the sidecar state change land only on full success — so a mid-list failure (a prepared command exiting nonzero, a file edit invalidated by an earlier command) leaves real mutations on disk with no ledger row and the proposal stuck Pending, breaking the epic's promise that applying is always a recorded operator action. Reorder: append an attempt row (actor, proposal, step count) **before** the first step runs; execute steps echoing each to stdout as it runs (the audit's blind-`/bin/sh` note — the operator sees what fired, not just what status once displayed); append the outcome row naming applied and failed steps; move the sidecar out of Pending on both outcomes (Applied, or a failed state that unblocks re-triage). Companion fix in the same surfaces: the Pending-proposal projection (crates/lisa-core/src/parking.rs) and `run_proposal_action` filter on `ticket_id` + state only — correlate against the park's attempt lease (the sidecar already stores `source_attempt_lease`), so a stale proposal from an earlier park neither renders against a newer park nor suppresses fresh triage.

_Advances: the ledger tells the truth about operator actions even when they fail halfway — and the advice on screen always belongs to the park it is attached to._

## Acceptance Criteria

- [ ] Ordering tests: a mid-list step failure leaves an attempt row, an outcome row naming the failed step and the steps that landed, and a sidecar not stuck Pending; a clean apply leaves attempt + Applied rows; each step echoed at apply time (string-pinned).
- [ ] Correlation tests: a Pending proposal whose `source_attempt_lease` mismatches the current park's lease is not rendered and does not suppress fresh triage; a matching one behaves exactly as today; existing S-049-07 fixtures pass unweakened.
