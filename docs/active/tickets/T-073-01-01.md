## Context

**Read `S-073-01` first.**

`lisa doctor` already checks nine things about a run and one of them is
*"Checking the environment agents will start in"* — the right neighbourhood.
This adds the check that the run's output depends on: **can a commit made here
reach `origin`?**

The measurement is cheap and read-only. `git ls-remote --heads origin` either
answers or it does not, and it costs one round trip.

## The trap this must not fall into

`ls-remote` proves **fetch**. A loop needs **push**. On most remotes the same
credential does both, and on a fine-grained token or a read-only deploy key it
does not — which is exactly the configuration someone will land while trying to
be careful. So the check has to be honest about which of the two it measured, or
it becomes another green light that means nothing. `git push --dry-run` against
the current branch is the closer measurement; decide which is used and say so in
the output, not only in the code.

The second trap is the one that cost the desk two days: **a check that runs in a
better shell than the work does measures nothing.** `lisa doctor` typically runs
in the operator's terminal, with an agent and an unlocked keychain. The pane the
scheduler spawns may have neither. If the check cannot be made to run under the
pane's conditions, it must say which shell it measured rather than implying it
measured the pane's.

## Acceptance Criteria

- **`lisa doctor` reports whether this board can reach its remote**, in the same
  shape as its existing checks, and names the protocol it went over (ssh or
  https) — because on this desk those two have opposite answers per machine.
- **Fetch and push are not conflated.** Whichever is measured is the word used.
- **`cannot tell` is a distinct outcome from `no`.** No network is not a broken
  credential, and a board with no remote at all is fine — plenty of work is local
  and should not be flagged.
- **It does not block a run.** This is `doctor`, which reports; the operator
  decides. A loop that refuses to start because a remote is unreachable is a
  worse failure than one that commits locally and waits.
- **It costs one round trip and no writes.** Nothing is pushed, no branch is
  created, no credential is stored or altered.
- Reproduce it: on a board whose road is closed — the laptop over https, or the
  mini over ssh, both real today — `lisa doctor` names it, and on a working board
  it passes.

## Notes

- The desk's `credentials` and `which-key` commands answer the machine-wide
  version of this question (`screen-design` `T-030-07`). Lisa should not
  reimplement them and should not shell out to them either — they are one
  operator's tools and lisa ships to anyone. The per-board question *"can this
  repository's remote be reached from here"* is lisa's own and is smaller.
- Worth deciding in review whether this belongs to `doctor` alone or also to the
  moment a loop starts. Starting is where it would pay most and is also where
  lisa is most careful about not adding latency or refusals.
