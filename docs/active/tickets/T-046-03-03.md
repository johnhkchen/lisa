## Context

The Chromebook baseline fixture intentionally has no `xz`, compiler, Rust, or
build tools. A real Codex/mini probe followed the README shell-install path on
arm64 and the installer resolved `v0.3.0` as
`lisa-cli-aarch64-unknown-linux-gnu.tar.xz`. It then stopped before installing
Lisa because tar could not execute `xz`: `tar (child): xz: Cannot exec: No such
file or directory`.

T-046-03-01 moves Linux releases to static-musl binaries and `~/.local/bin`, but
the cargo-dist archives and generated shell installer still use `.tar.xz`.
Static linkage removes the target glibc dependency; it does not remove the
installer's host decompressor dependency. The tested agent recovered only by
discovering Python's `lzma` module, downloading the versioned archive directly,
and extracting it manually. That improvisation is outside the promised README
one-command path.

Make the generated shell installer work on the no-`xz` Chromebook fixture for
both Linux architectures without installing xz, Rust, a compiler, or another
system package first. Preserve the existing verified-release and static-musl
properties. The implementation may change archive format or extraction
mechanism; this ticket owns the user-visible capability, not a prescribed
packaging technique.

_Advances: the blessed one-command install has only the prerequisites the README
and fixture actually declare; static portability includes unpacking the binary,
not merely executing it afterward._

## Acceptance Criteria

- [ ] In fresh arm64 and amd64 Chromebook-test containers where `xz` is absent,
      the exact README shell-installer command exits zero, installs Lisa in the
      configured user-local location, and plain follow-up PATH guidance is
      accurate.
- [ ] The install does not add or invoke `xz`, Rust, Cargo, rustup, GCC/CC/G++,
      Make, or a source checkout; release CI verifies both Linux archive paths
      and preserves checksum/integrity verification plus static-musl execution.
