## Context

**Read `S-064-01` first.**

`lisa status --json` returns this and nothing more about execution:

```json
"config": {"max_threads": 2, "phase_timeouts": {}, "session_timeout_secs": 3600}
```

`.lisa.toml` has the answer already — the running layout passes `client "claude"`
into the plugin alongside `max_threads` and `session_timeout_secs`, two of which
are in the envelope and one of which is not.

A consumer that wants to know what a board runs on has to read `.lisa.toml`
itself. That is a private file, and on a remote host it is a second round trip
for a fact the first one should have carried.

### The consumer, and why it is asking

`screen-design`'s `S-016` is building a view of six boards across three machines,
read from a phone. Its whole purpose is deciding **where to send work**, and three
of those six boards run token-efficient models on purpose. The envelope currently
describes the board's shape and omits the one field that decision turns on.

`rail` is already a disciplined consumer of this interface: it pins its own
`SCHEMA_VERSION`, reads `schema`, `schema_version` and `lisa_version` off the
envelope, and refuses one newer than it understands
(`rail/src/lisa_json.rs:401`). It will not break on an added field.

## Acceptance Criteria

- **`config` carries the configured client** (`claude`, `codex`, …) and the model
  when one is named, `null` when the board leaves it to the client's default.
- Additive within `schema_version: 1` — a consumer pinned to the current version
  keeps reading everything it read before. If that is judged wrong and it needs a
  version bump, say why; the bump is defensible, the silence is not.
- **Nothing secret crosses.** No API keys, no endpoints, no environment. The
  question is *what runs this board*, not *how does it authenticate*.
- The field reflects what the board is **configured** to run, and is present on a
  board that has never run at all. A consumer choosing where to send work asks
  before there is an attempt to inspect.
- `docs/knowledge/json-guide` (or wherever the consumer contract is written) names
  the new field with the same stability promise as the rest of `config`.
- One test reads a board whose `.lisa.toml` names a client, one reads a board that
  does not, and both get a well-formed answer.

## Notes

- `provenance.jsonl` already records `requested` and `actual` per attempt. This is
  not that. That is what happened; this is what the board intends, and only the
  second one can be asked of a board with no attempts.
- Cheapest possible moment to do this: one consumer, `schema_version: 1`, additive
  change. The same edit after a second reader exists is a compatibility
  discussion.
