## Context

`bounded_runner_kills_timeout_near_the_configured_deadline` (crates/lisa-cli/src/triage_agent.rs, ~line 312) spawns a `sleep 30` child under a 1-second deadline and asserts the whole affair lands inside a 3-second wall-clock window measured from the test process. Under parallel `cargo test --workspace` load that window blows on scheduler pressure alone: the test failed three separate gate runs during the 0.4.4 rc train while the kill path was correct every time, and the humans watching CI learned to retry once. A retry habit is a hole a real regression walks through. Rework the assertion so it fails only when the bounded runner is actually broken — candidates (research decides): assert the child's observed lifetime instead of the test's wall clock, widen the bound with a written rationale tying it to worst-case load, or isolate the test from parallel pressure. The negative fixture matters as much as the fix: a kill path that stops enforcing the deadline must still turn the test red.

_Advances: the workspace gate stops training people to distrust it — a red gate means broken code again, nothing else._

## Acceptance Criteria

- [ ] Twenty consecutive full-parallel `cargo test --workspace` runs pass with no bounded-runner failure (loop them; record the tally in progress notes).
- [ ] A deliberately broken kill path (deadline not enforced) still fails the test — demonstrate the mutation and its red result in progress notes, then revert it.
- [ ] The test carries a short comment explaining why its bound is now load-immune; no retry/sleep-and-hope constructs added (N2).
- [ ] No production change to the triage runner unless research shows the runner itself contributes to the timing spread — if it does, name the evidence.
