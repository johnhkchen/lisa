## Context

Detect the client instead of demanding it. Today an unconfigured `[agent]` defaults to Claude unconditionally, so a Codex-only machine fails doctor with a missing-claude remedy for a tool the user never chose. Resolve an unconfigured client by PATH detection (crates/lisa-cli/src/detect.rs has the pattern; wire into config resolution in config.rs and the surfaces in doctor.rs / loop startup): only `codex` present → Codex; only `claude` → Claude; both → Claude, the stated default; neither → doctor's existing install remedy unchanged. Whatever is decided is announced in one sentence on doctor and at loop start ("Driving Codex — it's the agent installed here." / "Driving Claude — both agents are installed; claude is the default."). Explicit `[agent] client` config and the `--client` flag override detection exactly as today. Detection reads PATH presence only — no version probes, no account state, no network. N1 holds: this picks a provider; it changes nothing about how either provider is driven.

_Advances: a machine with exactly one agent installed runs Lisa with zero client configuration, and the operator is told which agent is driving in plain words at the moment it matters._

## Acceptance Criteria

- [ ] Fixture tests with stub binaries on a controlled PATH: codex-only → Codex resolved, doctor green with the announcement line; claude-only → Claude; both → Claude with the both-installed line; neither → existing remedy byte-unchanged; explicit config and --client each beat detection.
- [ ] The announcement strings are pinned and brand-voiced; detection results appear in doctor and loop startup only (no new persistent state); provider adapters untouched (diff scope asserted by the include list).
