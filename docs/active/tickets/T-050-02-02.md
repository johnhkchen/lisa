## Context

A knob without a plain description becomes a CI failure. T-050-02-01 centralizes per-key descriptions in one in-code table; this ticket makes that table the single source for every operator-facing rendering of configuration: the `.lisa.toml` stubs (already wired) and the README configuration table. Mechanism to match the codebase's existing pattern: the bundled-workflow byte-sync test (crates/lisa-cli/src/templates.rs) proves docs and embedded copies cannot drift — do the same for the config table, either by generating the README table section from the table (with a sync test comparing the rendered block byte-for-byte against README.md) or by a test that parses the README table and asserts one row per key with matching default and description. Result: adding a config key without writing its kitchen-table description — or without updating the README — fails the build, not the review. The proliferation complaint becomes structurally impossible to repeat silently.

_Advances: every configuration knob ships described in plain words in both places an operator looks, enforced by the build — the flag thicket cannot regrow unnoticed._

## Acceptance Criteria

- [ ] A sync test binds the README configuration table to the description table: any parsed config key missing from the README, any default mismatch, or any missing description fails the test; the current full key set passes.
- [ ] Adding a fake key in a test (or an equivalent negative fixture) demonstrates the failure mode with an error message naming the missing description; README table regenerated/verified for all current keys including guards/triage.
