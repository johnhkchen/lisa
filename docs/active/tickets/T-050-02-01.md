## Context

Old projects learn about new knobs. Re-running `lisa init` on an existing project today upserts only `[scheduling]` keys — a 0.4.3-era `.lisa.toml` never gains `[agent]`, `[guards]`, or `[triage]`, so every knob shipped since is invisible to existing boards (the memorized field gap: re-init never adds the missing `[agent]` section; confirmed again by the 0.4.4 release audit for guards/triage). Extend init's TOML upsert (crates/lisa-cli/src/init.rs) to append missing sections as **commented stubs**: section header, each key commented out at its default, one plain-English comment line per key saying what it does ("# How finished work is sealed. auto picks the strongest your project supports."). Discipline unchanged: existing values, comments, and ordering preserved in place; only genuinely absent sections appended; a fully current file is a no-op; nothing is ever uncommented or re-valued. The stub set derives from the same description source T-050-02-02 formalizes — write stubs against a single in-code table now, so 02-02 only has to wire the README to it.

_Advances: a project initialized in any Lisa version stays current with every knob that exists — discoverability by re-init, not by release notes; the memorized upsert gap closes._

## Acceptance Criteria

- [ ] Fixture tests: a dirs+scheduling-only `.lisa.toml` re-inits to gain [agent]/[guards]/[triage] as commented stubs with prior bytes preserved in place; a current file no-ops (byte-identical); customized values and user comments survive; stubs never change effective config (parse before == parse after).
- [ ] The stub text lives in one table keyed by config key; a test enumerates parsed config keys and fails if any lacks a table entry; stub comments pass the brand-voice string checks.
