## Context

After staging the ticket-owned paths into an alternate index, the transaction checks what landed
(`crates/lisa-cli/src/commit_transaction.rs` ~749–758):

```rust
let committed_paths = staged_paths(repo, Some(alternate_index))?;
if committed_paths.is_empty() {
    return Err(CommitTransactionError::new(format!(
        "ticket {} has no changes in the requested include paths",
        request.ticket_id
    )));
}
```

An empty diff is treated as a hard error. But there is a case where an empty diff is the
*correct* outcome: the commit this transaction is trying to make **has already been made**. That
is not a failure. That is E-041's own promise — "replay converges on the existing commit rather
than duplicating it" — arriving at the convergence and being told it does not count.

This is what closes the livelock. Once a ticket's work is committed, every future completion
attempt stages nothing, errors here, and gets written back as a `block`. The loop re-attempts
`MarkDoneKey` on the next start and repeats it forever, because **the condition it retries on is
the condition its own earlier success created**. In the field run this consumed an afternoon and
ended in the operator archiving the ticket to get it out of Lisa's sight.

Recognise convergence, and only convergence. **Emptiness is not the evidence — the completion
key is.** A commit already at HEAD carrying this ticket's `Lisa-Completion-Key` for this
correlation is proof the seal happened; an empty diff with no such commit is a real failure and
must stay one. Getting this backwards would trade a livelock for a lie, which is the worse
trade (N3, P2).

Note also the ordinary-index overlap check immediately below (~762–773). Convergence must be
decided without weakening it: a repository whose ordinary index holds these paths is a different
situation again and still refuses.

One field detail worth designing against: the operator's escape attempts used `--ticket-file`
alone, which is not an include path — only `--work-dir` contents are staged. That is defensible,
but it means the failure message names "include paths" while the operator is looking at a
modified ticket file and concluding the message is wrong. If the message can say which paths it
actually staged, it should.

_Advances: P1 — replay converges on the existing commit instead of erroring on it, which is what
idempotency was supposed to mean in both directions._

## Acceptance Criteria

- [ ] An empty include-path diff is a **success** when a commit carrying this ticket's completion
      key for this correlation is already reachable from HEAD. It returns that commit's id, the
      same as a fresh seal would.
- [ ] An empty include-path diff with **no** such commit still fails, with the existing error.
      A test asserts both directions — this is the ticket's negative fixture and a naive "empty
      means done" implementation fails it.
- [ ] The ordinary-index overlap check is not weakened: staged-in-the-ordinary-index still
      refuses, convergent or not, with its own message.
- [ ] Running a completion twice with identical arguments produces exactly one commit and two
      successes, with the second reporting the first's id.
- [ ] The refusal message names the paths that were actually staged, so an operator can see why
      a modified file they are looking at did not count.
- [ ] Built on T-055-01-01's concurrency fixture: after four concurrent completions, replaying
      any one of them converges rather than erroring.
- [ ] `just check` green (fmt, clippy, WASM check, workspace tests).
