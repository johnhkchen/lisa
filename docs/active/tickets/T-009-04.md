## LLM-Driven Validate Loop

### Problem

After `lisa init`, the project isn't ready yet — the LLM needs to write
tickets, tune CLAUDE.md, verify the rdspi-workflow path, etc. Today
`lisa validate` reports errors in a human-readable format, but an LLM
running it iteratively (like `cargo check` → fix → `cargo check` → fix)
needs structured, actionable output.

The goal: a user runs `lisa init`, then tells an LLM "run `lisa validate`
and fix everything it reports until it passes." The LLM should be able to
parse validate's output, understand what to fix, make the fix, and re-run
until clean.

### Design

`lisa validate` should work like a compiler:

1. **Exit code 0** = all checks pass, ready for `lisa loop`
2. **Exit code 1** = errors found, not ready
3. **Structured output** — each error on its own line with:
   - File path (so the LLM knows what to edit)
   - Error category (so the LLM knows what kind of fix)
   - Specific message (so the LLM knows what's wrong)

Example output:
```
docs/active/tickets/T-001.md: frontmatter: missing required field 'phase'
docs/active/tickets/T-002.md: dependency: depends_on references unknown ticket 'T-999'
docs/active/tickets/T-003.md: frontmatter: invalid type 'ticket', expected one of: task, bug, feature, spike, chore
CLAUDE.md: missing reference to rdspi-workflow.md
.claude/settings.local.json: missing idle_prompt hook configuration
.lisa/hooks/on-idle.sh: not found or not executable
docs/active/tickets/: no tickets with phase 'ready' — nothing will run

7 errors found. Fix and re-run `lisa validate`.
```

When clean:
```
All checks passed. 4 tickets, 2 ready, DAG valid. Run `lisa loop` to start.
```

### Requirements

1. **Machine-parseable error format** — `{path}: {category}: {message}`
   one per line. No decorative output, no color codes when stdout is not
   a TTY (or with `--no-color` flag).

2. **Actionable categories**:
   - `frontmatter` — missing/invalid fields in ticket YAML
   - `dependency` — broken depends_on references, cycles
   - `structure` — missing directories, files, or permissions
   - `config` — CLAUDE.md issues, workflow path, hook setup
   - `readiness` — no ready tickets, all tickets done, etc.

3. **Exit code** — 0 for pass, 1 for errors. LLM checks exit code to
   know when to stop.

4. **Summary line** — final line with count and next action, whether
   "fix and re-run" or "ready to loop".

5. **Existing checks preserved** — all current validate checks continue
   to work; this is an output format improvement, not a logic rewrite.

### Acceptance Criteria

- `lisa validate` exits 0 when project is ready, 1 when errors exist
- Each error includes file path and category
- An LLM can parse the output and fix issues without human guidance
- Running `lisa validate` iteratively converges to exit code 0
- `cargo test --workspace` passes
