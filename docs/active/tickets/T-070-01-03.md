## Context

**Read `S-070-01` first.** That story is about recovery advice pointing at
things that are not there. This is the same failure one level up: the advice a
**review disposition** hands an operator.

`T-068-01-03`'s disposition, `remedy_owner: operator`, step 3 of 6:

```
"Prove the way back, on the mini: lisa upgrade --tag v0.4.4"
```

Measured on the dev desk, 2026-08-15 06:52:

```
$ lisa upgrade --help
error: unrecognized subcommand 'upgrade'
  tip: a similar subcommand exists: 'setup-guide'

$ lisa --version
lisa 0.5.0-rc.2
```

`lisa --help` lists thirteen subcommands and `upgrade` is not among them.
Neither is `nightly`, which an **earlier** version of the same disposition asked
for four times:

```
"lisa nightly install --project <that board> --alert '<the command that reaches you>'"
"lisa nightly run"
"lisa nightly status --json > docs/knowledge/mac-mini-nightly-record.json"
```

So this has happened twice on one ticket, with two different invented verbs.

## Why it costs more than a typo

**The operator is the one party who cannot check the source.** Every other
remedy on this board is written for an agent that can read the code beside it. A
disposition with `remedy_owner: operator` is the one output that leaves the
repository, and it is the one with no compiler behind it.

It also fails in the direction that wastes the most time. `unrecognized
subcommand` reads as *my install is wrong* — the operator goes and checks their
PATH, their version, their Homebrew — when the truth is that the command was
never real. On this desk that reading was one keystroke from being acted on: the
laptop genuinely does have two lisas shadowing each other, so *my install is
wrong* would have looked confirmed.

## Acceptance Criteria

- **A remedy step that names a `lisa` subcommand is checked against the CLI
  before the disposition is written.** The binary is right there and `lisa
  --help` is one call; whatever writes the disposition can afford it.
- **A step that cannot be checked says so.** Steps legitimately name `brew`,
  `ssh`, `rm` and things on other machines — the ask is not that every command
  be verified, it is that a **`lisa`** verb is never invented.
- **The failure is caught where it is written, not where it is run.** An
  operator hitting `unrecognized subcommand` is the last place this should
  surface.
- **Existing dispositions on the board are swept once.** `T-068-01-03` is the
  known one; say whether it is the only one.
- **`lisa upgrade` is either built or stopped being asked for.** Two dispositions
  have now assumed a way to move between versions that this CLI does not have,
  which is worth reading as a real gap rather than only a mistake — **the fleet
  has no supported way back**, and `T-068-01-03` is blocked on rehearsing exactly
  that. Say which it is.
- Reproduce it: write a disposition step naming a subcommand that does not
  exist, and have something object before an operator does.

## Notes

- **Found by reading the brief out loud before the operator did.** The step had
  already been copied into an inbox brief telling them to run it — so the wrong
  command had propagated one document further than the ticket, which is how these
  reach a person.
- Worth deciding in review: whether the check belongs to whatever writes
  dispositions, or to a lint over `docs/active/work/*/review-disposition.json`
  that runs with the rest of the suite. The second catches the ones already
  written.
- The dev desk that found this runs `0.5.0-rc.2` from `~/.local/bin`, shadowing a
  Homebrew `lisa` on `0.4.4`, while the Mac mini runs `0.5.0`. **Three versions
  across two machines**, and the operator's own laptop is the one behind. Not
  this ticket, and it is why `unrecognized subcommand` was ambiguous enough to
  need checking twice.
