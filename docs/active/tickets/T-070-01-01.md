## Context

**Read `S-070-01` first.** This is the deadlock in it.

A scheduler recorded `zellij_pid 15340`. That process was gone. The board had
`T-004-01` ready and nothing running, and lisa would not let anything start:

```
$ lisa release-seats --release
Nothing to release: a scheduler is holding these seats. renderer-3
(renderer-3-49ded6ab) is stamping this board …
  stop it with: zellij kill-session renderer-3

$ zellij kill-session renderer-3
(the session does not exist)

$ lisa schedulers --stop renderer-3-49ded6ab
Error: `zellij kill-session renderer-3` exited exit status: 1
Nothing was stopped and nothing was changed.
```

**The remedy lisa prints and the remedy lisa runs are the same command, and it
is a command that cannot succeed** once the session is gone. `--stop` is
implemented as the sentence the error message tells you to type, so there is no
second thing to try.

The board was recovered by moving `.lisa/schedulers/<id>.alive` and
`.lisa/scheduler.alive` aside by hand.

## lisa already has the fact it needs

`.lisa/schedulers/renderer-3-49ded6ab.alive`:

```json
{"scheduler_id":"renderer-3-49ded6ab","session_name":"renderer-3",
 "zellij_pid":15340,"started_at":1786768820,"stamped_at":1786771390,
 "poll_interval_secs":5}
```

Liveness is decided from `stamped_at`. The pid is written down and never asked
about. **A stamp says a process was alive when it wrote; a pid is a question you
can ask now.**

## The stamp renews itself on the way out

`stamped_at` was 2 minutes old while the process had been dead for 45. A later
`lisa loop` that **refused to start** still touched the stamp, so every attempt
to recover the board pushed the lock further out. That is the part that turns a
wrong answer into a deadlock: retrying makes it worse, which is the opposite of
what an operator expects.

## Acceptance Criteria

- **A scheduler whose zellij server is gone is reported as not running**, by
  checking the pid it already recorded rather than only the stamp's age. Say what
  happens when the pid exists but belongs to something else now — a reused pid
  must not read as alive.
- **`lisa schedulers --stop <id>` succeeds when the session is already gone.**
  Ending a scheduler whose session has ended is the ordinary case after a crash,
  not an error. It should say what it found and what it cleaned.
- **A command that refuses does not renew the stamp.** A `lisa loop` that
  declines to start must leave the lock exactly as it found it.
- **The remedy printed is a remedy that can work.** Where `zellij kill-session`
  is genuinely the right advice, keep it; where the session is already gone, the
  message must name the command that actually applies.
- **A live run is still protected.** The guard's own distinction — *"a stamping
  scheduler is a process that exists, not a ticket being worked"* — is right and
  must survive this. Nothing here may make it easier to release seats out from
  under a working pane.
- Reproduce it: start a loop, `zellij kill-session` it, then recover the board
  using only documented commands.

## Notes

- **Found on a machine nobody was sitting at**, which is where it costs the most:
  the board sat with a ready ticket for 45 minutes and every tool that looked at
  it said something was running.
- `.lisa/schedulers/` had four `.alive` records, three of them from dead runs
  hours old. Worth deciding in review whether a record for a scheduler that is
  provably gone should be retired automatically, or whether keeping them is
  deliberate for the ledger.
- `lisa release-seats` and `lisa reset-ticket` use different staleness windows.
  That is not this ticket, but a fix here should not quietly make them a third
  and a fourth.
