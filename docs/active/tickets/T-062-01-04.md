## Context

**Read `S-062-01` first.** Same subject — a running loop and its panes — and
this one stops work rather than looking untidy.

On 2026-08-11 three tickets sat at `phase: implement` with no work, no
provenance record, and an attempt counter climbing. The dashboard said:

```
⚠ ATTENTION NEEDED
✗ FAILED T-062-01-02  Session failed
✗ FAILED T-062-01-01  Session failed
✗ FAILED T-062-01-02  Session reported an error (pane 1)
```

`T-062-01-03` reached **attempt 4**. Every attempt produced one file — the
assignment — and nothing else.

### The cause, found after a wrong first answer

**The agent sessions inherited `CLAUDE_CODE_CHILD_SESSION=1`.** The loop had been
started with `wezterm cli spawn` from inside a Claude Code session, and
`wezterm cli spawn` hands the *client's* environment to the new pane — measured:
five `CLAUDE_CODE_*` variables arrive in a pane spawned that way. Every agent
underneath was then treated as a nested child. The pane said so:

```
⚠ Transcript saving is off — inherited CLAUDE_CODE_CHILD_SESSION marker
```

Which is also why the failures were so hard to read: **the sessions that failed
wrote no transcripts.**

Restarted through `env -u` stripping those six variables, the same three tickets
picked up and ran with no warning and no failure.

**That is the cause and it came from outside lisa.** What follows is what lisa
did with it, and is still worth fixing — a wedged pane and a retry that cannot
work should not look like this from the inside.

### What the agent in the pane said

From its transcript:

> *"Shell-ready signal written for pane-2 (`T-062-01-03`, attempt 3). Waiting on
> the scheduler to send the ticket prompt."*

and then, when handed the next attempt's launcher:

> *"Not runnable from inside this session. It launches an interactive `claude`
> TUI — attempt 4 of `T-062-01-03` in this same pane. If I run it through Bash it
> either hangs with no terminal or nests a Claude inside this one."*

**The pane's shell is what runs `.lisa-launch-N.sh`, and the shell only gets the
pane back when the agent exits.** The agent had not exited — it believed it was
waiting for a prompt — so the launcher was offered to the wrong process, one
whose tool has no controlling terminal. It correctly refused, the session was
marked failed, and the scheduler tried again into the same wedged pane.

A deadlock: the scheduler thinks the seat is free, the agent thinks it is waiting,
and each retry costs a full session's tokens.

### What it took to clear

Nothing in `lisa` did it. The operator's agent had to:

1. `pkill` the loop
2. `zellij kill-session` the wedged session
3. hand-edit `phase: implement` back to `phase: ready` in three ticket files —
   the one field every assignment prompt tells agents never to touch
4. restart the loop

`lisa clean` does not cover it, `lisa unblock` is for a different state, and
`lisa doctor` checks tools. **There is no supported way out of this**, and the
third step is the operator doing by hand exactly what the system forbids.

## Acceptance Criteria

- **An agent is not launched into an environment that will break it.** The
  marker is readable before the session starts. Refusing, stripping, or warning
  are all defensible; silently starting a session that cannot save a transcript
  is not.
- A pane whose agent has not released it does not receive the next attempt.
  Reproduce the state — an agent session that stays up past its assignment — and
  show the scheduler either waiting or choosing a different seat.
- **A retry that cannot possibly work does not happen.** Four attempts produced
  four assignment files and nothing else; say what distinguishes a retry worth
  making from a re-offer into the same wedge.
- The dashboard says what is actually wrong. *"Session failed"* three times sent
  the operator to the transcripts; the pane being occupied is a fact lisa knows.
- **A supported way out exists**, and it does not involve editing `phase:` by
  hand. Whether that is `lisa clean`, a new word, or a scheduler that recovers on
  its own, an operator must not have to do the thing every assignment forbids.
- Attempt counters that climbed on wedged sessions are accounted for. Attempt 4
  of a ticket that never started once is a misleading record.
- Say whether the shell-ready handshake is the right shape at all. The agent
  wrote a shell-ready signal and then waited for a prompt that the scheduler
  believed it had already sent — if both sides can hold that belief at once, the
  protocol has a gap wider than this bug.

## Notes

- Costly in a way that is easy to miss: each failed attempt is a full agent
  session, so a wedge that retries is spend with no output. Three tickets and a
  counter at four.
- Related and not the same as `S-060-01`, which is a run that *died* leaving
  leases behind. This is a run very much alive, retrying into a seat that cannot
  take work.
- The three tickets recovered and ran normally once the marker was stripped, so
  nothing here is about the tickets themselves.
- **The first diagnosis of this bug was wrong** and is left visible above rather
  than rewritten: the wedged handshake was real and was a symptom. Anyone
  reading this should treat the acceptance criteria as being about how a poisoned
  session presents, not about what poisoned it.
- The consuming desk fixed its side — `~/ergo/bin/station` now starts everything
  through `env -u`. Whether lisa should also refuse to launch an agent under a
  marker that will break it is a fair question and is the first criterion below.
