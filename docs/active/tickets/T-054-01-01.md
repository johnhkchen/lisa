## Context

`render_dag` computes a status color for every node — RDY cyan, WRK green, REV bright-yellow, BLK red, DON bright-green (crates/lisa-plugin/src/ui.rs ~816–828) — and then the post-processing loop destructures the pair as `(phase_color, _status_color)` and never touches the second element (~833): only the ticket id gets painted (phase color), while the status token renders in whatever the terminal had loaded. The field screenshot's wall of same-weight text is this bug wearing 49 tickets. Paint the token: apply the already-computed status color to the `BLK`/`RDY`/`WRK`/`REV` text in the post-processed line (a `DON` token can never appear on one — Done tickets are filtered before nodes are built, ~752 — so the Done arm is covered at the color map, not on rendered output). Small on purpose — this is the legibility budget T-054-01-02 spends when it drops the token and moves status entirely into color, so it lands first and alone.

_Advances: blocked-versus-working becomes a color scan instead of a read — and the condensed mode about to land inherits a status channel that actually shows (P4)._

## Acceptance Criteria

- [ ] Status tokens render wrapped in their mapped color codes for the four statuses that can appear on rendered lines — RDY, WRK, REV, BLK (unit test on post-processed DAG lines, one per status); the Done arm is asserted at the color-map level, since Done tickets never reach the renderer (~752).
- [ ] Phase coloring of the ticket id is unchanged — existing rendering tests stay green untouched, or are updated only for the new token codes with a note saying so.
- [ ] No layout drift: raw (pre-color) line content is byte-identical to before — this ticket changes color only (N4).
- [ ] `just check` green (fmt, clippy, WASM check, workspace tests).
