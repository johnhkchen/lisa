## Context

Stable-0.4.4 blocker from the release audit, reproduced with the built binary: a ticket that completes with a note, reopens, and completes with a second note before the operator's batched review — exactly the deferred-reading pattern Notes for you encourages — makes `lisa notes ack <ticket-id>` exit 1 with "multiple active notes for {ticket_id}; acknowledgment requires an exact generation", and no command accepts a generation. The only escape is hand-editing provenance. Replace the dead-end with behavior (crates/lisa-core/src/notes.rs, crates/lisa-cli/src/notes.rs, main.rs): bare `ack` acknowledges the **oldest** active note and says what it did in plain words — "Marked the oldest note read — 1 more remains." — so repeating the command drains the queue naturally; a new `--generation <n>` flag targets exactly (listed by `lisa notes`, which gains the generation label on multi-note tickets); the jargon error message is deleted. Every ack writes its provenance row as today; acking with nothing to ack says "Nothing to read for {ticket_id}." per the no-blank-surfaces rule.

_Advances: the queue built for reading on the operator's schedule can always be cleared on the operator's schedule — no state it creates requires hand-editing a ledger to leave._

## Acceptance Criteria

- [ ] Fixture tests with the built binary: two active notes → bare ack clears the oldest with the remaining-count line, second ack clears the last, provenance rows for each; `--generation` acks exactly and rejects an unknown generation with a plain message naming the listed ones; single-note and empty cases keep today's behavior plus the plain nothing-to-ack line.
- [ ] `lisa notes` labels generations whenever a ticket holds more than one active note (string-pinned); the old multi-note error string is gone from the codebase; durable clearing across fresh processes asserted per the existing notes_ux pattern.
