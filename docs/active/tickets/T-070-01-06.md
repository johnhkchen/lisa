## Context

**Read `S-070-01` first.** That story is about runs that could not be put down.
This is smaller and the same family: a test that says something failed when what
actually happened was that the machine was busy.

`triage_agent::tests::bounded_runner_returns_valid_proposal_and_surfaces_failure`
failed once on 2026-08-15 while four `lisa loop` boards and a `cargo build
--release` were running on the same laptop:

```
test result: FAILED. 787 passed; 1 failed
panicked at crates/lisa-cli/src/triage_agent.rs:302
```

It passed on every re-run, and on a second full-suite run minutes later. Nothing
in today's commits touches `triage_agent.rs` — `git log --since` on that file is
empty.

## Why it is a flake and not a bug in the code under test

The test writes an executable script, runs it through the bounded runner, and
asserts on the output. The bound is **2**:

```rust
let output = run_triage_agent(&args(dir.path().to_path_buf(), agent, 2)).unwrap();
```

A time or attempt bound of 2, against a freshly-spawned subprocess, on a machine
with four agent panes and a release build competing for it. The thing being
measured is not the runner's logic; it is whether a process started fast enough.

## Why it is worth fixing rather than shrugging at

**It fails in the direction that wastes the most time.** A red suite during a
release cut is a stop-everything signal, and this one stopped a release cut for
long enough to check whether the day's work had broken something. The answer was
no, and getting to that answer took three runs and a `git log`.

It will also get worse. The desk now runs four boards at once by design, and
`S-072-01` is about running them harder.

## Acceptance Criteria

- **The test does not depend on how busy the machine is.** Say how — a larger
  bound, a fake clock, a stubbed runner, or asserting on the runner's decision
  rather than on a subprocess finishing.
- **If a bound is what is being tested, test it deterministically.** A bound that
  is real is worth a test that always exercises it, not one that exercises it
  when the CPU is free.
- **A slow machine still fails loudly if the runner is genuinely broken.**
  Whatever replaces the timing must not turn a real regression into a pass.
- **The suite is green three times running on a loaded machine.** Reproduce the
  load: start the boards, then run the suite.
- Say whether any other test in the suite has the same shape. This one was found
  by accident.

## Notes

- Found during the `v0.5.1-rc.1` cut, by a gate that required a green suite. The
  gate did its job; the test wasted the gate's credibility.
- Worth deciding in review whether the suite should refuse to run at all on a
  machine with live loops, rather than running and being unreliable. That is the
  honest version of "not a good time to measure this".
