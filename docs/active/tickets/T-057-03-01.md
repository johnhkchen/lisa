## Context

> **Closed 2026-08-09 against `v0.5.0-rc.2`, not the `rc.1` this ticket names.**
> rc.1 was prepared here and never published: a 0.4.4 field run on
> `tabular-recipes` found that Lisa never delivered a ticket's prompt to a
> recycled pane, so the release was re-cut with that fix (`f508031`) instead of
> shipped as prepared. rc.2 is rc.1 plus that fix, and the preparation proven
> here carried forward rather than being redone. Every criterion below holds
> with `0.5.0-rc.2` substituted, except the publication boundary — rc.2 *was*
> published, after John authorized it explicitly. The account is in
> `docs/active/work/T-057-03-01/review.md`; the cut record is
> `docs/knowledge/release-0.5.0-rc.2-cut-record.md`. The criteria are left
> as written, naming rc.1, because they are the historical record of what was
> asked for — not a claim about what shipped.

Cut `0.5.0-rc.1`, publish it to the Homebrew tap, and update the `lisa` on this machine.

**Read `docs/knowledge/release-checklist.md` first and follow it.** It is the maintainer runbook,
557 lines, version-parameterized from a block at the top (currently `VERSION=0.4.4`,
`PRIOR_STABLE=v0.4.3`, plus cumulative ancestry gates). Nothing below replaces it; this is the
ticket-shaped account of a release-candidate pass through it, and where the two disagree the
checklist wins.

**The mechanics that already exist and are not being changed.** `just release` (`justfile` ~20–36)
runs the gates, reads the version from Cargo.toml, refuses a tag that already exists, tags
`v${version}`, and pushes main plus the tag; cargo-dist CI builds and publishes.
`dist-workspace.toml` publishes prereleases to `johnhkchen/homebrew-lisa` deliberately
(`publish-prereleases = true`, ~33–36) while apt publishing skips them. Four targets, `.tar.gz`
archives, `install-path = "~/.local/bin"`. If any of this turns out to be broken, that is a new
ticket with the failure in hand — do not repair the release machinery inside the release.

**Preparation — everything an agent can do.**

1. Set the workspace version to `0.5.0-rc.1` in the root `Cargo.toml` (the three crates inherit via
   `version.workspace = true`). Confirm `config::LISA_VERSION` follows and that a project written
   by 0.4.4 is still judged stale by `version_is_stale` against it — S-057-02's entire upgrade path
   hangs off that comparison, and a prerelease suffix is exactly the kind of string that breaks a
   naive version compare. Test it rather than reasoning about it.
2. Re-parameterize the checklist's version block for this cut and append the gate commit for this
   line. The checklist says gates are cumulative lineage proof — append, never delete.
3. Write the cut record, following `docs/knowledge/release-0.4.4-cut-record.md` as the shape. It
   is the first document that will state, in one place, what 0.5.0 changes for someone upgrading:
   four phases collapsed to one, `CLAUDE.md`/`AGENTS.md` no longer scaffolded,
   `rdspi-workflow.md` renamed, `auto_advance` gone, `lisa clean` added — and the accepted
   regression S-057-01 named, that journal-sealed projects no longer resume a dead session's work.
   Write it for someone who ran 0.4.4 yesterday.
4. Confirm the channel baseline live rather than assuming it — the checklist's "Channel baseline"
   section gives the exact `gh api` calls. Stop if `v0.5.0-rc.1` already exists.
5. `just check` green.

**Then stop.** Only John authorizes publication; the checklist states this in its opening lines,
and preparing a release is not authorization. Do not run `just release`, do not tag, do not push,
do not dispatch a workflow. Write `review-disposition.json` as a block with
`remedy_owner: "operator"` and an `ask` naming the action — the field example in the workflow
document is the model: name the command, say Lisa will notice once it is live, keep the version
arithmetic in `reason` and `steps`.

**The check is the interesting part of this ticket.** It has to verify a published reality that
does not exist when it is written, from a machine that cannot make it exist. Write it against the
contract: project root, read-only, exit 0 only when the tap actually serves `0.5.0-rc.1`. Give it
a `check_timeout_secs` sized for a network round trip and no more — the operator runs it *after*
CI finishes, so it is verifying a settled fact, not waiting for one. A check that tries to wait out
a cargo-dist build will hit the 1800-second ceiling and refuse, and `lisa check-disposition` will
tell you so while you are still here to fix it. Run `lisa check-disposition` before finishing.

**Updating this machine is part of the ticket, not a footnote.** `lisa` here is
`/Users/johnchen/.local/bin/lisa` at `0.4.4` — the shell installer's path, not Homebrew's. So
`brew upgrade lisa` may install a second `lisa` that PATH does not reach, and "the tap has
0.5.0-rc.1" would be true while `lisa --version` still says `0.4.4`. Determine which installation
actually owns the binary on PATH and write the operator's steps for *that* one. The step that
matters to the person reading it is the one that makes `lisa --version` change.

_Advances: P5 — field evidence becomes regression evidence: the 0.5.0 claim is that agents do
better work with less scaffolding, and that claim only becomes evidence once a released binary runs
a real board. And P2 — the ticket's own state stays honest: it blocks because a person must act,
rather than reporting success at the boundary it cannot cross._
