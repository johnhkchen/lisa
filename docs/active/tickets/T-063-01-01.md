## Context

**Read `S-063-01` first.** Three schedulers ran on this board at once for
seventeen hours and nothing on the desk could say so.

The mechanism is one line long: `lisa loop` starts a zellij client, the plugin
lives in the zellij server, and the server outlives the client. Every ordinary
way of stopping a loop — closing the pane, closing the window, killing the `lisa
loop` process — stops the client and leaves the scheduler running.

`ps aux | grep 'lisa loop'` returned `0` while `.lisa/scheduler.alive` was being
stamped every five seconds by three different processes.

### The cost, measured

- **10 of 12 agent sessions** were given the shell-readiness probe as their first
  prompt instead of an assignment, and died in ~60s having done nothing. Those
  transcripts are 57–165 KB; the two that got a real assignment are 1.0–1.3 MB.
- **Three finished tickets never advanced.** `T-062-01-01`, `-03`, `-04` wrote
  passing dispositions and committed six commits between 12:19 and 12:26, and
  were still at `phase: implement` at 12:47.
- **Both supported recoveries were locked out** — `release-seats` and
  `reset-ticket` each refused, citing a scheduler heartbeat that three processes
  were keeping fresh.

### Why the existing safeguards did not catch it

`scheduler.alive` answers *is a scheduler running* with a boolean. The question
that matters here is *how many, and which*. One file with N writers cannot tell
them apart, and the two commands built to rescue a stuck board both key on it.

## Acceptance Criteria

- **A second scheduler on the same board is detected and says so.** Whether it
  refuses to start, warns, or takes over, starting a second `lisa loop` on a board
  that already has a live scheduler must not silently produce two.
- **`lisa status` (or `doctor`) can name the schedulers on this board** — enough
  identity that an operator can go and stop the right one. Today that takes `lsof`
  across every zellij server on the machine.
- **A supported way to stop a detached scheduler exists.** `kill <pid>` on the
  zellij server did not work; only `zellij kill-session <name>` did, and finding
  the name is the hard part.
- **`release-seats` and `reset-ticket` distinguish "a run is working" from "a
  scheduler is stamping".** Both refused correctly and both were wrong about the
  world. Say what evidence should gate them instead of a shared heartbeat file.
- **Signal consumption is attributable.** With one reader, a drained signal is
  handled; with three, it may have been eaten. Whether that means per-scheduler
  signal claims, an owner id in the lease, or something else, a signal that
  vanished into another scheduler must be distinguishable from one that was acted
  on.
- Reproduce it before fixing it: two schedulers on one board, and a
  `pane-N.started` that the live one never sees.

## Notes

- **Not `S-060-01`.** That is a run that *died* leaving leases nothing will clean.
  This is the opposite failure — a run very much alive, invisible, and holding the
  board against every recovery lisa offers.
- The shell probe those ten sessions received is itself already known-bad against
  a live TUI (`lib.rs:4776`), and there is a test for the residency leg
  (`test_unobserved_startup_on_a_resident_pane_re_exits_instead_of_probing`). The
  panes here produced no residency evidence, so they took the old branch. Worth
  deciding whether the probe should exist at all when the client is `claude`.
- The operator had already quit every loop they could see before these three were
  found. Any fix whose recovery step is "quit the loop" does not address this.
- Two of the three schedulers dated from the previous evening, which means this
  had been degrading the board across a full overnight run and the whole of the
  following morning before anyone could name it.
