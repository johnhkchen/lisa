## Context

T-056-01-02 lets the check see the project. That is not yet enough to unblock T-010-03, because
two more ceilings sit behind the first — and both were only invisible because the run never got
past the missing `dist/`.

1. **Five seconds.** `const CHECK_TIMEOUT: Duration = Duration::from_secs(5);`
   (`crates/lisa-cli/src/unblock.rs` ~22), hardcoded, no per-check override. The recorded check in
   the field case is a 2130-page-view headless-Chrome sweep; the disposition's own `reason` puts
   it at roughly twenty minutes. Fix the cwd alone and the operator's next run reads
   `That didn't work yet — it took longer than 5 seconds.` — a second false gate with the same
   shape as the first.

2. **The tree is read-only and fingerprinted.** The snapshot is chmod'd read-only (~319) and
   compared before and after (~236–239), so any check that writes is `ChangedFiles`. A reviewer's
   natural instinct here — `npm run build && npm run verify:mobile` — is refused, and the refusal
   again says nothing about the remedy.

Neither ceiling is written down anywhere a reviewer would look. `docs/knowledge/rdspi-workflow.md`
~59 asks for "a read-only verification command" and stops. `lisa check-disposition`, which the
review phase is instructed to run before finishing, validates the disposition's *shape* and never
tries the check. So a check that cannot pass is accepted in silence and discovered weeks later, in
the operator's terminal, by the one person who cannot fix it.

And when the same shape lands on a world-owned remedy it is worse: `run_world_rechecks` (~120–129)
matches `Failed | TimedOut | ChangedFiles` and does nothing at all. No message, no count, no
record. A structurally impossible world check parks forever and never says why — which is also
why the ask's promise that "Lisa will pick it up from there" had no mechanism behind it.

Four moves, one theme: make the constraints visible at authoring time instead of at unblock time.

- Raise or parameterise the timeout. A per-check budget with a sane cap is the shape suggested by
  the field case (twenty minutes is a real verification, not an abuse); an arbitrary larger
  constant is not a fix, because the next check will be longer. Whatever bound is chosen, expiry
  still says how long it waited.
- Decide, and state, whether a check may write — and if it may not, say so where checks are
  written, so `build && verify` is rejected by the author rather than by the operator.
- Make the recording path try the check. `lisa check-disposition` (and/or `lisa validate`) runs
  the recorded check under the real execution contract and refuses or warns at record time, while
  the reviewer is still on the ticket. This is the highest-leverage part: it is the difference
  between a bad check costing one review turn and costing an afternoon.
- Make `run_world_rechecks` surface repeated non-pass results instead of discarding them, so a
  world remedy that can never clear becomes visible (N2 — bounded, observable, ending in a named
  actionable state). Automation still does not act on a non-pass; only the silence changes.

_Advances: N2 — recovery is observable and bounded rather than a silent loop. And P5 — the two
latent traps found by the same field run are closed with it, not left to be rediscovered as the
next false gate._

## Acceptance Criteria

- [ ] A check may declare a time budget above the current 5 seconds, bounded by a documented cap.
      A test asserts: a check sleeping past the default budget but inside a declared larger one
      passes; a check exceeding its declared budget times out; a check exceeding the cap is
      rejected when it is recorded, not when it is run.
- [ ] Timeout expiry names the budget it actually waited for, not the literal string
      "5 seconds". Pinned by test at two different budgets.
- [ ] Whether a check may write is decided, implemented, and stated in
      `docs/knowledge/rdspi-workflow.md` alongside the rest of the contract. A test asserts the
      documented behaviour for a writing check.
- [ ] `docs/knowledge/rdspi-workflow.md` ~59 states the execution contract a reviewer is writing
      against: the directory the check runs in, which files are present, whether writes are
      allowed, and the time budget. A test asserts the documented facts match the code (e.g. the
      documented default budget equals the constant).
- [ ] `lisa check-disposition <ticket-id>` runs the recorded check under the real contract and
      reports a check that cannot pass, at record time. A test drives the field case: a
      disposition whose check is unsatisfiable is reported by `check-disposition` with a message
      naming what failed, while a satisfiable one passes unchanged.
- [ ] `run_world_rechecks` no longer discards non-pass results silently: repeated non-passes for
      the same remedy become observable through a durable record naming the remedy and what the
      check reported. A test asserts a world remedy whose check always fails produces that record
      and still is not reopened.
- [ ] End-to-end on the story's fixture: with T-056-01-01 and T-056-01-02 landed, a blocked
      ticket whose check reads a gitignored artifact and takes longer than 5 seconds unblocks
      cleanly under a declared budget.
- [ ] `just check` green (fmt, clippy, WASM check, workspace tests).
