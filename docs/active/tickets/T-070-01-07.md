## Context

**Read `S-070-01` first.** This one stopped a release.

`headless::tests::the_terminal_lisa_opens_has_a_plausible_size` failed on CI for
the `v0.5.1-rc.2` release commit, and Auto Release skipped because of it — so no
tag was cut and the tap fix that commit carried could not publish:

```
left: None
right: Some("  50 200")
test result: FAILED. 787 passed; 1 failed
```

The test, in full:

```rust
let mut command = Command::new("/bin/sh");
command.arg("-c").arg("stty size");
let run = run_on_pty(command).expect("a pty to open");
assert_eq!(
    run.transcript_head().as_deref(),
    Some(format!("  {HEADLESS_ROWS} {HEADLESS_COLS}").as_str())
);
```

It opens a pty, runs `stty size`, and expects `50 200` back. **On CI the
transcript came back empty** — `transcript_head()` was `None`. The pty opened;
nothing was read from it.

It passes here: `788 passed; 0 failed`, and it passed all six release gates on
the same commit minutes earlier. A re-run of the same CI job went green.

## What it is really testing, and what it accidentally tests

The intent is good: *a board with no terminal gets one Lisa opens*, and the
assertion proves the pty carries the size Lisa asked for. That is worth a test.

**What it accidentally tests is whether output arrived before it looked.**
`stty size` writes once and exits; reading the transcript is a race with the
child's write and the pty's flush. On a laptop that race is never lost. On a CI
runner under load it is.

## Acceptance Criteria

- **The test waits for output rather than sampling once**, or reads the size
  from the pty directly rather than from a subprocess's stdout. Say which and
  why.
- **A genuinely wrong size still fails.** Whatever replaces the race must not
  turn a pty configured at the wrong dimensions into a pass — that is the bug
  the test exists to catch.
- **An environment with no pty at all is a skip that says so, not a failure**, if
  such an environment is possible for this suite. Say whether it is.
- **It passes ten times running under load.** Start four `lisa loop` boards and a
  release build, then run it in a loop. That is the condition it failed under.
- Say whether `run_on_pty`'s other callers have the same race, since the helper
  is shared.

## Notes

- **This is the second environment-sensitive test in this suite** and they cost a
  release between them. `T-070-01-06` is the other — `triage_agent`'s bounded
  runner, which failed under load this morning with a bound of 2 against a
  freshly-spawned subprocess. Same family: **both measure whether something
  happened fast enough, while claiming to measure whether it happened at all.**
  Worth fixing together and worth a sentence in `docs/knowledge/` about the
  shape.
- The cost was not the re-run. It was that a red CI on a release commit is a
  stop-everything signal, and the day's real question — *did the tap fix work* —
  waited behind establishing that this failure was noise.
