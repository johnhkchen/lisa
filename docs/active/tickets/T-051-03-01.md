## Context

The provenance row for a completed ticket is written at completion; the usage capture for that ticket's session lands afterward — always, now that finished sessions rest before retirement (the rc.8/rc.9 field legs lost 8/9 and 9/9 captures to exit races; the fix makes captures durable but late). So `tokens_in`/`tokens_out` in `.lisa/provenance.jsonl` are null at write time by construction. Build the late join in the scheduler (which owns the pane×time attempt history the hook process lacks): when a record appears in `.lisa/<client>/captures.jsonl` for a pane and provider session, attribute it to the ticket whose attempt held that pane over the capture window, and append a correction record to the ledger carrying the tokens for that completed ticket — the original row is never mutated. Captures that match no attempt keep quarantining by session id (`.lisa/<client>/quarantine/`); a quarantined capture that later gains attribution evidence drains; one that cannot is terminal and stays countable. Both 0718 leg shapes become fixtures: capture-after-completion (normal), capture-never (columns stay null, never fabricated — zero is not unknown).

_Advances: the ledger's token columns become true instead of guaranteed-null; cost accounting gets a foundation that survives the capture timing the exit-race fix made permanent._

## Acceptance Criteria

- [ ] Fixture: complete a ticket, then land its capture — the ledger view reports that ticket's tokens via an append-only correction record; the original row's bytes are untouched.
- [ ] Fixture: a capture matching no attempt quarantines by session id; a late-attributable quarantined capture drains to a correction record; an unattributable one stays quarantined and countable.
- [ ] Fixture: capture-never leaves columns null — no zeros fabricated, and the gap is visible (count of completed tickets without joined usage) on `lisa status` or the dashboard.
- [ ] Per-ticket token totals surfaced anywhere read from the corrected view, not the raw first-write row.
