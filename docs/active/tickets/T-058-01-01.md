## Context

`ON_HEARTBEAT_HOOK` (`crates/lisa-cli/src/templates.rs` ~222–238) publishes a lease-bearing signal
without checking the identity of the process publishing it:

```sh
if [ -n "$LISA_PANE_ID" ]; then
    marker="$SIGNAL_DIR/pane-$LISA_PANE_ID.lease"
    tmp="$SIGNAL_DIR/pane-$LISA_PANE_ID.heartbeat.tmp.$$"
    if [ -r "$marker" ] && cp "$marker" "$tmp"; then
```

Compare `ON_START_HOOK` (~191–214), which builds `expected` from the caller's own
`LISA_TICKET_ID` / `LISA_ATTEMPT_ID`, compares it to the marker, and exits 0 on mismatch. That
guard is why a resident predecessor cannot forge a successor's *start*. Nothing equivalent guards
the heartbeat. `ON_STOP_HOOK` (~57–85) is not affected: it writes a bare timestamp and carries no
lease, so it is presence-only and there is nothing in it to forge.

**Read `S-058-01` first.** It states the tension this ticket exists to resolve, and that tension is
the whole difficulty — do not fix this by copying the ON_START_HOOK guard into the heartbeat hook
and stopping there.

**What consumes the signal today.** `check_heartbeat_signals` (`crates/lisa-plugin/src/lib.rs`)
does two separable things with one file. It records residency — a process is in this pane — via
`record_provider_residency`, before any authority check, deliberately. Then, if the carried lease
matches the slot's, it treats the heartbeat as *progress*: `bump_pane_activity`, clearing the
attention debounce, and clearing `awaiting_human` so injection into the pane resumes. The second
group is the one a forged heartbeat should never reach, and clearing `awaiting_human` is the
sharpest edge — it is what stops Lisa typing over a live `AskUserQuestion`.

0.5.0-rc.2 already refuses that second group while the seat is in `ResettingStartup`, with a
comment saying why. That containment is scoped to one window and should be reconsidered, not
preserved by reflex, once the signal itself is trustworthy.

**The constraint that rules out the obvious fix.** `DeadlineEvaluator::transitions`
(`crates/lisa-plugin/src/deadline.rs`) holds a pane past the exit grace while `last_provider_signal`
is fresh, and heartbeats are the densest contributor to that timestamp. During a recycle,
`publish_prompt_lease_marker` installs the *successor's* lease before the launch line is typed, so
a predecessor that is still resident has an env that no longer matches the marker. A hook hardened
to require a match would go silent precisely then — and "the old TUI is still sitting there" is the
fact the exit hold exists to notice. Verify this against the code rather than taking it on trust;
if it turns out to be wrong, say so with the trace in hand and the ticket gets simpler.

**The direction, not the design.** Residency and authority are different claims and want different
evidence. A signal that says only *a process ran a tool call in this pane* needs no identity and
cannot be forged into anything, because it asserts nothing about who. A signal that says *attempt N
is making progress* must prove it. Splitting them is one way; an authenticated heartbeat plus an
unauthenticated liveness ping is another spelling of the same idea. Choose deliberately and write
down why. Whatever shape you pick, the exit hold must keep seeing a resident predecessor, and the
progress path must stop believing anyone who cannot name themselves.

**The upgrade path is part of the work, not a follow-up.** Hooks are written into projects by
`lisa init` and only replaced when the on-disk text matches a known prior generation:
`LEGACY_ON_HEARTBEAT_HOOKS` (`templates.rs` ~240) consumed by `init.rs` (~614). A new hook whose
predecessor is not appended to that list will never reach a project that already has the old one —
every existing board keeps the forgeable hook forever and the fix ships to nobody. If the shape
changes such that a *new* signal file appears, decide what happens to projects mid-run when a pane
already holds the old one, and what `lisa doctor` should say.

**Scope boundary.** Do not change the scheduler's residency model or the exit policy; rc.2 shipped
them with tests and they are not what is broken here. Touch `check_heartbeat_signals` only as far
as the new signal shape requires.

_Advances P2 — a lease-bearing signal comes to mean that its writer holds the lease. And P3 —
whatever shape is chosen has to hold for both native clients, since `PostToolUse` and its Codex
counterpart write the same file through the same contract._

## Acceptance Criteria

- [ ] A process running a tool call in a Lisa pane **cannot** publish a signal that the scheduler
      admits as progress for an attempt it does not hold. Asserted by driving the real hook script,
      not by hand-writing the signal file: the repo already shells out to hooks in
      `crates/lisa-cli/tests`, and this claim is about the script's own logic.
- [ ] A **resident predecessor still produces residency evidence** after the successor's lease
      marker has been published — the recycle case in `DeadlineEvaluator::transitions`. Asserted
      with a test that fails if the hardening darkens this leg, because that regression is the
      reason this was not bundled into rc.2.
- [ ] `awaiting_human` is not cleared, and no activity clock moves, on a signal whose writer did
      not prove it holds the current attempt lease.
- [ ] The prior hook generation is appended to `LEGACY_ON_HEARTBEAT_HOOKS`, and a project written
      by 0.5.0-rc.2 is upgraded in place by `lisa init` — verified end to end on a fixture project,
      not by reading the list.
- [ ] `ON_START_HOOK` and `ON_STOP_HOOK` are re-read and either confirmed sound as written or
      brought along; the ticket states which, and why, in `review.md`.
- [ ] The rc.2 `ResettingStartup` containment in `check_heartbeat_signals` is revisited on the
      record: kept with a reason, or removed because the signal is now trustworthy. Not left
      unexamined.
- [ ] `just check` green (fmt, clippy `-D warnings`, WASM check, workspace tests).
- [ ] `review.md` states what a forged signal can still achieve after this change, if anything.
      "Nothing" is an acceptable answer only if it is argued against the hooks as written.
