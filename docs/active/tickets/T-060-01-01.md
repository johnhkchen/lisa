## Context

**Read `S-060-01` first.**

A run that dies without shutting down leaves its pane lease markers in
`.lisa/signals/`. They are the scheduler's record of a placement and the plugin
does not consume them, which is correct while a run is live and wrong once it is
not. `lisa status --json` keeps reporting them in `attempts[]`, and `json-guide`
tells consumers that such an entry is *"Lisa's best answer to 'this seat is
working'"*.

Measured on `screen-design` after a crash at 17:45: four leases, two naming
tickets in `implement` and `review`, every zellij session `EXITED`, no process
holding anything, and `lisa status` reporting `2 in progress`. That state
persisted until the operator ran `lisa loop` by hand, which reassigned the
tickets and overwrote the leases.

### What makes this awkward to fix

A lease that looks abandoned and a lease held by a slow session look identical on
disk. The obvious discriminator — the heartbeat — is consumed by the plugin, so
it is not there to read after the fact. `scheduling.session_timeout_secs` is the
project's own statement of how long a session may run, which makes a lease older
than it a session Lisa would already have ended; whether that is the right test,
and what else corroborates it, is the substance of this ticket.

The cost of being wrong runs both ways. Clearing a live seat could put a second
agent on a ticket someone is working. Keeping a dead one wedges the board and
misleads every consumer of `attempts[]`.

## Acceptance Criteria

- A run that died without shutting down does not leave the board reporting seats
  as working indefinitely. State the mechanism — reconciliation at `lisa loop`
  startup, a `lisa status` diagnosis, a `lisa clean` category, or something else
  — and why it is the right place.
- A live seat is never released. State the test used to tell the two apart and
  what corroborates it, and prefer keeping a doubtful seat over clearing it.
- The operator can find out. Whatever the mechanism, `lisa status` should be able
  to say that a seat is held by a run that is no longer there, rather than
  reporting it among the working ones with no distinction.
- If it is not safely automatic, an explicit command is a good outcome. Something
  the operator runs deliberately, that lists what it would release and why before
  doing it — the shape `lisa clean` already uses.
- `attempts[]` in `lisa status --json` reflects the outcome, so a consumer reading
  the documented contract sees the same truth the prose does.
- The signal contract is unchanged. Consumers are still told not to read
  `.lisa/signals/` themselves, and this must not make those files something
  anybody else is expected to interpret.
- Recovery is written down where an operator will meet it, alongside the guidance
  that already exists for setting a project up.

## Notes

- The reporter is a status strip on the same desk (`rail`, in
  `~/swe/repos/screen-design`) which reads `attempts[]` exactly as `json-guide`
  describes, to avoid starting a second loop on one repository. It behaved
  correctly throughout; it is the input that went stale. It is shipping its own
  tolerance for this in the meantime, which stops mattering once Lisa reconciles.
- `lisa clean` was the first place looked and its scope is deliberate — it lists
  finished attempt folders and leaves everything Lisa did not write. Extending it
  is one option, not an assumption.
- The crash that produced this had nothing to do with Lisa: a BAML toolchain
  writing a ~40MB profile per test run filled memory until the machine swapped.
  Any process death does the same thing here, which is the point — it is not an
  exotic path.
