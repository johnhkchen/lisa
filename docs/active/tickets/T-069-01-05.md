## Context

**Read `S-069-01` first.**

`T-069-01-01` made `lisa` mean stable. It did not make an *existing* `lisa.rb`
mean stable, and the live tap proves the gap. After the `v0.5.0-rc.3` cut on
2026-08-14:

| formula | version | should be |
| --- | --- | --- |
| `lisa` | **0.5.0-rc.2** | 0.4.4 — the newest release that is not a prerelease |
| `lisa-nightly` | 0.4.4 | 0.4.4 |
| `lisa-canary` | 0.5.0-rc.3 | 0.5.0-rc.3 |

`scripts/publish-tap-formulae.sh:162-167` is why:

```
if [[ $is_prerelease == false ]]; then
    render "$stable_formula" stable ...
else
    echo "skipped Formula/$stable_formula.rb -- ... is a prerelease and stable never takes one"
fi
```

**Refusing to write a prerelease into stable is right. Leaving the prerelease
that is already there is not.** A prerelease cut skips the file, so the rc.2 that
the single-formula era put under the stable name simply stays, and every
prerelease cut from here leaves it there.

`dists/stable` in the apt archive has the correct `0.4.4`. So the two package
managers currently disagree about what stable means, and Homebrew is the wrong
one.

### This is not theoretical

The `screen-design` desk measured its Mac mini the same day: Homebrew `lisa`
0.4.4, and `brew outdated` reporting `0.4.4 < 0.5.0-rc.2`. The machine is
**exactly current on stable** — 0.4.4 is the newest non-prerelease and has been
since 2026-07-19 — and its package manager tells it otherwise every time it is
asked. That desk pinned the machine to stop an absent-minded `brew upgrade` from
taking it onto a release candidate.

Their proposed repair is two hand-dispatches of `publish-homebrew-tap.yml` — one
naming the newest stable to write `lisa.rb`, then one naming the newest release
to put `lisa-canary` back. It works, and it is a repair a person has to know
about and get the order right on. A publisher that cannot leave a tap correct in
one run is the defect.

## Acceptance Criteria

- **A publish leaves every formula naming the release its channel says it
  should**, in one run, whatever kind of release triggered it. After a
  prerelease cut, `lisa.rb` names the newest non-prerelease — not whatever was
  there before.
- **The prerelease refusal survives.** Stable must still never be written *from*
  a prerelease; the fix is that stable is written from the newest stable, not
  that the guard is loosened.
- **A run with nothing to change still writes nothing.** `T-069-01-01` earned
  the no-op-commit behaviour and correcting stale formulae must not cost it.
- **Reproduce it:** a tap seeded with a prerelease under `lisa.rb`, one publish
  from a prerelease tag, and `lisa.rb` afterwards naming the newest stable.
- **The live tap is corrected**, by this code path rather than by hand, and the
  end state recorded: `lisa` 0.4.4, `lisa-nightly` 0.4.4, `lisa-canary`
  0.5.0-rc.3.
- **The two-dispatch repair is written down** as the manual path for a tap that
  is already wrong, including that the second dispatch must name the *newest*
  release and not the one that was newest when the plan was written.

## Notes

- Ordering trap, found while checking `screen-design`'s rehearsal: their step 2
  named `v0.5.0-rc.2` because they rehearsed against a tap seeded before
  `v0.5.0-rc.3` existed. Run as written it would move `lisa-canary` *backwards*
  from rc.3 to rc.2. Whatever repair is documented has to name the newest
  release at the time it is run, not a literal.
- Between the two dispatches `lisa-canary` reads the older version, so a
  `brew upgrade lisa-canary` inside that window is a downgrade. Another reason
  the one-run fix is the real answer.
- `lisa-nightly` is not affected either way: `publish-homebrew-tap.yml` resolves
  it from `packaging/apt/nightly-tag.txt` on `main` (currently `stable`), not
  from the triggering tag.
- Worth deciding in review: whether `lisa.rb` should ever move *backwards*. This
  correction is a downgrade — rc.2 to 0.4.4 — and anyone who ran
  `brew upgrade lisa` in the single-formula era is holding rc.2 today. The
  honest answer is probably yes, with the runbook saying so out loud.
