## Context

T-055-01-01 stops the race and T-055-01-02 stops the livelock. This ticket is for the boards
that are already in it, and for every future rejection that turns out to be unclearable: **a
completion in `rejected` / `action-required` must have an action that works.**

Today it does not. From the field run, with the ticket's work committed and verified good:

- `lisa unblock <id>` reports "can run again" and returns the ticket to `review` — the phase
  that already failed. The next loop start re-attempts `MarkDoneKey`
  (`crates/lisa-plugin/src/lib.rs` ~661, ~2655) and re-fails identically.
- `lisa proposal dismiss <id>` refuses with "isn't waiting" once the ticket reads done.
- `lisa complete-ticket` invoked directly **succeeds and commits** — twice, at generations 2 and
  3 — and writes **no journal transition at all**, because the journal is written by the
  plugin's effect adapter and the CLI is plumbing beneath it. So the operator can seal the work
  and still not convince Lisa it happened.

Both completion tracks for that ticket (`attempt_id: "1"` and `attempt_id: "operator"`)
terminate at `rejected`. There is no supported sequence that moves either to a terminal success.
The operator's actual escape was to move the ticket out of `docs/active/tickets/` so Lisa would
stop looking at it — which is a bug report, not a workflow.

Three things this must produce, and the design decides how they are packaged:

1. **A documented operator route from `rejected` to a terminal, recorded state**, when the work
   is verifiably committed. Whether that is `unblock` learning to reconcile, or a named
   command, is design's call — but it writes a journal transition, so board and journal agree
   afterwards.
2. **A bound on re-attempting `MarkDoneKey`.** N2 asks that recovery be bounded and end in a
   named actionable state. Re-attempting on every loop start, forever, is neither. After the
   bound, the ticket sits in a state that says what happened and what to run — and stops
   consuming a seat and a pane.
3. **A disposition written from a failed internal command must not present that command's error
   text as a review reason.** The field disposition read
   `{"disposition":"block","reason":"… Error: ticket T-002-05 has no changes in the requested
   include paths"}`, and the operator reasonably read `block` as a verdict on the work and went
   looking for what was wrong with twelve recipes. Nothing was. A transport failure and a review
   judgement are different things and the record should not conflate them (P2 — state means what
   it says).

_Advances: N2 — bounded recovery ending in a named **actionable** state, where today the state is
named and the action does not exist. And P5 — a real field failure closed at the boundary that
failed._

## Acceptance Criteria

- [ ] A completion in `rejected` / `action-required`, whose intended commit is verifiably at
      HEAD, can be moved to a terminal recorded success by a single documented command. A test
      drives the full field sequence — lost race, rejection, recovery — and asserts the journal
      ends terminal and the board agrees with it.
- [ ] `MarkDoneKey` re-attempts are bounded. A test asserts that a repeatedly-failing completion
      stops being retried, names the state it lands in, and names the command that clears it.
- [ ] A disposition produced by a failed internal command is distinguishable from a review
      verdict — by field, not by reading the prose — and its reason does not present a command's
      error text as a judgement about the work. A test asserts a transport failure never
      produces a disposition indistinguishable from a reviewer's `block`.
- [ ] The recovery path writes a journal transition. Invoking the underlying plumbing directly
      still works as plumbing, but the supported operator route leaves board and journal in
      agreement.
- [ ] `lisa unblock`'s existing meaning for ordinary parked tickets is unchanged — whatever
      carries the recovery, it does not repurpose unblock's behavior for cases that work today.
- [ ] `just check` green (fmt, clippy, WASM check, workspace tests).
