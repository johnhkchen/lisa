## Context

**Read `S-068-01` first.**

The Mac mini is the first machine in the fleet with a stated job. It runs
background workloads on a schedule — real work, nothing whose failure costs us
anything in front of anyone. Its role is to **meet the next release before a user
does**, so a bug in an rc becomes a broken Mac mini on a Tuesday morning instead of
a broken install after we promote it.

That role has two requirements the previous two tickets do not satisfy on their own.

**It has to keep moving.** A nightly box that waits for a human to run `lisa
upgrade` is a stable box with extra steps, and it will drift into staleness exactly
the way the curl-installed machines did — those went four weeks behind without
anyone deciding they should. Insurance you have to remember to renew is not
insurance.

**It has to be loud, and it has to be reversible.** A mini that quietly breaks and
sits there broken is worth nothing, and an unattended upgrade with no way back is a
machine we will be nervous about. Rollback is what makes automatic movement safe to
agree to.

## Acceptance Criteria

- **The mini upgrades on its own schedule, unattended**, on the `nightly` channel.
  Say where that schedule lives — a launchd job, a cron entry, whatever is right for
  macOS — and write it down somewhere a person can find it later.
- **An upgrade never lands mid-run.** Lisa is driving agent sessions on this box. An
  upgrade that swaps the binary under a live loop is a worse failure than being one
  release behind, so it waits for an idle moment or it does not happen this cycle.
- **A failed upgrade leaves the working version in place.** Downloading, verifying
  and swapping must not be able to strand the mini with no usable `lisa`.
- **A broken nightly reaches us the same morning.** State the signal — the mini's
  own `doctor --json` collected somewhere we look, a failed background run that
  reports, the loop failing loudly. Do not leave this as "we'll notice."
- **Rollback is one command and it is tested for real**, not just described: put the
  mini on a known-bad tag, run `lisa upgrade --tag <previous>`, and confirm the
  workloads run again.
- **The mini is actually on nightly at the end of this ticket**, verified with
  `lisa doctor` showing channel `nightly` and level with it — and the run it does
  next is recorded, so we know the arrangement works rather than assuming it does.
- **The soak window is exercised at least once.** A tag newer than the window must
  be visible and correctly *not* taken.

## Notes

- This is deliberately the only machine changed here. The stale curl-installed boxes
  and the workload machines stay exactly where they are until the nightly
  arrangement has proven itself on the mini — moving the whole fleet at once removes
  the control group.
- Worth recording as this runs: how often nightly actually catches something. If it
  catches nothing over several releases, the honest conclusion is that the soak
  window is the wrong length or the workloads are not exercising Lisa hard enough,
  not that the releases were fine.
- macOS installs Zellij separately (`brew install zellij`) rather than using the
  pinned `/usr/libexec/lisa/zellij` that apt boxes get, so a Lisa upgrade on the
  mini can drift out of `SUPPORTED_ZELLIJ_RANGE` in a way a Linux box would not.
  `doctor` already checks this; make sure the unattended path does not ignore it.
