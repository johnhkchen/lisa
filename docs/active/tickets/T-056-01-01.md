## Context

This ticket is about what the operator reads, and is deliberately independent of why the check
failed. Even after T-056-01-02 lands, the next check that misbehaves for a different reason will
produce the same unreadable dead end, and the operator will have the same nothing to work with.

What they get today (`crates/lisa-cli/src/unblock.rs` ~164–166, ~245–251, ~275–286):

```
$ lisa unblock T-010-03
That didn't work yet — No build at dist/. Run: npm run build
$ echo $?
1
```

Every word after the dash was written by the *project's* script — `check-touch.mjs` ~191 — and
Lisa has quoted it without attribution. Nothing on screen says a check ran, what the check was,
where it ran, or what it exited with. The operator cannot tell Lisa's finding from the script's
finding, cannot tell "the check looked and said no" from "the check could not look", and cannot
reproduce it: they ran the same command by hand from the project and it passed.

Three separable things, all in this ticket because they are one message:

1. **Attribute and show the work.** A decline that came from running a check reports the check
   string as recorded, the directory it ran in, the exit code, and the captured output — labelled
   as the check's output, not as Lisa's sentence. The existing `MAX_CAPTURE_BYTES` /
   `MAX_OBSERVATION_CHARS` caps and `sanitize_observation` (~289) stay; this is about what is
   *shown*, not about capturing more.

2. **"Could not look" is not "did not pass."** `run_check` collapses every non-zero exit into
   `CheckResult::Failed`, and `decline_message` words all of them as a verdict. Give the
   inconclusive case its own result and its own wording — a check reporting a missing
   prerequisite is not evidence about the remedy. Where the line between them is drawn is
   design's call (a distinguished exit code is one option; the field case exits 2 for exactly
   this reason). What is pinned: an inconclusive result never reads as a judgement on the
   operator's work, and it always names the way through.

3. **A way through that always exists.** `lisa unblock` has exactly two arguments today
   (`main.rs` ~126–133) and no override. An operator who has performed the ask and verified it
   themselves must not be permanently held by a gate that cannot be satisfied — that is the N2
   violation this story was opened on: a named state with no action that works. Add the override,
   and record that it was used, so a forced unblock is visible afterwards rather than
   indistinguishable from a passing one (P2).

Do not change what the check does or where it runs — that is T-056-01-02. If the two tickets
disagree about a cwd, this one reports whatever `run_check` actually used.

_Advances: P2 — the message corresponds to what happened, and a failure Lisa cannot verify stays
visible instead of being mislabelled as a verdict. And N2 — recovery ends in a state with an
action that works._

## Acceptance Criteria

- [ ] A declined unblock caused by a check reports, in the output: the check string as recorded,
      the working directory it ran in, the exit code, and the captured stdout/stderr attributed
      to the check. A test pins the rendering against a fixture check that exits non-zero with
      known output on both streams.
- [ ] A check that cannot run is a distinct `CheckResult` variant from one that ran and failed,
      with distinct wording that does not assert the remedy was not done. Tests cover both
      variants and pin both strings; the existing `TimedOut` and `ChangedFiles` strings still
      render distinctly.
- [ ] `lisa unblock <id>` gains a documented override flag. With it, a ticket whose check
      declines is reopened (`UnblockOutcome::Reopened`, exit 0); without it, behaviour is
      byte-identical to today apart from the new reporting. A test asserts both.
- [ ] A forced unblock leaves a durable record naming that the check was overridden and by whom
      (operator actor), so it is distinguishable after the fact from a check that passed. A test
      asserts the record exists and that an ordinary unblock writes no such record.
- [ ] `sanitize_observation`'s escape-sequence and control-character stripping still applies to
      everything shown; a fixture check emitting ANSI sequences and tabs renders clean.
- [ ] The field line is reproduced and then improved: a test whose check prints
      `No build at dist/. Run: npm run build` to stderr and exits 2 produces output naming the
      command, the cwd and exit code 2, and does not present that sentence as Lisa's verdict.
- [ ] `just check` green (fmt, clippy, WASM check, workspace tests).
