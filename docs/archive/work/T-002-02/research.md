# T-002-02 Research: Config Validation

## What Exists

### Config file format (.lisa.toml)

The config file has two sections, parsed via serde into typed structs in `crates/lisa-cli/src/config.rs`:

```toml
[dirs]
tickets = "docs/active/tickets"
stories = "docs/active/stories"
work = "docs/active/work"

[scheduling]
max_threads = 2
# auto_advance = false
```

### Parsing pipeline

1. `load_config(root)` in `config.rs:57` reads `.lisa.toml` from disk, returns `LisaConfig` (serde-deserialized). Missing file → defaults. Parse error → `Err(String)`.
2. `resolve_config(&LisaConfig, cli_max_threads)` in `config.rs:73` merges file values with CLI overrides. Precedence: defaults < .lisa.toml < CLI flags.
3. Result is `ResolvedConfig` with concrete values used by `loop_cmd::run_loop` and the Zellij layout generator.

### Current types

```rust
// config.rs
struct LisaConfig { dirs: DirsConfig, scheduling: SchedulingConfig }
struct DirsConfig { tickets: Option<String>, stories: Option<String>, work: Option<String> }
struct SchedulingConfig { max_threads: Option<usize>, auto_advance: Option<bool> }
struct ResolvedConfig { ticket_dir: String, story_dir: String, work_dir: String, max_threads: usize, auto_advance: bool }
```

`max_threads` is `Option<usize>` — serde parses negative TOML integers as error (TOML integers are i64, usize parse fails for negatives). Zero is silently accepted. `usize` prevents negative values at the parsing level for valid TOML, but 0 is a valid usize.

### Consumers of config

- `main.rs:75` — `load_config` called in `Loop` command handler. Parse errors already exit with error.
- `init.rs:181` — `load_config` called in `run_validate`. Parse errors surfaced as validation errors.
- `loop_cmd.rs:10` — `run_loop` receives `ResolvedConfig`. Uses `max_threads` for layout generation (number of agent panes).
- `lib.rs:280` (plugin) — uses `PluginConfig::from_config_map` from Zellij's BTreeMap, separate path from CLI config. Plugin config comes from KDL layout, not .lisa.toml directly.

### Current validation gaps (what the ticket requires)

1. **max_threads = 0**: Currently silently accepted. `generate_layout` would create 0 agent panes — the loop would start with no workers. Should be rejected.
2. **Negative max_threads**: TOML uses i64 for integers. Serde will fail to parse negative i64 into `Option<usize>`, but the error message is a raw serde/toml parse error, not a user-friendly message about max_threads specifically.
3. **Unknown keys**: serde `#[derive(Deserialize)]` with default behavior silently ignores unknown fields. A user typing `max_thread = 4` (typo, missing 's') gets no feedback — value ignored, default 2 used. This is the "unknown keys warned about" acceptance criterion.
4. **Missing optional fields use defaults silently**: Already works — all fields are `Option<T>` with `#[serde(default)]`, and `resolve_config` fills defaults. No changes needed for this criterion.

### serde deny_unknown_fields behavior

Adding `#[serde(deny_unknown_fields)]` to the structs would cause parse failures on unknown keys. But the ticket says "warned about", not "rejected" — so we want warnings, not hard errors. This means we can't use serde's built-in mechanism directly. We need a custom approach.

### Approaches for unknown key detection

- **toml::Value approach**: Parse TOML first as `toml::Value` (a generic table), compare keys against known set, collect unknown keys as warnings. Then deserialize normally into typed struct.
- **serde_ignored crate**: A crate specifically for tracking ignored fields during deserialization. Adds a dependency.
- **Manual key enumeration**: After parsing into `toml::Value`, walk the table structure and check keys.

### Where validation should live

Currently `load_config` returns `Result<LisaConfig, String>`. Validation could:
- Return a richer result with warnings (struct with config + warnings vec)
- Print warnings to stderr directly (simpler, but less testable)
- Return a separate validation result type

### Existing test coverage

`config.rs` has 11 tests covering: full/empty/partial parsing, missing file, valid file, invalid TOML, resolve with defaults/overrides/CLI. No tests for semantic validation (max_threads=0, unknown keys).

### Plugin-side config

`PluginConfig::from_config_map` in `types.rs:393` silently skips unparseable `max_threads` values. This is a separate code path from the CLI config. The plugin receives config through the KDL layout, which is generated by the CLI from the already-resolved config. So validation in the CLI path covers both paths — invalid values never reach the plugin.

## Summary

The config pipeline: `.lisa.toml` → `load_config` → `LisaConfig` → `resolve_config` → `ResolvedConfig`. Validation needs to happen between parsing and resolution. Three gaps: reject max_threads=0, warn on unknown keys, and provide clear error messages for invalid numeric values. Missing optional fields already default silently.
